# Results: batch upload survives a reload / killed PWA

Date: 2026-10-12.

## Design decision

Two sources of truth, each for what it can know:

- **Server: what already became a receipt.** New `GET /api/receipts/my-unsaved`
  returns the caller's own receipts (`UploadedByUserId` = JWT `sub`) from the
  last 24 h that are not saved, newest first, max 20. The capture screen shows
  them as «Недавние загрузки» / “Recent uploads” with live status (polls every
  2 s while any is queued/processing). Works after any reload, on any device.
- **Device: photos that may not have reached the server.** Photo bytes are
  kept in IndexedDB until the server answers for each photo; after a reload
  (or leaving the screen mid-batch) the screen shows «Загрузка прервалась»
  with «Продолжить загрузку (N фото)» / «Не продолжать».

Why IndexedDB with bytes rather than "tell the user to re-pick": re-picking
on iOS is error-prone (photo-library picks get generic names and new
timestamps, so the user cannot tell which ones are missing), and iOS may
re-encode a re-picked photo, which would defeat server dedup. Storing the
exact bytes makes resume one tap and keeps idempotency exact.
Bytes are stored as `ArrayBuffer` (not `Blob`) to avoid old Safari
Blob-in-IndexedDB bugs and to be structured-clone-safe everywhere.

Safety limits: total kept bytes capped at 100 MB per batch (10 typical iPhone
photos are 20–50 MB); a photo over the cap or refused by storage (quota,
private mode) keeps only its name and is listed as "pick again". Batches
older than 24 h or started by another user are dropped on load. Each photo's
bytes are deleted as soon as the server has it; the whole record is cleared
when every photo is sent, on «Не продолжать», or on «Загрузить другие фото».
Every storage call is wrapped in try/catch; with no IndexedDB the screen
behaves exactly as before (server panel still works).

Idempotency: no client id needed. The server already deduplicates by the
SHA-256 of the image set; resume re-sends the identical bytes, so a photo
whose response was lost comes back as `exactDuplicate` («Уже был загружен»),
never a second receipt. One small server change closes the remaining gap:
`POST /api/receipts?process=true` on an exact duplicate that is still
`Uploaded` (stored but never queued, e.g. the request died between store and
queue) now queues it. Duplicates in any other status are untouched.

Rate limit: resume goes through the same sequential batch loop, so a 429
stops it with the existing «Лимит загрузок» / wait-minutes UX; the unsent
photos stay on the device for a later «Продолжить загрузку». A resent photo
spends one token like any upload.

No migration: the query uses existing columns and the existing `CreatedAt`
and `Status` indexes on `receipt_captures`.

## Known limitations

- Photos are kept only on the device that started the batch; the server
  panel is the cross-device view.
- A photo that did not fit the 100 MB cap or storage must be re-picked; its
  identity is only its file name.
- iOS can still evict a web app's storage under heavy disk pressure; then
  the notice simply does not appear and the server panel remains.
- Session expiry (as opposed to explicit sign-out) keeps the stored batch, so
  the same user can resume after signing in again.

## Review follow-up (2026-10-12)

1. Privacy: explicit sign-out (`AuthGate.signOut`) now clears the stored
   batch (`deviceBatchStore.clear()`, errors swallowed). The user check is
   strict: any mismatch, including a batch stored without a user and opened
   by one (or the reverse), drops it. Tests: `AuthGate.test.tsx` (sign-out
   clears), `pendingBatchStore.test.ts` (null on either side = other person).
2. While «Загрузка прервалась» is shown, the photo pickers are hidden and the
   notice says to continue or press «Не продолжать» first (all-lost case:
   «Понятно»). So a new batch can no longer silently replace the interrupted
   one. Test in `CapturePage.resume.test.tsx`.
3. A photo the server refused for good (4xx other than 401/403/408/429, e.g.
   400 unsupported/empty, 413 too large) is marked done on the device, so it
   is not offered again after a reload; in the current session it stays
   «Не удалось загрузить» with «Повторить». Network errors and 5xx stay
   resumable. Store method renamed `markSent` → `markDone`. Test in
   `CapturePage.resume.test.tsx`.
4. «Недавние загрузки» polling: 2 s while something is recognising, 30 s
   after a failed fetch, off when nothing is active
   (`recentUploadsPollInterval`, unit-tested).
5. Help `capture-batch` (ru/en): pickers are blocked while the notice is up;
   «Уже был загружен» after resume means the answer was lost, no second
   receipt; «Понятно» when no photo was kept; refused photos are not offered
   again.

Checks after follow-up: `npx tsc -b` clean; `npm test` 37 files, 301 tests
passed; `npm run build` ok; `./scripts/dotnet.sh test` 626 passed, 8 skipped,
0 failed; `data/purchases.db` unchanged (1788010733 / 118784).
