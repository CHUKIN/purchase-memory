## What was built
- Contract `IReceiptTextLocator` (Application) + `AzureDocumentIntelligenceTextLocator`
  (Infrastructure): REST `prebuilt-read` v4.0 (`2024-11-30`), POST + poll, 1.1 s
  request spacing, Retry-After / 429 (3 waits ≤ 60 s), 30 s timeout per request,
  30 polls max. Env `AZURE_DOCINTEL_ENDPOINT` (https only) / `AZURE_DOCINTEL_KEY`,
  read like the other provider keys; absent → `IsConfigured=false`, nothing sent.
  The key goes only to the configured host (a foreign `Operation-Location` is
  refused). Logs: stage, HTTP status, Azure's short error code, timings — never
  key, photo, recognised text or URLs.
- Background `ReceiptTextLocationWorker` + `ReceiptTextLocationService`: one
  DB-driven loop for new receipts and the backfill (newest first). State lives on
  `receipt_captures` (`TextLocationStatus` NotRequested/Located/Unavailable/Failed,
  `TextLocationAttempts` = tries for the retry limit, `TextLocationCalls` = calls for
  the budget, `TextLocationAttemptedAt`) → idempotent, resumes after a restart. The
  call is counted and saved BEFORE Azure is called (receipt reads Failed until an
  outcome is recorded), so a crash, malformed answer or failed save afterwards can
  never cause an uncounted retry. Starts 60 s after the app, woken by a doorbell when recognition finishes
  (save/recognition paths only ring it, never wait). Sends the single *viewing*
  copy (EXIF applied, same image the app shows); multi-photo / >4 MB photos are
  marked Unavailable without a call. Failures: passing (incl. any exception while
  handling the answer) → retried after 60 min, max 3 tries; refused photo → never
  again; 429 → pause by Retry-After, 401/403/404 → pause 6 h — these two give the
  receipt its try back (a wrong key never makes good receipts Unavailable) but the
  call still counts toward the budget. Budget `TextLocation__*`: 450 calls/month total (UTC month), backfill
  stops at 300; 10 s between receipts.
- Matching `ReceiptTextMatcher` + `ReceiptTextSimilarity`: port of
  `highlight_study/analyze.py` (`hybrid_words` on the line layer, `snake`, combo
  paddings 0.30/0.10) incl. Python `difflib.SequenceMatcher.ratio` (autojunk too).
  Re-runs from the stored layout on every review save and purchase correction
  (`IReceiptTextHighlighter`), so renamed/moved/deleted lines never keep another
  line's outline. Haiku extraction, prompt and model unchanged.
- Migration `AddReceiptTextHighlight` (SQLite `20261018155538`, PG `20261018155541`):
  4 columns on `receipt_captures` (+ index on status), `TextPolygons` (JSON text,
  default `[]`) and `BoxSource` (default `Recognition`) on `receipt_capture_items`,
  table `receipt_text_layouts` (1:1, cascade; lines + words with pixel quads and
  page size; ~20–40 KB per receipt, never loaded by lists). Down drops all of it.
- API: `textPolygons` (`[[x0,y0,…],…]`, photo fractions like `boundingBox`) and
  `boxSource` (`recognition`/`azure`) on snapshot items and purchase detail items;
  `textPolygons` on item issues. `boundingBox` unchanged (fallback). Output only.
- Web: `TextHighlight` SVG overlay ("combo": rgb(255,196,0) ×0.45 multiply over the
  union of outlines, 2 px `#9c5a14` outer contour via masks, rest dimmed ×0.70) in
  `LinePhoto` (inside the zoom layer, edge stays thin when zoomed) and in the
  IssueReview crop; crop/zoom window fits the outline bounds; fallback to the old
  frame. Stories: LineReview `PrintedText`, `PrintedTextTwoRows`, `PrintedTextZoomed`,
  `PrintedTextFallback`; IssueReview `PhotoFragmentPrintedText` (tilted stand-in
  photo, `storyReceipt.ts`).
- Help (ru + en, `receipt-lines-photo` + capture topic): how the highlight looks,
  that it appears a few seconds after recognition, frame fallback, wrong-line case.
  Alt texts «выделена строка» / "highlighted". Env vars in
  `docs/ПЕРЕМЕННЫЕ_И_СЕКРЕТЫ.md`, `docs/secrets.template.env`.

## Known limitations
- Multi-photo receipts: no Azure call, whole first photo as before (non-goal).
- Curved/crumpled paper: outlines follow words but a crease can split a line
  (study: 4/265 failures on h08_05, h10_09).
- A line renamed far from the print and with a price not on the receipt falls back
  to the frame; identical printed lines may swap (first unused line wins).
- The highlight appears only after the worker processed the receipt (~5–15 s); an
  already open screen shows the frame until it refetches.
- If recording the answer fails (e.g. a DB error), the call is still counted and the
  receipt is retried after 60 min (one more call, within the try limit and budget).
- Monthly budget = calls on receipts last tried this month; a receipt also tried in
  an earlier month is counted whole (over-count only). Every call is counted before
  it is sent, so no path under-counts.
- Old receipts without a display copy send the original; if it carries EXIF
  rotation the outlines may not line up (prod has display copies from day one;
  only very old local receipts lack them).
