# Личный учёт покупок — первоначальный план

Статус: черновик для обсуждения  
Дата: 13 июля 2026  
Рабочее название: **Purchase Memory** (название потом можно заменить)

## 1. Идея проекта

Сделать личную историю покупок, к которой можно обращаться разговорным языком:

- «Когда и где я покупал этот сыр?»
- «Какие сорта кофе я уже пробовал и какие понравились?»
- «Сколько этот товар стоил в прошлый раз?»
- «Что я покупал в этом магазине за последний год?»
- «Покажи товары, которым я поставил низкую оценку».

Данные можно будет добавлять несколькими способами:

1. сфотографировать чек;
2. отдельно сфотографировать товар, штрихкод или ценник;
3. продиктовать или написать покупку вручную;
4. позже — обработать набор фотографий или видео из пакета.

Основной интерфейс первой версии — MCP-сервер. GPT-клиент выбирает подходящий инструмент, задаёт уточняющие вопросы и показывает результат. Собственный полноценный UI на старте не нужен.

## 2. Короткая рекомендация

Для первой версии я рекомендую:

- **C# и ASP.NET Core**, на актуальной LTS-версии .NET на момент начала реализации;
- **официальный MCP C# SDK**;
- **PostgreSQL** как основную базу;
- **EF Core + Npgsql** для доступа к данным и миграций;
- обычную файловую систему для изображений локально, но через абстракцию `IBlobStorage`;
- Docker Compose для API, PostgreSQL и, при необходимости, фонового worker-процесса;
- модульный монолит, а не микросервисы;
- отдельный Python-worker только тогда, когда появится подтверждённая необходимость в локальном OCR, computer vision или видео.

Главная мысль: **использование моделей не обязывает писать весь проект на Python**. Мы не собираемся обучать модель в первой версии. ASP.NET Core хорошо подходит для API, фоновых заданий, PostgreSQL, Docker и MCP, а C# уже знаком владельцу проекта. Это важнее гипотетического удобства Python.

## 3. Что важно проверить до большой разработки

### 3.1. MCP на компьютере и телефоне — разные сценарии

Локальный MCP через `stdio` прекрасно подходит для локального клиента на том же Mac. Для удалённого клиента используется Streamable HTTP и защищённый HTTPS-доступ.

На 13 июля 2026 года официальная документация ChatGPT говорит, что пользовательские MCP-приложения доступны в ChatGPT только на web и для определённых workspace-планов; мобильные MCP apps пока не поддерживаются. Локальный MCP также нельзя подключить к ChatGPT напрямую: нужен Secure MCP Tunnel или удалённый HTTPS-сервер.

Следовательно, перед реализацией нужно провести короткий **capability spike** именно с тем тарифом и клиентами, которыми планируется пользоваться.

Если добавление с телефона обязательно уже в MVP, запасные варианты:

- iOS/Android Shortcut, отправляющий фото в upload endpoint;
- очень маленькая PWA-страница только с кнопкой «сфотографировать/загрузить»;
- бот в мессенджере;
- синхронизируемая папка, которую локальный worker отслеживает и обрабатывает.

Это не отменяет MCP как основного интерфейса для поиска и редактирования.

### 3.2. Нельзя заранее полагаться на передачу вложения в MCP tool

Аргументы MCP-инструмента описываются JSON Schema. Клиент может уметь видеть приложенное пользователем изображение, но это ещё не гарантирует, что он передаст исходный файл стороннему MCP-серверу.

Поэтому нужны два совместимых пути приёма данных:

1. **Client-assisted extraction:** GPT-клиент сам видит чек, извлекает структуру и вызывает `create_purchase_draft` с JSON. Это самый дешёвый MVP.
2. **Backend-owned extraction:** оригинал сначала загружается в наше хранилище, затем backend/worker распознаёт его и создаёт такой же черновик.

Оба пути должны приводить к одной и той же структуре черновика и обязательному подтверждению человеком.

## 4. Почему PostgreSQL, а не NoSQL

Предметная область естественно реляционная:

- одна покупка сделана в одном месте и содержит много строк;
- строка покупки может быть связана с вариантом товара;
- магазин может иметь сеть и конкретную точку;
- один товар покупается многократно по разным ценам;
- у товара могут быть оценки, заметки, фотографии и теги;
- нужны фильтры по датам, ценам, магазинам, категориям и оценкам.

PostgreSQL даёт сразу несколько нужных режимов хранения:

- нормальные реляционные таблицы для фактов;
- `jsonb` для сырого результата распознавания и нестабильных метаданных;
- полнотекстовый и нечёткий поиск (`pg_trgm`) по названиям;
- агрегаты и отчёты через SQL;
- `pgvector` позже, если семантический поиск действительно будет полезен.

NoSQL здесь не даёт заметного выигрыша, зато усложнит связи, дедупликацию, историю цен и отчёты.

### SQLite как альтернатива

SQLite годится для сверхбыстрого одноустройственного прототипа, но переход на PostgreSQL всё равно понадобится при удалённом доступе и фоновой обработке. Поскольку PostgreSQL легко запускается в Docker, лучше начать сразу с него.

## 5. Рекомендуемая архитектура

```text
GPT/Codex/MCP client
        |
        | MCP: stdio локально или Streamable HTTP удалённо
        v
+---------------------------+
| ASP.NET Core application  |
|                           |
| MCP tools                 |
| Application services      |
| REST upload endpoint      |
| Search/query layer        |
| Background job runner     |
+-------------+-------------+
              |
       +------+-------+
       |              |
       v              v
  PostgreSQL      Media storage
  facts + jobs    local / S3-compatible
       |
       v
Optional extraction adapters
GPT vision API / OCR / Python CV worker
```

Начать стоит с **модульного монолита**. Пример модулей внутри одного solution:

- `Purchases` — покупки и строки чека;
- `Catalog` — товары, варианты, штрихкоды, категории и алиасы;
- `Merchants` — сети и точки магазинов;
- `Media` — изображения и другие исходники;
- `Ingestion` — распознавание, нормализация и задания;
- `Search` — запросы и отчёты;
- `Mcp` — тонкий адаптер над application services.

MCP не должен содержать бизнес-логику. Это только один вход в приложение. Тогда позже можно добавить PWA, Telegram, REST или CLI без переписывания ядра.

## 6. Предлагаемый стек

| Область | Основной выбор | Альтернативы | Комментарий |
|---|---|---|---|
| Backend | C#, ASP.NET Core | Python/FastAPI; TypeScript/Fastify | C# знаком владельцу и хорошо подходит для долгоживущего backend |
| MCP | официальный MCP C# SDK | Python SDK; TypeScript SDK | Поддерживает локальный `stdio` и удалённый Streamable HTTP |
| Database | PostgreSQL | SQLite для throwaway-прототипа | SQL + `jsonb` + полнотекстовый поиск |
| ORM | EF Core + Npgsql | Dapper | EF удобнее для старта и миграций; Dapper можно добавить точечно |
| Media local | bind-mounted directory | MinIO | MinIO не нужен в самом первом compose |
| Media hosted | Supabase Storage или S3-compatible storage | Cloudflare R2 и аналоги | Выбирать ближе к деплою, цены и лимиты меняются |
| Background jobs | таблица jobs в PostgreSQL + `BackgroundService` | Hangfire/Quartz; отдельная очередь | Не добавлять Redis/RabbitMQ до реальной нагрузки |
| Tests | xUnit + Testcontainers | NUnit | Интеграционные тесты должны работать с настоящим PostgreSQL |
| Observability | structured logs + OpenTelemetry | Sentry и hosted APM позже | Особо логировать pipeline распознавания без утечки секретов |
| API docs | OpenAPI | — | Полезно даже при основном MCP-интерфейсе |
| Local orchestration | Docker Compose | .NET Aspire | Aspire можно оценить позже, Compose более переносим |

### Когда всё-таки нужен Python

Python стоит добавить отдельным worker-контейнером, если потребуется:

- PaddleOCR, docTR, OpenCV или другая Python-first CV-библиотека;
- локальная модель распознавания;
- извлечение кадров и анализ видео;
- экспериментальные ML-pipelines и notebooks.

Связь с C# можно начать с простой таблицы заданий в PostgreSQL и HTTP-вызова. Не нужно заранее вводить Kafka, gRPC или микросервисную платформу.

### Альтернатива: всё на Python

FastAPI + SQLAlchemy + Alembic + официальный MCP Python SDK дадут быстрый AI-прототип. Минусы для этого проекта: владельцу сложнее сопровождать код и типы предметной области, а реальной ML-части в MVP почти нет.

### Альтернатива: TypeScript

TypeScript + официальный MCP SDK удобны для Apps SDK и возможного web UI. Но для текущей задачи они не дают преимущества над C#, достаточного для отказа от знакомого языка.

## 7. Основная модель данных

Названия ниже рабочие. До кода нужно оформить ER-диаграмму и миграцию.

### `Purchase`

Факт одной покупки/транзакции:

- `Id`;
- дата и время покупки отдельно от даты внесения;
- `MerchantLocationId`;
- валюта;
- итог чека, скидка, налог — если известны;
- способ ввода;
- статус `Draft`, `NeedsReview`, `Confirmed`, `Rejected`;
- confidence и предупреждения;
- ссылка на исходный чек;
- timestamps.

### `PurchaseItem`

Строка покупки:

- оригинальный текст строки чека — хранить всегда;
- нормализованное название;
- `ProductVariantId`, если удалось сопоставить;
- количество и единица измерения;
- цена за единицу;
- сумма строки;
- скидка;
- confidence каждого распознанного поля;
- ручные исправления и признак подтверждения.

Деньги хранить как `decimal/numeric`, никогда не `float`. Валюту хранить явно. Количество должно поддерживать не только штуки, но и вес.

### `Product` и `ProductVariant`

Важно разделить:

- `Product` — общая сущность, например «Milka молочный шоколад»;
- `ProductVariant` — конкретная упаковка/вкус/объём/штрихкод, например 90 г;
- `ProductAlias` — варианты названия из чеков и пользовательские названия;
- `Barcode` — EAN/UPC/другие идентификаторы.

Не нужно насильно создавать товар для каждой строки чека. Сначала строка может жить только с оригинальным названием, а сопоставление выполняется позже.

### `Merchant` и `MerchantLocation`

- `Merchant` — сеть или продавец;
- `MerchantLocation` — конкретный адрес/онлайн-магазин;
- алиасы названий из чеков;
- координаты — только если позже понадобятся.

### `ProductExperience`

Впечатление пользователя не стоит хранить одним полем внутри товара, потому что мнение может измениться:

- оценка по выбранной шкале;
- «понравилось / не понравилось / нейтрально»;
- текст заметки;
- дата;
- контекст или конкретная покупка;
- фотографии.

### `MediaAsset`

- тип: чек, товар, штрихкод, ценник, видео;
- storage key, MIME type, размер, hash;
- дата создания и загрузки;
- технические метаданные;
- связь с покупкой/товаром/job;
- политика удаления.

Hash нужен для обнаружения повторной загрузки.

### `IngestionJob` и `ExtractionAttempt`

- тип и статус задания;
- ссылка на входной media asset;
- версия extractor-а и prompt-а;
- сырой ответ в `jsonb`;
- нормализованный результат;
- ошибки и timings;
- число попыток;
- стоимость/tokens, если используется платный API.

Нужно хранить не только итог, но и происхождение результата. Это позволит перепроцессить старые чеки улучшенным распознавателем.

## 8. Черновик MCP-контракта

Не нужно делать MCP-копию каждой CRUD-операции. Инструменты должны выражать пользовательские намерения.

### Команды

- `create_purchase_draft` — создать черновик из структурированных данных;
- `create_media_upload` — получить безопасный способ загрузить файл;
- `process_receipt` — запустить обработку уже загруженного чека;
- `add_or_update_purchase_items` — дополнить или поправить строки;
- `confirm_purchase` — явно подтвердить черновик;
- `attach_product_photo` — связать фото с товаром/строкой;
- `record_product_experience` — добавить оценку и заметку;
- `merge_product_variants` — ручное объединение дублей с подтверждением.

### Чтение

- `get_purchase`;
- `get_ingestion_status`;
- `search_purchases`;
- `search_products`;
- `get_product_history`;
- `compare_product_prices`;
- `list_items_needing_review`;
- `get_spending_summary` — позже.

### Правила безопасности и качества

- команды записи должны быть идемпотентны через `idempotency_key`;
- `confirm_purchase` отделён от распознавания;
- MCP-ответы возвращают стабильный структурированный результат, а не только красивый текст;
- опасные операции объединения/удаления требуют подтверждения;
- доступ MCP к базе только через application services, без инструмента «выполни произвольный SQL»;
- описания инструментов должны явно объяснять модели, когда их использовать и когда не использовать.

## 9. Потоки добавления данных

### Поток A — самый дешёвый MVP

1. Пользователь прикладывает фото чека в GPT-клиенте.
2. Модель читает чек.
3. Модель вызывает `create_purchase_draft` и передаёт распознанные поля.
4. Backend валидирует арифметику и обязательные поля.
5. MCP возвращает краткое резюме и список сомнений.
6. Пользователь исправляет данные разговором.
7. Вызывается `confirm_purchase`.

Плюс: можно проверить ценность проекта без отдельной оплаты vision API.  
Минус: оригинальное изображение и воспроизводимость распознавания зависят от возможностей клиента.

### Поток B — backend владеет оригиналом

1. Пользователь/Shortcut/PWA получает upload URL.
2. Фото сохраняется как `MediaAsset`.
3. `process_receipt` создаёт `IngestionJob`.
4. Adapter вызывает multimodal API или локальный OCR.
5. Нормализатор создаёт тот же `PurchaseDraft`.
6. Валидатор проверяет суммы, валюту, дату и дубли.
7. Пользователь подтверждает результат через MCP.

Это целевой надёжный поток.

### Поток C — фото товара после чека

1. Пользователь указывает покупку или строку чека.
2. Загружает фото лицевой стороны и/или штрихкода.
3. Система извлекает бренд, название, вариант, массу и EAN.
4. Предлагает связать строку чека с существующим вариантом товара.
5. Пользователь подтверждает связь.

### Поток D — видео из пакета, значительно позже

1. Видео загружается как media asset.
2. Worker извлекает кадры по смене сцены/резкости.
3. Выбираются лучшие кадры товара, ценника и штрихкода.
4. Кадры обрабатываются как обычные фотографии.
5. Результаты группируются и дедуплицируются.
6. Пользователь подтверждает найденные позиции.

Видео не должно входить в MVP: оно резко увеличивает объём хранения, время обработки и количество неоднозначностей.

## 10. Поиск

Поиск стоит развивать слоями:

1. точные фильтры SQL: даты, магазин, цена, оценка, категория;
2. нормализация регистра, диакритики и единиц измерения;
3. `pg_trgm` и полнотекстовый поиск по оригинальным и нормализованным названиям;
4. алиасы товаров и продавцов;
5. только потом embeddings/`pgvector` для запросов вроде «острые азиатские снеки, которые мне понравились».

Для начала embeddings не нужны. Большинство ожидаемых вопросов лучше и точнее решаются обычным SQL.

Языки поиска нужно учесть заранее: названия в чеках могут быть на русском, польском, английском и других языках. Оригинальный текст нельзя терять после нормализации или перевода.

## 11. Локальная среда

Минимальный `docker-compose.yml`:

- `api` — ASP.NET Core, MCP + REST upload;
- `postgres` — база;
- named volume для базы;
- bind mount или named volume для media.

Позже при необходимости:

- `worker` — тот же C# image с другой entry point;
- `python-worker` — CV/OCR;
- `minio` — только для тестирования S3-совместимого storage.

В локальном профиле должна быть возможность запустить MCP как `stdio` без сетевой аутентификации. HTTP-профиль должен быть отдельным и по умолчанию слушать только localhost.

Секреты не класть в репозиторий или compose-файл. Использовать user secrets/переменные окружения и подготовить `.env.example` без значений.

## 12. Варианты развёртывания

### Этап 1: только Mac

- Docker Compose;
- локальный PostgreSQL;
- локальное media-хранилище;
- резервная копия базы и media в один архив;
- `stdio` MCP для локального клиента.

Это полностью бесплатно и проще всего для разработки.

### Этап 2: backend дома, доступ снаружи

- Mac должен быть включён;
- HTTPS-доступ через Secure MCP Tunnel либо иной проверенный tunnel/VPN;
- обязательная аутентификация;
- не публиковать PostgreSQL и storage напрямую.

### Этап 3: бесплатный/дешёвый hosted MVP

Предпочтительный вариант на сегодня:

- PostgreSQL + object storage в **Supabase Free**, если хватает лимитов;
- либо PostgreSQL в **Neon Free**, а media отдельно;
- API на любом Docker-совместимом хостинге с публичным HTTPS;
- worker можно временно запускать локально или по расписанию.

На дату этого плана Supabase Free документирует 500 MB базы и 1 GB object storage на проект; Neon Free — 0.5 GB базы на проект и поддержку расширений, включая `pgvector`. Эти лимиты и условия нужно перепроверить непосредственно перед деплоем.

Не стоит привязывать доменную модель к Supabase/Neon API. Приложение должно видеть обычный PostgreSQL и интерфейс blob storage. Тогда провайдера можно сменить.

Видео почти наверняка не поместится в устойчивый бесплатный режим. Исходники видео можно удалять после извлечения кадров по настраиваемой политике.

## 13. Этапы реализации

### Этап 0 — проверка допущений, 1–2 короткие сессии

- уточнить используемый GPT-клиент, тариф и устройства;
- поднять минимальный MCP echo/server на C#;
- проверить `stdio` на Mac;
- проверить Streamable HTTP через выбранный безопасный способ;
- выяснить реальный путь фото: attachment → tool arguments или отдельный upload;
- зафиксировать решения короткими ADR.

**Критерий готовности:** с выбранного клиента можно вызвать тестовый read-tool и тестовый write-tool; понятен путь загрузки фото.

### Этап 1 — каркас и ручной учёт

- solution и модульная структура;
- PostgreSQL, EF migrations, Docker Compose;
- сущности покупки, строки, магазин, товар, впечатление;
- MCP-инструменты создания черновика, исправления, подтверждения и поиска;
- интеграционные тесты с Testcontainers;
- backup/restore script.

**Критерий готовности:** покупку можно полностью внести и найти через разговор с клиентом без фото.

### Этап 2 — чек через client-assisted extraction

- строгая JSON-схема черновика;
- confidence и список неоднозначностей;
- проверки арифметики;
- защита от повторной записи;
- сценарий уточнения и подтверждения;
- набор обезличенных тестовых чеков и ожидаемых результатов.

**Критерий готовности:** типичный чек превращается в подтверждённую покупку, а ошибки можно исправить разговором.

### Этап 3 — собственная загрузка и backend extraction

- media storage abstraction;
- безопасная загрузка;
- таблица заданий и worker;
- интерфейс `IReceiptExtractor`;
- первый multimodal extractor;
- сохранение сырого результата, версии prompt/model и метрик;
- повторная обработка.

**Критерий готовности:** backend хранит оригинал и воспроизводимо создаёт черновик независимо от GPT-клиента.

### Этап 4 — каталог и фото товаров

- штрихкоды;
- варианты товара и упаковки;
- привязка строк чеков к товарам;
- дедупликация и merge workflow;
- оценки, заметки и дополнительные фото.

**Критерий готовности:** можно увидеть историю конкретного товара по разным покупкам и магазинам.

### Этап 5 — хороший поиск и аналитика

- полнотекстовый/нечёткий поиск;
- история цены;
- фильтры и агрегаты;
- экспорт JSON/CSV;
- embeddings только после проверки реальных запросов.

**Критерий готовности:** система отвечает на основные вопросы из раздела 1 проверяемыми данными.

### Этап 6 — удобный телефонный ingestion

- использовать MCP на mobile, если клиент к этому времени поддерживает его;
- иначе Shortcut/PWA/bot только для загрузки;
- удалённая аутентификация;
- rate limits и ограничения размера;
- политика хранения фото.

### Этап 7 — пакетная обработка и видео

- пакетные jobs;
- извлечение и ранжирование кадров;
- OCR штрихкодов/ценников;
- дедупликация кадров и товаров;
- лимиты стоимости и времени;
- review queue.

## 14. Тестовая стратегия

- unit tests для расчётов, нормализации, сопоставления и валидации;
- integration tests с реальным PostgreSQL через Testcontainers;
- contract tests MCP-схем;
- golden tests: входной сырой extraction → ожидаемый draft;
- небольшой версионируемый набор обезличенных/синтетических чеков;
- тест идемпотентности повторной отправки;
- тест backup → чистая база → restore;
- ручной end-to-end сценарий с реальным GPT-клиентом.

AI-распознавание нельзя тестировать только утверждением «похоже, работает». Нужны измеримые поля: доля верных дат, сумм, строк, количества и сопоставлений.

## 15. Риски и способы их ограничить

### Ошибки распознавания

Всегда создавать черновик, показывать сомнения и подтверждать. Сохранять оригинал и исходный текст.

### Дубли

Hash файла, idempotency key, проверка магазина + даты + суммы, отдельный merge workflow.

### Неверное объединение товаров

Не объединять автоматически при низкой уверенности. Штрихкод сильнее похожего названия, но даже он относится к варианту/упаковке, а не всегда к абстрактному продукту.

### Привязка к одной модели или провайдеру

Интерфейсы `IReceiptExtractor`, `IProductEnricher`, `IBlobStorage`; хранение версии extractor-а; единый внутренний DTO.

### Стоимость AI и хранения

Client-assisted MVP, сжатие изображений, лимиты размеров, очередь, учёт стоимости на job, запрет видео в ранних этапах.

### Потеря личных данных

Регулярные автоматизируемые backup и проверенный restore. Экспорт данных должен появиться до сложных AI-функций.

### Безопасность удалённого MCP

HTTPS, аутентификация, минимальные права, отсутствие произвольного SQL/file access, rate limiting и явное разделение read/write tools.

## 16. Что сознательно не делать в MVP

- собственный красивый UI;
- микросервисы;
- Kubernetes;
- Kafka/RabbitMQ/Redis без необходимости;
- embeddings до качественного обычного поиска;
- автоматическое окончательное сохранение без review;
- распознавание видео;
- социальные функции и многопользовательский режим;
- обучение собственной модели;
- сложную аналитику расходов до накопления данных.

3. Что важнее в первом работающем результате: внесение чека с фото или ручное внесение/поиск через разговор?

5. Допустимо ли отправлять фотографии чеков во внешний AI API, или всё должно оставаться локально?
6. Допустимы ли небольшие расходы на API после прототипа? Какой месячный предел приемлем?

### О предметной области

7. Какие покупки важнее всего: продукты, рестораны, техника, одежда, лекарства, всё сразу?
8. Нужен учёт только оплаченных покупок или также желаний, возвратов, гарантий и подписок?
9. Какие страны, языки чеков и валюты ожидаются?
10. Что означает «понравилось»: бинарный признак, 5/10 баллов, несколько критериев или свободная заметка?
11. Нужно ли хранить цены за единицу измерения, например PLN/кг или PLN/литр?
12. Нужно ли различать покупателя/члена семьи, или система строго для одного человека?
13. Нужно ли учитывать скидочные карты, купоны, налоги и возвраты?
14. Насколько важно хранить оригиналы чеков и фото бессрочно?

### О взаимодействии

15. Как должен выглядеть review: модель перечисляет только сомнительные поля или всегда весь чек?

18. Нужен ли минимальный web-экран очереди «требует проверки», если чат станет неудобен для больших чеков?

### О деплое и приватности

## 18. Предлагаемый следующий шаг

В следующей сессии:

2. выбрать первый клиент;

## 19. Зафиксированные предварительные решения

Это рекомендации, а не необратимые решения:

- язык: C#;
- архитектура: модульный монолит;
- база: PostgreSQL;
- основной интерфейс: MCP;
- дополнительный технический интерфейс: REST только для upload/health/admin needs;
- изображения локально: filesystem за `IBlobStorage`;
- hosted media: S3-compatible storage/Supabase, решение позже;
- распознавание MVP: модель клиента → структурированный MCP-вызов;
- надёжное распознавание позже: backend-owned media + `IReceiptExtractor`;
- Python: отдельный worker только при доказанной необходимости;
- видео: не раньше устойчивой обработки отдельных изображений;
- любые распознанные данные сначала являются черновиком.
