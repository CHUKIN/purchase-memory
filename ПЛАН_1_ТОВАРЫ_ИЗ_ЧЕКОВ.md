# Plan #1: every receipt line is a product, back navigation, tilted line highlight, human product names (PL + RU), «Ревью» hub

Owner asked 2026-10-16 after a real receipt (IMMOMOK, 35 lines). Status: PLAN ONLY.
Owner priority: **plan #1, goes before everything else** (before Stage 2 of
`ПЛАН_ФОТО_И_ШТРИХКОД_ТОВАРА.md`). Each stage needs the owner's explicit yes;
deploy needs a separate yes. Every stage updates help (`helpText.ts`, `topics.ts`,
`HelpLink`) and keeps button names in sync with `i18n.ts`.

## What the owner saw (facts from code, 2026-10-16)

1. **«ACTIV KEFI NAT 280» is not in Товары, but is in the receipt.**
   `ProductMatcher` (`Application/.../ProductMatcher.cs:70-148`) is rule-based:
   score ≥0.86 → link; no candidate → auto-create product; **0.62–0.86 →
   `PendingProductMatch`, line stays without a product**. NAT vs BOR scores
   ~0.75 → pending. Product search (`GET /api/products`) searches products and
   aliases only, so pending lines are invisible there. «N позиций ждут выбора
   товара» on Товары is plain text, links nowhere.
2. **Scan flow cannot create a new product.** There is no create-product API;
   a product is created only via purchase edit `Link=CreateNew`. Scan says
   «Товары пока появляются только из чеков». No merge API, no rename API
   (`Product.Rename` exists in the domain, unused).
3. **No way back from receipt to product and back.** Purchase page shows the
   product as plain text (`ProductLinkNote`, LineReview «Связано с …»), no
   link. Back infrastructure already exists (`app/backNavigation.ts`:
   `useReturnState` / `useBackTarget`), but some links do not pass it
   (`ProductMediaSection.tsx:148`, related links in `ProductCard.tsx:158`).
   Line sheet text «Строка не привязана… карандаш «Исправить» → «Товар в
   каталоге»» sends the user on a 3-step detour.
4. **Highlight is a straight rectangle.** Boxes are axis-aligned
   `{x,y,width,height}` fractions from the vision LLM; no angle anywhere.
   On a tilted photo the box cuts across two text lines.
5. **Names are raw receipt text** (`CanonicalName` = first line text). The
   only AI on products today: OpenAI categorizer (category + brand, batch,
   after each save) and Haiku tag suggestions.

## Stage 1.1 — Every line becomes a product; «нужно проверить» flag; merge; manual create

Goal: no line is ever left without a product; doubtful matches are visible and
fixable later.

- Domain:
  - `Product.NeedsReview` (bool) + `ReviewReason` (`AmbiguousMatch`,
    `CreatedByHand`, …) + optional link to the candidate list (reuse
    `PendingProductMatch` candidates, now pointing at the new product instead
    of an unlinked line).
  - `ProductOrigin`: `Receipt` / `Manual` / `Barcode` (for scan-created).
- Matcher: grey-zone outcome → **create a separate product with
  `NeedsReview=true`** and keep the candidates (OWNER DECIDED 2026-10-16:
  separate flagged product; wrong merges are harder to undo than duplicates).
  Confident and no-candidate outcomes stay.
- Resolving a flagged product:
  - «Это тот же товар, что …» → **merge** into the chosen product: move
    purchase lines, aliases (as `HumanConfirmed`), tags, later barcodes/photos;
    keep the target's confirmed name/category/brand; delete the source;
    audit entry with both ids. Undo: not in v1 (audit keeps enough to redo by
    hand) — say so in help.
  - «Это отдельный товар» → clear the flag, aliases become `HumanConfirmed`.
- Manual merge from any product card («Объединить с…»), not only flagged ones.
- `POST /api/products` (name, optional brand/category) for scan «Новый товар»
  and Open Food Facts prefill; product with 0 purchases is allowed. Scan text
  «Товары пока появляются только из чеков» goes away.
- `PUT /api/products/{id}/name` (uses `Product.Rename`, audit), needed by 1.4.
- Data migration (SQLite + Postgres): every open `PendingProductMatch` →
  create a flagged product, link the line. Prod today: ~13 such lines.
  Check on a throwaway DB copy made by the app itself, never the owner DB.
- UI:
  - Товары: badge «проверить» on flagged products, filter «Нужно проверить»;
    «N позиций ждут…» replaced by a tappable «N товаров нужно проверить».
  - «Нужно проверить» queue: kind `pendingMatch` becomes «похожие товары»:
    «Да, это он» = merge, «Это другой товар» = clear flag.
  - Line sheet (LineReview and editor): «Связано с ACTIV KEFI NAT 280 ›»
    (opens product, see 1.2) + «Изменить товар» right in the sheet (reuse
    `ProductPicker`), drop the detour text.
- Acceptance: integration tests for matcher outcomes, merge (lines, aliases,
  tags, analytics totals unchanged), migration on both DBs; review tries
  merge across households and without token; DB size/mtime check.
- Model: **Opus implementer + Opus review** (migration, data).

## Stage 1.2 — «Назад» everywhere, back to the exact place

Goal: from any screen you can go back to where you came from, at the same
scroll position and the same line.

- Rule: every link/`navigate` to a non-tab screen passes `useReturnState()`;
  every non-tab screen has a back button via `useBackTarget`. Add a small lint
  test that greps for `to="/products/` / `navigate(` without return state.
- New links: purchase line → product (summary row, LineReview «Связано с»,
  editor sheet), product card → purchases of this product → purchase (with
  return), scan result → product, flagged product → candidate product.
- Return to the exact place: return state carries `line` (line index) and
  scroll; purchase page reopens the same line sheet / scrolls to it; LineReview
  resumes on the same card; lists restore scroll (already true for
  history-index back; extend to fallback path).
- Fix the known gaps: `ProductMediaSection.tsx:148`, `ProductCard.tsx:158`.
- Tab roots keep no back button; tab bar behaviour unchanged.
- Acceptance: unit tests per path; headless walk 320 px: purchase → line →
  product → back lands on the same line; queue → product → back.
- Model: Sonnet implementer, Opus review (touches many screens).

## Stage 1.3 — Highlight follows the text line, tilted

Goal: the orange frame lies along the printed line at the photo's angle.

- No angle in the data today. Step 1 is a **free measurement** on
  `test-data/receipts/` photos (≥10 receipts, incl. tilted ones), comparing:
  - (a) angle from boxes: fit a line through the left edges / centres of
    consecutive item boxes → one skew angle per photo (no new calls, can run on
    the backend at save time);
  - (b) image deskew on the display copy (projection profile / Hough over
    the receipt area, backend, at upload);
  - (c) ask the vision model for a per-line angle or 4-point quad — this is a
    recognition change: only with `score_items.py` before/after numbers and an
    announced budget; last resort.
  Metric: does the rotated frame cover the right line without touching
  neighbours (by eye on overlays + simple overlap score). Owner sees overlays.
- Then: store `SkewDegrees` per receipt image (migration), API exposes it,
  `LinePhoto` rotates the frame around the box centre (`transform: rotate`),
  crop window (`fitWindow`) widened for the rotated corners; pinch zoom keeps
  working; `IssueReview` crop uses the same.
- Old receipts: backfill angle by method (a)/(b) without paid calls.
- Not in scope: multi-photo receipts (still shown whole), curved paper.
- Model: Sonnet implementer, Opus review; Opus if (c) is chosen.

## Stage 1.4 — Human product name by AI, Polish + Russian (text)

Goal: «ACTIV KEFI NAT 280» → PL «Kefir naturalny Activia 280 g» + RU «Кефир
натуральный Activia, 280 г». OWNER DECIDED 2026-10-16: both languages.

- Domain: `Product.NamePl`, `Product.NameRu`, each with its own source
  (`Suggested` / `Confirmed`; AI never overwrites `Confirmed`, same rule as
  category). `CanonicalName` stays the raw receipt text (plus all aliases).
- How it is shown (proposal; owner picks from a Storybook mock at stage start):
  - **Variant 1 (recommended): Polish on top, Russian below.**
    ```
    Kefir naturalny Activia 280 g          ›
    Кефир натуральный · Молочное / Кефир
    ```
    Polish matches the shelf and package (useful in the shop and with the
    scanner); Russian explains what it is. Raw receipt text only on the product
    card («В чеке: ACTIV KEFI NAT 280») and in the purchase line.
  - Variant 2: Russian on top, Polish below (reading at home comes first).
  - Variant 3: setting «Основной язык названий: польский / русский» that swaps
    the two lines everywhere.
  - Purchase lines: receipt text stays the line name (it is what the receipt
    says); the product name in the selected language goes under it as
    «→ Kefir naturalny Activia».
  - Scan result and product card header: Polish large, Russian under it.
  - Missing name (AI returned null): fall back to the receipt text, no mark.
- Search covers PL, RU and receipt text (normalised, Cyrillic as is), so «кефир»,
  «kefir» and «kefi» all find it.
- Generation: extend the existing categorizer call (same batch, after save) with
  `namePl` and `nameRu` — no new request per product. Prompt: expand receipt
  abbreviations, brand + type + variant + size; RU is a translation of the PL
  name (brand kept in Latin); return null when unsure, never invent. Backfill for
  existing products via the existing backfill endpoint.
- Product card: both names editable (`PUT …/name` with language) → `Confirmed`;
  «предложено» mark like category; «Предложить заново».
- Measure before turning on: owner checks ~40 generated pairs from real products
  (sheet: receipt / PL / RU / ok?); target ≥80% ok, 0 wrong products (better null
  than wrong). Cost: a few dozen extra output tokens per product inside an
  existing call, well under $0.10 for the backfill; budget named before the run.
- Model: Opus (AI output, prompt).

## Stage 1.5 — Better name from the product photo

Goal: after adding a product photo, offer a name read from the package.

- Product photos are on the device today (IndexedDB, before Stage 2), so the
  photo is sent once with the request `POST /api/products/{id}/name-from-photo`
  (not stored on the server; compressed ~200 KB; not logged).
  Vision model reads brand / product / variant / size → suggested PL name
  (from the package text) + RU translation.
- Rule (per language): name `Suggested` or never edited → replace automatically and show
  «Название обновлено по фото: … Вернуть?»; name `Confirmed` → show
  «Предложить название: … Заменить?».
- Also a source: Open Food Facts name when a barcode is linked (free).
- Rate limit per user (like tag suggestions); budget announced before any
  test; measure on ≥20 owner product photos (correct name rate, time, cost).
- Model: Opus.

## Stage 1.6 — «Ревью» on Главная: one place for everything to check or do

Today: Главная has a row «Нужно проверить» with a count (75 on prod now), it
opens a grouped list (`/needs-attention`, `ReviewQueuePage`): failed / unsaved
receipts, total mismatch, missing price, pending match, suggested / missing
category. Swipe line review of purchases and «оценить покупки» live elsewhere.

Goal (owner 2026-10-16): a clear **«Ревью»** button on Главная that opens
everything that needs a look or an action, quick to go through.

- Home: big «Ревью» button at the top (next to capture actions) with the count;
  hidden count / «Всё проверено» when empty. The tab badge stays.
- One hub screen «Ревью», sections with counts, most important first:
  1. Чеки: failed, unsaved, total mismatch, missing price.
  2. Покупки: lines not checked by swipe yet → opens `LineReview` on that
     purchase.
  3. Товары «проверить» (from 1.1): «Да, это он» = merge / «Это другой товар».
  4. Названия «предложено» (from 1.4): ok / edit, PL + RU side by side.
  5. Категории «предложено» / без категории.
  6. Штрихкоды «Запомнить на потом» (from the 1b scanner) → link to a product.
  7. Оценить покупки (unrated).
- Fast mode «Проверять по одной»: card by card, the same gestures as the swipe
  review (right = correct, left = edit), «Пропустить», progress «12 из 75»;
  returns to the hub section after the last card.
- Bulk where safe: «Принять все предложенные категории» in a section (with an
  undo toast), never bulk for merges.
- Every item opens its screen with return state (1.2), so «Назад» lands back on
  the same item in the hub.
- Counts come from one endpoint (extend `GET /api/review-queue` with the new
  kinds + a summary block), so the home badge, tab badge and hub agree.
- Help: new topic «Ревью» replaces «Нужно проверить» wording; button names in
  sync with `i18n.ts`.
- Acceptance: unit tests per kind; headless 320 px walk through all sections
  and the card mode; count equals the sum of sections.
- Model: Sonnet implementer, Opus review (many screens, reuses data from 1.1 / 1.4).
