# Результаты этапа: вход через Supabase Auth + ручное подтверждение (24.09.2026)

Статус: **принят независимым review (два раунда, фокус — безопасность), блокеров нет.**

## Что сделано
- **Вход:** Supabase Auth — ссылка/код из письма и Google (провайдеры из конфигурации). supabase-js 2.117.1, PKCE. Настройки Supabase приходят с сервера (`/api/auth/config`), в сборке их нет.
- **Подтверждение:** таблица `public.app_users` в Supabase (RLS, без доступа anon/authenticated), триггер создаёт `pending` при первом входе, Custom Access Token hook кладёт статус в токен (`app_access`). Владелец меняет `status` на `approved`/`blocked` в Table Editor. Нет статуса → считается pending.
- **Сервер:** JwtBearer (issuer, aud `authenticated`, только ES256/RS256 по JWKS, HS256/none отвергаются). Все `/api/*` и `/mcp` — только approved; открыты SPA, `/health` (только статус), `/api/auth/config`; `/api/me` — любой вошедший. Неизвестные `/api/*` и `/mcp/*` → 404.
- **Экраны:** вход, «Заявка отправлена, ожидайте», «Доступ заблокирован», кнопка «Выйти»; ru/en, a11y, stories.
- **Ограничение загрузок:** на пользователя, 10 подряд, затем 1 в 3 минуты; 429 с понятным сообщением.
- **Аудит:** кто загрузил чек (`UploadedByUserId/Email`), кто правил (`Actor` + `ActorEmail`). Миграция `20260924154254_AddReceiptActorIdentity`, бэкап перед ней.
- **Локально без Supabase:** `Auth__DevelopmentBypass=true` — только Development, только с этой машины (loopback + проверка прокси-заголовков; LAN-доступ через Vite закрыт).
- **Инструкция:** `docs/SUPABASE_AUTH_SETUP.md`.
- Попутно исправлено: загрузка PNG (сигнатура).

## Ограничения
- Блокировка действует до истечения токена (до часа) — как выкинуть сразу, описано в инструкции.
- Токен хранится в `localStorage`, CSP нет — в бэклог.
- Bypass небезопасен, если поставить перед API свой туннель без прокси-заголовков (ngrok и т.п.).
- Удалённым MCP-клиентам пока нечем получить токен.
- При следующем запуске — миграция реальной базы (после автобэкапа).
