## 1. Обязательные правила (нарушение = остановка работы)

1. **Процесс — строго по `AGENTS.md`:** бриф → implementation-агент → отдельный независимый review-агент, который сам запускает сборку и тесты → исправления и повторное review → обновление плана и файла результата → стоп и ожидание согласия.
2. **Проект НЕ является git-репозиторием.** Никаких git-команд. Изменения определять через `stat -f "%Sm %N"` / `find … -newer`.
3. **`data/purchases.db` — реальная база владельца.** Не открывать, не читать, не копировать, не мигрировать, не указывать на неё ни одну строку подключения, тест или прогон. Контроль до и после каждого этапа:
   ```bash
   stat -f "%Sm %z" data/purchases.db
   ```
   Эталон: `Aug 29 15:38:53 2026`, размер `118784`. Изменилось — немедленно стоп и сообщить владельцу.
4. **Папка `data/receipts/`** — реальные фото владельца, не трогать.
5. Сборка и запуск — только через `./scripts/dotnet.sh …` и `./scripts/build-apple-sidecar.sh`.
6. Временные файлы — только в scratchpad сессии; параллельные агенты — **каждый в своей подпапке**.
7. **Секреты.** Ключ читается только из переменной окружения `OLLAMA_API_KEY`. Не писать его в код, `appsettings*.json`, логи, отчёты, вывод команд, имена файлов. Не печатать заголовки запросов. Не выполнять `env`/`printenv` целиком.
8. **Прод не переключать.** `Pipeline` в `src/PurchaseMemory.Api/appsettings.json` остаётся как есть. Все изменения — в инструменте бенчмарка и в инфраструктурных классах, которые он использует.
9. Никаких удалений существующих файлов и моделей Ollama.
10. Облачные прогоны — **последовательно**, по одной модели, без параллели.

## 3. Этапы

### C1. Прямой клиент Ollama cloud в бенчмарке (без сетевых прогонов)

**Цель:** инструмент бенчмарка умеет ходить напрямую на `https://ollama.com` так, как будет ходить приложение на хостинге.

**Scope:**
- Настройка базового URL для обоих провайдеров (vision и text) уже или ещё нет — проверить; добавить необязательный API-ключ, который подставляется как `Authorization: Bearer <ключ>` только если задан. Источник ключа — переменная окружения `OLLAMA_API_KEY`, не конфиг-файл.
- В бенчмарке две новые конфигурации, модель задаётся параметром/конфигом, не хардкодом:
  - `cloud-photo` — вариант A (фото → облачная vision-модель);
  - `apple-rows-cloud` — вариант B (Apple OCR локально → строки → облачная текстовая модель).
- Бенчмарк должен уметь: прогон по списку моделей, по списку чеков, запись результата каждого чека в отдельный JSON + сводную таблицу; отдельный статус для HTTP 429 (лимит) и 401/403 (ключ), не смешивая их с ошибками модели; время каждого запроса; размер отправленного тела (байты).
- Промпт и JSON-схема для A и B — те же, что уже используются соответствующими конвейерами; не переписывать.

**Non-goals:** реальные облачные запросы; изменение прода; изменение промптов; iOS; деплой.

**Критерии приёмки:**
- сборка 0 ошибок / 0 предупреждений, все существующие тесты зелёные;
- новые тесты (с подменой `HttpMessageHandler`, без сети): заголовок `Authorization` ставится при заданном ключе и отсутствует без него; ключ не попадает в логи и тексты исключений; 429 и 401 классифицируются отдельно; без ключа режим cloud выдаёт понятную ошибку до отправки запроса;
- локальный режим (`127.0.0.1:11434`) работает как раньше;
- `data/purchases.db` не изменена.

**Результат:** `РЕЗУЛЬТАТЫ_ОБЛАКО_ЭТАП_C1_КЛИЕНТ.md`, отметка в `ПЛАН_ОБЛАКО_ФОТО_ИЛИ_ТЕКСТ.md`.

### C2. Сито на 5 трудных чеках

**Предусловие:** C1 принят review; владелец задал `OLLAMA_API_KEY`.

**Шаги:**
1. `GET https://ollama.com/api/tags` — фактический список моделей, доступных по ключу; сверить с разделом 2. Новые подходящие модели добавить в список кандидатов, отметив это.
2. Выбрать 5 трудных чеков из 20 (плотные, со скидками/OPUST, с перекосом, длинные). Выбор обосновать в отчёте, дальше не менять.
3. Вариант A: все vision-модели × 5 чеков. Вариант B: все модели × те же 5 чеков (OCR-строки снять один раз и переиспользовать, чтобы все модели получили одинаковый вход).
4. Правило остановки: модель, которая на 3 из 5 чеков дала невалидный JSON, обрыв или расхождение суммы > 1 zł, дальше не гоняется.
5. При 429 — пауза, повтор позже; если лимит исчерпан — остановиться и сообщить владельцу, сколько удалось прогнать. Не обходить лимиты.

**Выход:** таблица по каждой модели и варианту; шорт-лист до 3 моделей на вариант.

**Результат:** `РЕЗУЛЬТАТЫ_ОБЛАКО_ЭТАП_C2_СИТО.md`. Review-агент выборочно перепроверяет минимум 3 чека по сохранённым JSON против `ground_truth.json`.

### C3. Полные 20 чеков для финалистов

- Финалисты A и B × все 20 чеков.
- Эталон для сравнения: локальная `qwen3.5:35b` в конвейере `apple-ollama` на тех же 20 чеках (локальный демон).
- Метрики через `score.py` плюс: сходится ли сумма в копейку; верные итог, магазин, дата; точность позиций; обрывы; время на чек; байты на чек.
- Оценка расхода лимита: сколько чеков на модель в сутки/неделю выдерживает бесплатный тариф (по фактическому поведению и странице использования, которую владелец может показать скриншотом).

**Результат:** `РЕЗУЛЬТАТЫ_ОБЛАКО_ЭТАП_C3_ПОЛНЫЙ_ПРОГОН.md`.

## 4. Что review-агент проверяет обязательно

- сам запускает сборку и тесты, приводит числа;
- ищет ключ в коде, конфигах, логах, отчётах и scratchpad: `grep -r "OLLAMA_API_KEY"` должен находить только чтение переменной окружения, а значение ключа — нигде;
- что прод-конфигурация не изменилась;
- что лимиты инструмента (таймаут `HttpClient`, `num_predict`, `num_ctx`) не ниже рабочих настроек конвейеров — иначе ограничение инструмента будет выглядеть как слабость модели;
- что все модели в одном варианте получили одинаковый вход;
- дату/размер `data/purchases.db`.
