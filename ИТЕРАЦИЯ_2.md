# Итерация 2 — локальное PWA и Ollama

## Цель

Проверить жизнеспособность самостоятельного продукта без обязательного AI-чата: пользователь фотографирует чек в PWA, backend локально извлекает структуру, пользователь исправляет результат и сохраняет покупку.

## Реализованный срез

1. PWA принимает JPEG, PNG и WebP до 15 МБ с камеры или из файла.
2. Backend проверяет magic bytes, считает SHA-256 и атомарно сохраняет оригинал вне web-root.
3. SQLite хранит долговечное состояние `Uploaded/Queued/Processing/ReadyForReview/Failed/Saved`.
4. Background worker вызывает Ollama и сохраняет безопасную ошибку, допускающую retry.
5. PWA опрашивает статус, показывает исходник и редактируемые реквизиты/товарные строки.
6. Повторный `save` идемпотентен благодаря `SourceReceiptId`.
7. История ищется по магазину и названиям товаров.
8. Старые MCP tools остаются доступными параллельно REST API.

## Выбор распознавания

OCR не обязан быть LLM. Для чеков полезно разделять задачи:

```text
изображение → OCR/vision → сырой текст → структурирование → ручная проверка → база
```

В default-конфигурации первый этап выполняет специализированный `glm-ocr`, второй — небольшой `qwen3.5:4b`. Также benchmark сравнивает прямое vision-распознавание через `qwen3.5:4b`, `qwen3.5:9b`, `gemma4:12b-mlx` и `minicpm-v4.6`.

Почему не Tesseract как единственный путь: он бесплатный и быстрый, но сам не связывает переносы строк, скидки, весовые позиции и итог. Его имеет смысл добавить позже как дешёвый baseline/первичный OCR, а не как единственный parser.

## Критерии готовности

- solution и frontend собираются без предупреждений;
- проходят автоматические backend/frontend тесты;
- Docker image собирается и видит нативный Ollama;
- минимум один реальный чек проходит полный сценарий до сохранения;
- результаты нескольких моделей сохранены воспроизводимым JSON/Markdown отчётом;
- пользователь всегда может исправить результат до записи в историю.

## Что измеряет benchmark

Для каждого изображения вручную зафиксированы магазин, календарная дата, итог, число товарных строк, контрольные фрагменты названий и ожидаемая сумма строк. Баллы: магазин 20, дата 15, итог 20, количество строк 15, арифметика строк 15 и названия 15. Это проверка жизнеспособности, а не статистически достоверная оценка OCR.

Публичный интернет почти не даёт современных чеков с открытой лицензией. В репозитории сохранены только допустимые для локального QA примеры Biedronka/Lidl; для Żabka, Auchan, Carrefour и E.Leclerc сохранены ссылки и причины, почему чужие изображения автоматически не копировались. Следующий честный benchmark должен состоять из собственных или явно разрешённых чеков.

## Следующая итерация

1. Собрать 30–50 собственных чеков из целевых сетей и вручную разметить JSON.
2. Добавить нормализацию поворота, перспективы, контраста и разбиение длинного чека на области.
3. Сравнить Apple Vision OCR/Tesseract/PaddleOCR как первый этап с текущим GLM-OCR.
4. Выбирать pipeline по качеству снимка и confidence, а не одной моделью для всех чеков.
5. Добавить каталог нормализованных товаров, aliases и полнотекстовый поиск SQLite FTS5.
6. После подтверждения личной ценности — пользователи, passkeys/OIDC, PostgreSQL и синхронизация.
7. Только затем решать, нужен ли ChatGPT/Claude connector как дополнительный UI и какие платные API оправданы.
