# Large-image protection (Normal level, 2026-11-08)

Finding: a 143 KB 7000x7000 PNG passed the 50 MP cap and decoded at full size
(~+275 MB per request, 6 parallel ~1.57 GB) on a 512 MB host.

## What was done
- Only decoder in the repo is SkiaSharp, and every decode goes through
  `ReceiptImageCompressor` (receipts display copy, product photo + thumb, impression
  photo, haul photo source + model copy). `SKCodec.Create` reads the header only;
  find-by-photo and name-from-photo send bytes to the model and never decode.
  The haul cropper decodes the already-stored <= 2048 px copy (~16 MB), left ungated.
- Charge formula (4-byte pixel units), computed from the header before any allocation:
  `footprint = decodedW*decodedH + (resize needed ? resizedW*resizedH : 0) + outputW*outputH
  + (JPEG not provably baseline ? 2 * sourceW*sourceH : 0)`.
  The decoded size is what the codec really decodes to (native 1/8..7/8 down-scaling chosen
  first; PNG cannot down-scale). Progressive JPEG makes libjpeg allocate full-size coefficient buffers (~2 bytes x up to
  4 components per source pixel) whatever the output size, hence the 2 term. Fail closed:
  `IsBaselineJpeg` must strictly reach SOF0/SOF1 and a first scan carrying all frame components (Ns == Nf, the libjpeg condition for no buffering); stray bytes (which
  libjpeg skips), other frame types or truncation count as progressive (post-commit security
  review finding).
  `source`/`output` bitmaps are `SetImmutable()` so `SKImage.FromBitmap` wraps instead of copies.
- `MaximumDecodePixels` = 40 MP (160 MB, = gate budget): a call above it is refused (`tooLarge`). `MaximumSourcePixels`
  (50 MP, header size) stays as the outer cap. Effects: crafted PNG 7000/20000 refused; 16 MP PNG
  receipt (~25 MP footprint) passes; 48 MP baseline JPEG decodes at 1/2 size and passes; a
  progressive JPEG passes up to ~12 MP of source (12 MP receipt ~37 MP footprint); progressive 7000x7000
  and 8000x6000 are refused.
- `ImageDecodeGate`: process-wide budget `MaximumConcurrentDecodePixels` = 40 MP (160 MB), one
  shared instance per budget value, every call charges its footprint. Waiters block up to
  `DecodeWaitSeconds` = 30, then the compressor returns null.
- Errors: `TryCreate(bytes, out tooLarge)`. Product photo and haul photo -> 413 `photoTooLarge`;
  impression photo -> 400 "Invalid image"; receipts keep the old behaviour (no display copy,
  original kept and served). No new user-visible message: no i18n/help change.
- Web app already downscales product (1280), naming (1024) and haul (2000) photos before upload.
- No allocator limit: SkiaSharp has none.

## Checks
- Area tests (ImageDecodeGuard, ReceiptImageCompressor, HaulPhoto, ProductMediaApi, ImpressionApi,
  ReceiptImageStore, ProductPhoto*): 114 passed, 6 skipped (S3 backend), 0 failed.
- `ImageDecodeGuardTests`: crafted PNG 7000/20000 and JPEG 20000 refused; crafted progressive
  JPEG (real SOF2 file, 532 bytes) declaring 7000x7000 and 8000x6000 refused; a real 1600x1200
  progressive JPEG accepted; 12 MP baseline JPEG and 6 MP PNG accepted; tight-budget PNG refused
  while same-size JPEG down-samples; gate unit tests; 12 parallel compressions release the gate;
  product upload bomb -> 413; haul propose bomb -> 413 with no model call.

## Limits
- Footprint is an estimate from measured behaviour (progressive 48 MP: +303 MB ~ 6.3 bytes/pixel),
  not a hard allocator limit. Peak memory not re-measured on Render.
- A baseline JPEG declaring 7000x7000 is not refused: it decodes at a reduced size (~3-7 MP).
  This does NOT hold for progressive JPEGs, which are charged as above.
- Stray-byte progressive bomb test added (refused). No 12 MP progressive acceptance test with a real file (fixture would be ~70 KB); covered by arithmetic.
- Backlog (in `ЧТО_ДАЛЬШЕ.md` §6): gate blocks a thread-pool thread (async gate later); on gate
  timeout product/haul answer 415 `photoNotAnImage` and a receipt silently gets no display copy;
  haul cropper ungated; no impression endpoint bomb test.

## Pre-deploy (2026-11-08)
- Pre-deploy agent was stopped by a classifier before real attempts; it flagged interlaced PNG and lossless WebP from reading. Root measured with the real compressor code (standalone probe, peak RSS):
  interlaced 4000x4000 16-bit PNG was +186 MB while charged ~27 MP -> fixed: PNG not provably non-interlaced (`IsNonInterlacedPng`, IHDR byte) is charged +2x source pixels.
- After the fix (peak RSS, single / 8 parallel): interlaced PNG 3500/4000 8- and 16-bit, progressive JPEG bombs -> all refused, ~49 MB / ~54 MB;
  plain 16 MP PNG 172 / 174 MB; 48 MP baseline JPEG 121 / 194 MB; lossless and lossy WebP 7000x7000 138 / 229 MB.
- No API/auth/access change in the batch, so smoke after deploy covers 401s. Backend 913 passed / 12 skipped.
