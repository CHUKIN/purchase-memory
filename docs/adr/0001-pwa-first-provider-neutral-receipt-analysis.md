# ADR 0001: PWA-first и provider-neutral анализ чеков

- Статус: принят
- Дата: 31 июля 2026
- Область: первая версия AI-сценария Purchase Memory

## Контекст

Purchase Memory уже имеет PWA, ASP.NET Core backend, фоновую обработку чека и
отдельный шаг сохранения покупки. Распознавание сейчас реализовано как два полных
pipeline: основной Apple и fallback Ollama. При прямом добавлении OpenAI в том же
виде prompt, схема ответа, разбор и правила валидации начнут расходиться между
провайдерами.

Нужно получить один пользовательский сценарий, который одинаково работает:

- локально через Ollama;
- в размещённом приложении через OpenAI;
- в существующем приложении во время миграции.

## Решение

### PWA — основной клиент

PWA загружает изображение и необязательную пользовательскую инструкцию только в
Purchase Memory API. Она не вызывает OpenAI или Ollama напрямую, не получает их
секреты и не выбирает доверенным параметром фактический provider или model.

Backend отвечает за хранение изображения и инструкции, очередь, выбор provider,
общий workflow, валидацию, состояние задания и сохранение результата.

### Один intent первой версии

Первая версия поддерживает только стабильный intent `receipt.extract`.
Неизвестный intent отклоняется до обращения к модели. Новые intent добавляются
отдельным решением и не расширяют семантику `receipt.extract`.

### Workflow отделён от транспорта провайдера

Единый receipt workflow владеет:

- версионируемым prompt;
- строгой JSON Schema;
- включением пользовательской инструкции как недоверенных данных;
- десериализацией, нормализацией и C#-валидацией;
- ограниченной исправляющей попыткой;
- преобразованием результата в черновик существующего приложения.

Provider adapter владеет только преобразованием общего запроса в API провайдера,
отменой и timeout, классификацией транспортных ошибок и возвратом общего ответа
с техническими метаданными. Адаптер не обращается к базе и не имеет собственной
версии receipt prompt или схемы.

Нормативные контракты описаны в
[`receipt-extract-v1.md`](../contracts/receipt-extract-v1.md), а машинная схема —
в [`receipt-extract-result-v1.schema.json`](../contracts/receipt-extract-result-v1.schema.json).

### Provider выбирает backend

Provider и model задаются конфигурацией backend. Автоматический fallback между
провайдерами выключен по умолчанию и может быть включён только явно. Смена
provider не меняет request/response PWA и receipt workflow.

Ollama является локальным dev/test provider. OpenAI является кандидатом для
размещённой версии. Текущий Apple pipeline сохраняется без изменений как
`legacy/experimental` до сравнительного тестирования новой архитектуры; он не
определяет новый общий контракт.

### Модель создаёт только черновик

Успешное распознавание переводит чек только в состояние проверки. Ни model,
provider adapter, workflow, retry, fallback, очередь, ни пользовательская
инструкция не могут сохранить покупку.

Сохранение происходит только отдельным действием после того, как человек увидел
редактируемый черновик и явно подтвердил его. Этот инвариант действует и для
будущих tools или агентных сценариев.

## Privacy и безопасность

- Секреты провайдеров существуют только на backend и не сохраняются в
  репозитории, PWA bundle, ответах API или логах.
- Изображение и пользовательская инструкция считаются персональными и
  недоверенными данными.
- При выборе облачного provider пользовательское изображение и инструкция
  передаются этому provider; интерфейс должен сообщать об этом до production
  deploy.
- Полные изображения, base64, prompt, model output и пользовательская
  инструкция по умолчанию не логируются.
- Логи могут содержать receipt/correlation id, provider, model, версии prompt и
  schema, длительность, usage и безопасный код ошибки.
- Инструкция ограничена 1 000 Unicode-символами, хранится вместе с receipt job и
  удаляется по той же retention-политике.
- Текст инструкции и текст на изображении не могут отменить JSON Schema,
  C#-валидацию, лимиты, выбор provider или обязательное ручное сохранение.

## Timeout, retry и ошибки

- Каждый provider request имеет настраиваемый timeout; рекомендуемые начальные
  значения: 90 секунд для OpenAI и 120 секунд для локального Ollama.
- Отмена HTTP-запроса пользователя распространяется до provider, если обработка
  ещё привязана к этому запросу; фоновая задача использует собственный
  ограниченный deadline.
- Transport retry разрешён только для явно временных ошибок и только в
  ограниченном количестве. Начальная политика: не более двух повторов с
  backoff; ошибки авторизации, неверная конфигурация, неподдерживаемая модель и
  невалидный request не повторяются.
- Workflow может выполнить не более одной model-repair попытки при JSON/schema
  или доменной ошибке. Repair использует ту же schema и не ослабляет правила.
- Автоматический переход к другому provider не происходит по умолчанию.
- При окончательной ошибке receipt становится `failed`, изображение и
  инструкция остаются доступны для явного пользовательского retry, а покупка не
  создаётся.
- Частичный или невалидный model output не публикуется как готовый черновик.
- Пользователь получает безопасное сообщение и возможность повторить обработку;
  внутренний stack trace, provider body и секреты не возвращаются.

## Версионирование

Prompt и JSON Schema имеют независимые стабильные версии:

- `receipt.extract.prompt.v1`;
- `receipt.extract.schema.v1`.

Обе версии фиксируются в каждом запуске анализа и в benchmark-результате.
Изменение только текста prompt не требует изменения schema version. Любое
изменение имён, типов, обязательности или семантики полей результата требует
новой schema version. Старые сохранённые запуски не переинтерпретируются новой
версией.

Provider и model являются метаданными запуска, а не частью версии контракта.

## Последствия

Положительные:

- OpenAI и Ollama сравниваются на одинаковом задании;
- prompt, схема и бизнес-валидация имеют один источник истины;
- PWA и доменная модель не зависят от SDK провайдера;
- секреты и автоматическое сохранение остаются за доверенной границей backend.

Компромиссы:

- возможности конкретной модели нельзя использовать в обход общего контракта;
- понадобится совместимый фасад для существующего `IReceiptExtractor`;
- пользовательская инструкция не является произвольной агентной командой;
- Apple временно существует рядом с новой архитектурой как legacy pipeline.

## Не входит в решение

- изменение текущего UI или endpoint-ов;
- реализация новых интерфейсов в коде;
- выбор модели по умолчанию без benchmark;
- произвольный tool loop;
- автоматическое сохранение;
- удаление Apple pipeline.
