# Результаты этапа «Редактирование сохранённой покупки»

Дата: 26.09.2026.

## Что сделано

Сохранённую покупку теперь можно исправить прямо в приложении, а не только
через MCP. У каждой покупки появилась своя страница `/purchases/{id}`:
просмотр (магазин, дата, итог, строки, связь строки с товаром, что стоит
проверить) и режим «Исправить».

В режиме исправления можно:

- поменять магазин, дату, валюту и итог чека;
- поменять у строки название, количество, цену за единицу и сумму;
- добавить или удалить строку, добавить или поправить скидку (скидка
  показывается тем же блоком, что и при проверке нового чека);
- выбрать товар для строки: из похожих товаров, которые предложил
  сопоставитель, через поиск по каталогу, «создать новый товар» или
  «подобрать автоматически».

Пока вы правите, сверху видна живая сверка: сколько дают строки, какой итог
чека и какая разница (с тем же допуском 0,01, что и на сервере). Строки без
цены подсвечены. Рядом показывается фото чека, если оно есть.

После сохранения очередь «Нужно проверить», значок в меню, лента покупок и
каталог обновляются. Если покупку за это время успели изменить в другом окне,
сохранение не перезаписывает чужую правку, а просит загрузить свежую версию.

Из очереди «Нужно проверить»:

| Пункт | Кнопка | Куда ведёт |
|---|---|---|
| Сумма не сходится | «Исправить» | редактор, курсор в поле «Итог чека» |
| Нет цены | «Исправить» | редактор, курсор в цене первой строки без цены |
| Товар не сопоставлен | «Выбрать товар» | редактор, открыт выбор товара для этой строки |

Покупка без чека (создана через MCP) теперь ведёт на свою страницу, а не на
общий список. В ленте покупок название магазина стало ссылкой на покупку; на
странице сохранённого чека есть ссылка «Открыть и исправить покупку».

Мелочь из прошлой проверки: в карточке очереди нестандартный код валюты больше
не роняет страницу — выводится «15,00 zł» вместо ошибки.

## Для разработчика

- `GET /api/purchases/{id}` — покупка со строками, связями с товарами
  (`productId`, `productName`), признаком `pendingMatch` и кандидатами,
  областями на фото и проблемами.
- `PUT /api/purchases/{id}` — полный исправленный снимок (строки, которых нет в
  запросе, удаляются). Обязательно `expectedUpdatedAt` = `updatedAt` из GET;
  другое значение → 409. У строки `productLink`: `auto` | `existing` (+
  `productId`) | `new`. Ошибки проверки → 400 с понятным текстом («Line 2: …»).
  Доступ — только одобренный пользователь (общая fallback-политика).
- Код: `src/PurchaseMemory.Application/Purchases/PurchaseEditing.cs`
  (`PurchaseEditService`), эндпоинты и DTO в
  `src/PurchaseMemory.Api/Endpoints/PurchaseEndpoints.cs`, страница
  `src/PurchaseMemory.Web/src/features/purchases/PurchaseDetailPage.tsx`,
  общий формат денег `features/purchases/money.ts`.
- Используются те же фабрика строк, проверки домена, привязка скидок,
  `PurchaseDraftIssueDetector` и `ProductMatcher`, что при обычном сохранении.
  Строки без решения человека проходят через сопоставитель как при первом
  сохранении.
- Сохранённая связь узнаётся по товару, а не по номеру строки: удаление или
  вставка строки не превращает старые связи в «решение человека» и не пишет
  лишних записей в историю. Категоризация ставится в очередь только для новых
  или сменённых товаров.
- Некорректный JSON или неверный тип значения в теле запроса → 400
  ProblemDetails (раньше в Development — 500).
- Выбор товара человеком записывается как псевдоним магазина с источником
  `HumanConfirmed` (существующий псевдоним перенаправляется), поэтому
  следующий чек из этого магазина с той же строкой свяжется сам. Сохранение
  прежней связи псевдоним не трогает.
- Если у покупки есть чек, его снимок обновляется вместе с покупкой, а правки
  попадают в существующую историю правок чека (`/api/receipts/{id}/audit`) с
  автором; смена товара пишется как `Item:N.Product`.
- В пунктах очереди появилось поле `itemPosition` (строка для фокуса).
- Миграций нет. Новые методы репозитория каталога и
  `ReceiptCapture.ApplyCorrectionAfterSave`, `ProductAlias.ConfirmFor`.

## Ограничения

- История правок ведётся только для покупок с чеком (она живёт у чека).
  Покупки, созданные через MCP, исправляются без истории.
- Защита от одновременной правки — сверка `updatedAt` в приложении с
  точностью до миллисекунды. Токена конкурентности в базе (rowversion/xmin)
  нет: два сохранения, пришедшие почти одновременно, теоретически могут
  пройти оба, и последнее победит.
- Сопоставитель товаров запускается после первого `SaveChanges` отдельным
  сохранением (как и при обычном сохранении покупки). Если он упадёт, правка
  покупки уже сохранена, а строки «на автомате» останутся без товара до
  следующей правки или повторного сопоставления.
- Поля строки «единица» в редакторе нет (сохраняется как было).
- История правок сравнивает строки по позиции: удаление строки в середине
  выглядит как изменение следующих строк и удаление последней — так же, как
  при проверке нового чека.
- MCP-инструмент `update_purchase_draft` не менялся: он не обновляет снимок
  чека и не пишет историю.
- Визуальная проверка в браузере в этом этапе не проводилась — только
  компонентные тесты.

## Следующий кандидатный шаг

«Скрыть пункт» в очереди и отдельный экран разбора всех несопоставленных
строк подряд; при желании — история правок и для покупок без чека.

## Для подсказок

- У каждой покупки есть своя страница: откройте её из ленты (нажмите на
  название магазина), со страницы чека или из «Нужно проверить».
- Кнопка «Исправить» открывает правку: можно поменять магазин, дату, итог,
  строки, цены и скидки, добавить или удалить строку.
- Сверху во время правки видно, сходятся ли строки с итогом чека и какая
  разница. Строки без цены подсвечены.
- У каждой строки можно выбрать товар: из похожих, через поиск, создать новый
  или оставить автоматический подбор. Выбор запоминается для этого магазина —
  в следующий раз строка свяжется сама.
- «Сумма не сходится», «Нет цены» и «Товар не сопоставлен» в «Нужно
  проверить» сразу открывают правку на нужном месте. После сохранения пункт
  пропадает из очереди.
- Если покупку уже поменяли в другом окне, приложение не затрёт правку и
  предложит загрузить свежую версию.

## Независимая проверка (26.09.2026)

Первая проверка нашла ошибку: после удаления или вставки строки автоматические
связи «магазин → товар» ошибочно становились подтверждёнными, и в историю
попадали ложные записи. Ещё битый JSON давал ошибку 500. Обе ошибки исправлены.

Повторная проверка — готово. Проверяющий сам прогнал: .NET SQLite 479 / 0 упало,
Postgres 481 / 0, vitest 157/157, `tsc -b` и сборка — успешно. Повтор сценария с
Lidl подтвердил, что связи не меняются. Битое тело запроса возвращает 400,
слишком большое — 413. Запросы без входа получают 401. Экран редактирования
пройден в браузере со скриншотами. Реальная база не изменилась.

Мелочи на потом: неверный Content-Type даёт 404 вместо 415; `?limit=abc` в
списке покупок молча игнорируется.
