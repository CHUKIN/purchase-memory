## Что сделано

1. **Выбор базы в настройках.** По умолчанию, как и раньше, SQLite
   (`data/purchases.db`, те же миграции, тот же бэкап перед миграцией).
   `Database__Provider=Postgres` + `ConnectionStrings__Postgres` переключают на
   Postgres (Supabase). Для Postgres — свой набор миграций в отдельном проекте
   `src/PurchaseMemory.Infrastructure.Postgres` (одна миграция
   `InitialPostgresSchema`), миграции применяются при старте сами. Бэкап файла
   для Postgres не делается: в лог пишется предупреждение со списком миграций.
2. **Таблицы в отдельной схеме `purchase_memory`.** Supabase открывает схему
   `public` через Data API всем, у кого есть публичный ключ (а он публичный).
   Поэтому таблицы приложения — в своей схеме, до которой роли `anon` и
   `authenticated` не дотягиваются (проверено тестом).
3. **Фото в S3-совместимом хранилище** (Supabase Storage). `Storage__Provider=S3`
   + адрес, регион, бакет и ключи. Бакет закрытый, публичных и подписанных
   ссылок нет; фото отдаёт только API одобренным пользователям. По умолчанию —
   локальная папка, как раньше. Хранилище спрятано за контрактом: общий
   `ReceiptImageStore` (проверка формата, лимит, хэш, копии) поверх простого
   `IReceiptBlobStorage` с двумя реализациями — папка и S3.
4. **Сжатая копия фото.** При загрузке оригинал сохраняется байт в байт, рядом —
   копия `part-000.display.jpg`: длинная сторона ≤ 2400 px (маленькие не
   увеличиваются), поворот по EXIF применён, JPEG качество 82, EXIF/GPS/модель
   камеры удалены, прозрачность PNG — на белом фоне. Большие JPEG декодируются
   сразу в уменьшенном масштабе (ближайшая доля 1/8…7/8, не меньше цели), чтобы
   не держать в памяти полный кадр; защита от огромных картинок — 50 МП.
   - **Приложение показывает сжатую копию** (`/api/receipts/{id}/image` и
     `/images/{n}`); оригинал — по `?original=true`. Старые чеки без копии
     показывают оригинал, как раньше. Frontend менять не пришлось.
   - **Распознавание получает оригинал** (как было). Причина: точность
     распознавания мерилась на оригиналах, а по правилам проекта входные данные
     распознавания меняются только после замера на размеченных чеках. Для
     перехода есть переключатель `ReceiptImages__AnalysisSource=Viewing`
     (проверен: модель получила копию 54 766 байт вместо 99 791). Ожидаю, что
     точность не пострадает (OpenAI при `detail=high` сам уменьшает фото до
     2048 px), и при этом GPS перестанет уходить внешнему провайдеру — но
     решать по замеру (платный прогон с бюджетом — отдельно).
   - Если файл с верной «сигнатурой» не декодируется, копия не создаётся, в лог
     пишется предупреждение, отдаётся оригинал (поведение как до этапа).
   - HEIC приложение не принимало и не принимает (только JPEG/PNG/WebP).
5. **Документы для владельца:** `docs/ПЕРЕМЕННЫЕ_И_СЕКРЕТЫ.md` (все переменные:
   что это, где взять, секрет или нет, куда вписать), шаблон только с именами
   `docs/secrets.template.env` (копировать вне проекта),
   `docs/SUPABASE_БАЗА_И_ФОТО.md` (строка подключения Session pooler, бакет,
   S3-ключи, переменные), ссылка из `docs/SUPABASE_AUTH_SETUP.md`.
   В `.gitignore` — `*.env`, кроме шаблона.
6. **Локальные Postgres и S3 для разработки:** `deploy/local/docker-compose.yml`
   (+ `s3-dev-identities.json`), порты только на `127.0.0.1`, пароли одноразовые
   и помечены как dev-only.

Docker-образы. Postgres — `postgres:17.11-alpine`.

## Особенности Postgres, которые проверены

- **Деньги:** `numeric(18,2)`, количества `numeric(18,3)` — точный возврат
  (тест: 12 345 678,99; 0,482 кг). Чтобы обе базы хранили одно и то же,
  приложение само округляет при записи до объявленного масштаба колонки
  (деньги — 2 знака, количества — 3, половина — от нуля): 1,995 → 2,00;
  0,4825 → 0,483. Тест `DecimalRoundingTests` проходит на SQLite и на Postgres;
  миграции SQLite не менялись.
- **Время:** `DateTimeOffset` по-прежнему хранится числом миллисекунд UTC
  (`bigint`), как в SQLite, а не `timestamptz`. Смысл одинаковый у обеих баз,
  переносу данных (пункт 6) это упрощает жизнь; минус — в панели Supabase даты
  видны числами. Тест: момент с офсетом +01:00 и миллисекундами возвращается
  точно.
- **Поиск и сопоставление товаров:** поиск покупок фильтруется в памяти
  (регистр польских/русских букв не зависит от базы), поиск по каталогу —
  по нормализованному имени (нижний регистр, без диакритики), поэтому
  регистрозависимость Postgres не влияет. Сырой SQL и SQLite-функций в запросах
  нет; старый SQLite-бутстрап (`sqlite_master`) для Postgres не запускается.
- **Сортировка по имени** в каталоге в Postgres идёт по правилам языка
  (`en_US.utf8`), в SQLite — побайтово; тесты на обе проходят.
- Уникальные ключи (дубль загрузки, гонка загрузок) дают тот же
  `DbUpdateException` — тесты на дубли проходят на Postgres.
- Обе модели проверены на `HasPendingModelChanges() == false`: миграции каждого
  провайдера точно соответствуют коду.

  смоук ещё не делался (проекта пока нет).
