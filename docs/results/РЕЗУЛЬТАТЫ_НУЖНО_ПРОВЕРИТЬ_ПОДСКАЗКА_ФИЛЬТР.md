# Needs attention: inline product suggestions, return after save, category filter (8 Oct 2026)

Follow-up to `РЕЗУЛЬТАТЫ_НУЖНО_ПРОВЕРИТЬ.md` and `РЕЗУЛЬТАТЫ_НУЖНО_ПРОВЕРИТЬ_ТЕГИ.md`.
No migrations. Queue rules unchanged.

## Done

### 1. «Товар не сопоставлен» — suggested products inline

- `GET /api/review-queue` items now carry `candidates` (pending match only, empty
  otherwise): up to 3 products the matcher weighed, best score first, each
  `{ productId, name, brand, categoryId }`. Products that no longer exist are
  skipped (same as the purchase editor). Product has no size/unit field, so
  brand + category are shown instead.
- Loaded with two flat queries (candidates by match id, then products by id)
  instead of a nested projection, so SQL is the same on SQLite and Postgres.
- Card: «Похоже на» list — name (links to the product), «brand · category path»,
  a «Да, это он» button per candidate (first one primary), «Создать новый
  товар», and «Другой товар» → the purchase editor focused on the line's
  picker (existing deep link). Without candidates the card is as before
  («Выбрать товар» + «Открыть похожий товар»).
- One tap reuses the editor's API: `GET /api/purchases/{id}` then
  `PUT /api/purchases/{id}` with the full stored snapshot and only that line
  changed (`existing` + productId, or `new`); other linked lines are sent as
  `existing`, unlinked ones as `auto`, discounts as `auto` — exactly what the
  editor sends (`relinkLineRequest` in `features/review-queue/resolvePendingMatch.ts`).
  So the alias is confirmed and the store remembers the choice, as in the picker.
- If the line is no longer pending (decided elsewhere) nothing is saved, the
  queue refreshes and the card says «Эту строку уже разобрали — очередь
  обновлена.». Other failures: «Не удалось связать строку с товаром…», card stays.
- On success the queue, badge (same query prefix), feed/purchase, products and
  the receipt caches are invalidated; the item leaves the queue.

### 2. Return to the queue after saving a receipt

- Receipt links in the queue pass router state `{ returnTo: "/needs-attention?<current filters>" }`.
- `ReceiptDetailPage` (`CapturePage.tsx`) navigates to that address after a
  successful save (only `/needs-attention` or `/needs-attention?…` is
  accepted, anything else → `/purchases`, the default). It also invalidates the
  review-queue queries on save so the list and badge are fresh.
- State lives in history (survives reload), the receipt URL stays clean.

### 3. Category filter

- `GET /api/review-queue?categoryId=…` or `?uncategorized=true` (combinable
  with `tagId`). Same validation/semantics as feed and catalog via
  `ProductClassificationFilter`: a group includes its subcategories, an
  AI-suggested category counts, unknown category → 400, non-GUID → 400,
  `categoryId` + `uncategorized=true` → 400. `/count` ignores it (badge stays global).
- Matching is the tag rule generalised: category items through their product,
  total/price items through any linked line, failed/unsaved receipts and
  pending lines never (even if a candidate is in the category).
- Service: new `ReviewQueueFilter(CategoryId, Uncategorized, TagIds)` overload;
  the old tag overload delegates to it (MCP unchanged).
- UI: «Категория» select (extracted `CategoryFilterField` from
  `ClassificationFilterFields`, reused by feed/catalog) next to «Тег»; URL
  `?category=…` (`none` for «Без категории»); a deleted category from a link is
  dropped before any request; if the tree fails to load the whole queue is shown.
  Summary/empty texts now describe any filter («из категории «…»», «без
  категории», «с тегом «…»»); «Сбросить фильтр» clears both.

## Known limitations

- Stories were type-checked but not opened in a browser in this stage.
- One-tap is two requests (read + PUT); a save between them gives the editor's
  usual 409 → generic error, retry works.
- Candidate line is found by position; the check is «still pending and unlinked».
- MCP `list_review_queue` returns `candidates` automatically but has no
  category parameter yet.
- Only receipt links return to the queue; the purchase editor still stays on
  the purchase after saving.
- As before, the scan is bounded to the last 5000 purchases.
