# Photo/barcode stage 6 «Сфотографировать покупки» — result

Level: Full (recognition + new paid call). No migration. No paid calls: every
test uses a fake matcher or a fake transport; the benchmark was only run to
check that it refuses (no budget, unknown price, no key).
The feature is **off by default** (`HaulPhoto:Enabled=false`).

## Done
- **API** (approved-user policy like every purchase endpoint; purchases are
  the household's shared data, an unknown purchase is 404; line and product
  ids always come from the stored purchase, never from the app):
  - `GET /api/purchases/haul-photo/status` → `{enabled}` (free).
  - `POST /api/purchases/{id}/haul-photo` (multipart `photo`, JPEG/PNG/WebP
    ≤ 1.5 MB, same checks as stage 5) → `{items:[{index, box{x,y,width,height}
    0..1, lineId|null, confidence}], lineCount}`. Nothing is stored.
  - `POST /api/purchases/{id}/haul-photo/save` (multipart `photo` = the same
    bytes again + `pairs` JSON `[{lineId,x,y,width,height}]`, 1–40) →
    `{results:[{lineId, status, productId, photoId, isMain}]}`; status is
    `saved | alreadySaved | noProduct | lineNotFound | invalidBox | photoLimit |
    productGone | failed`.
- **Switch** `HaulPhoto__Enabled` (default false in code and appsettings). Off →
  both POSTs 503 `haulPhotoDisabled` before the upload is read; on without key
  or provider failure → 503 `haulPhotoUnavailable` (no details).
- **Rate limits**: propose has its own bucket `RateLimiting:HaulPhoto` (10
  burst, +1 / 360 s per user, 429 «Too many haul photos»); save uses the
  product-photos bucket (storage, no model).
- **Storage decision: re-upload on save, no server state.** The app keeps the
  shrunk photo (≤ 2000 px, ≤ 1.2 MB) and sends it again with the confirmed
  pairs. Why: no temp files or expiry job, survives Render sleep/restart, no
  cross-user session ids to guard; a different photo on save can only put the
  user's own picture on a product, which the photo upload already allows. Cost:
  one extra ~0.5–1 MB upload. Saving is idempotent: the client id of each crop
  is a hash of photo + line + box, so a repeated save returns `alreadySaved`.
- **Orientation**: the server prepares both copies from one EXIF-rotated
  decode (`HaulPhotoImageProcessor`, reusing `ReceiptImageCompressor`): source
  ≤ 2048 px for crops, model copy ≤ 1.15 MP and ≤ 1568 px (what Claude sees
  without its own downscale, so pixel boxes are exact). Boxes are fractions of
  the upright picture, so model, crop and the phone (which also draws upright)
  agree. Tested with EXIF orientation 6 and 8. No EXIF survives re-encoding.
- **Matcher** `AnthropicHaulPhotoMatcher` behind `IHaulPhotoMatcher`, same
  transport/key/logging style as stage 5. Prompt: photo size in pixels + product
  lines as `lN | receipt text | product Polish name | quantity unit` (no prices,
  no ids; `|`/line breaks neutralised; list is data). Schema
  `{items:[{box{x1,y1,x2,y2}, line|null, confidence}]}`. Strict validation
  (matcher and again in the service, `HaulPhotoRules.Enforce`): item without a
  usable box or with a bad confidence dropped; boxes clamped, sides < 2 %
  dropped; unknown code → item kept without a line; a line used more often than
  its whole quantity (> 1) keeps only its most confident items; ≤ 40 items.
- **Save**: crop (4 % margin) → `IProductMediaService.AddPhotoAsync` (existing
  limits, audit, storage; first photo becomes main, an existing main photo
  stays). Discount lines and lines of other purchases → `lineNotFound`; line
  without product → `noProduct`.
- **Model: Claude Sonnet 5.5, effort Medium** (configurable). Why: 10–30 items
  on one photo, boxing each and telling look-alike lines apart is spatial and
  comparative work where Haiku is weakest; it runs once per shopping trip.
  Prices added to `AnthropicPricing`: Sonnet 5.5 $2/$10, Opus 5.5 $4/$20 per M.
- **Logging**: counts (lines, items, paired, rejected), ms, model, tokens, cost;
  never the image, prompt, line names or key (tested on the log files).
- **UI**: on a saved purchase, row «Сфотографировать покупки» under date/total
  (only when status is enabled) → camera → «Ищу покупки на фото…» → one row per
  item: CSS cut-out of the sent photo, a line select (lines without product
  disabled, discounts hidden), confidence, «Верно» / pick another line (=
  confirm) / «Пропустить», «Изменить» to undo → «Сохранить фото (N)» → summary
  (saved, already saved, not saved with reasons). Recognition is a mutation sent
  once per photo id (focus or `invalidateQueries()` never repeats it); retry
  only via «Попробовать ещё раз». i18n ru+en.
- **Help**: new topic «Сфотографировать покупки» (`haul-photo`, ru+en,
  catalog group) + `HelpLink` in the sheet.
- **Benchmark** `tools/PurchaseMemory.HaulPhotoBenchmark` (core linked into
  tests): refuses without a positive `--budget-usd`, exits 2 for a model
  without a known price or without key, stops before a call could cross the
  budget: every call is assumed at max(worst case, most expensive so far),
  worst case = 6 000 input + all `MaximumOutputTokens` at the model's list
  price (Sonnet $0.092); a failed call is charged at that estimate; usage
  without cost at $30/$150 per M. Same fix applied to the stage-5
  `FindByPhotoBenchmark` (worst case = 20 000 input + max output, Haiku $0.004). Outputs correct /
  wrong pairs (multiset per line), missed, found without a line, precision,
  recall, mean ms, mean and total cost; per-photo CSV + `.summary.txt`;
  `--crops <folder>` writes every proposed crop for a visual box check.

## Estimated cost (computed, not measured)
Sonnet 5.5: input ≈ 1 500 (image ≤ 1.15 MP) + 650 prompt + 30 lines × 20 ≈
2 800 tokens → $0.006; output (medium thinking + ~25 boxed items) ≈ 2–4k →
$0.02–0.04. **≈ $0.03–0.05 per photo**; worst case (8 000 output tokens) ≈
$0.09. Haiku 5.5 on the same photo ≈ $0.002–0.004.

## Limits
- Hit rate and box quality are unknown until the measurement; that is why the
  switch is off. Boxes are not scored by the benchmark (no box labels): use
  `--crops` and look.
- Save does not re-apply the per-line quantity rule: a person may pair one line
  with several items on purpose (each becomes a photo, up to 20 per product).
- No swipe review reuse: a plain list was simpler and accessible (select +
  buttons); can move to the carousel later if the owner prefers.
- HEIC photos are not decoded by the server/benchmark; the phone app sends JPEG
  (browser canvas), but benchmark photos must be JPEG/PNG.
- Shrinking happens on the phone; a 48 MP photo takes a moment on old phones.

## How the owner prepares ≥ 5 labelled hauls
1. After a shopping trip, save the receipt, lay all items out on the table and
   take one photo from above (iPhone: Settings → Camera → Formats → «Most
   Compatible», or export as JPEG). Put the photos in a folder outside the repo,
   e.g. `~/Pictures/haul-photos/`.
2. For each trip, save the purchase JSON: in desktop Chrome/Safari open the
   purchase in the app with developer tools → Network, «Save response» of
   `GET /api/purchases/<id>` as `purchase-1.json` next to the photos.
3. `hauls.json` in the same folder (UTF-8):
   ```json
   [
     {"file": "IMG_2001.jpg", "purchase": "purchase-1.json",
      "expected": ["MLEKO UHT 3,2% 1L", "JOGURT NAT 150G", "JOGURT NAT 150G", "Chleb żytni"]}
   ]
   ```
   `expected` = the receipt text (or the product's Polish name) of every item
   visible on the photo, repeated when several pieces of one line are visible.
   Instead of `purchase` you may give `"lines": [{"name", "product", "quantity", "unit"}]`.
