# Результаты: подготовка к хостингу на Render

Дата: 06.10.2026. Пункт 5 плана деплоя. Цель: образ Docker, который запускается
на бесплатном Render (512 МБ, 0.1 CPU) за его HTTPS-прокси, с Postgres и фото
в Supabase. Сам сервис на Render создаётся отдельно (раздел «Деплой на Render»
ниже).

## Что сделано

1. **Порт из `PORT`.** Приложение слушает `http://0.0.0.0:$PORT`, если
   переменная задана (Render ставит 10000). В образе по умолчанию `PORT=5099`,
   поэтому `compose.yaml` работает как раньше. Неверное значение (`0`, `80a`,
   `70000`) останавливает запуск с понятной ошибкой. В Development `PORT` не
   используется: там порт задаёт `launchSettings.json`, и случайная переменная
   в терминале не уведёт API от порта, который ждёт Vite.
   Код: `src/PurchaseMemory.Api/Configuration/HostingSetup.cs`.
2. **Проверка здоровья.** Уже была: `/health` без входа отвечает
   `{"status":"healthy"}` и ничего больше. Переиспользована. Отвечает только
   после применения миграций.
3. **За прокси.** Новая настройка `ReverseProxy__TrustForwardedHeaders`
   (по умолчанию выключена, на Render — `true`). Берётся только последняя
   запись `X-Forwarded-For`/`X-Forwarded-Proto` (её дописывает Render), всё, что
   подставил клиент, игнорируется. Список доверенных прокси пуст, потому что
   Render их адреса не публикует; это безопасно, только пока контейнер доступен
   лишь через прокси. Включить её вместе с `Auth__DevelopmentBypass` нельзя —
   приложение не запустится. Лимиты запросов и так считаются по пользователю, а
   не по IP. Подробнее: `docs/ДЕПЛОЙ_RENDER.md`.
4. **Защита в Production проверена (поведение не менялось, тесты уже были):**
   `Auth__DevelopmentBypass` вне Development останавливает запуск; без
   настроек Supabase API отвечает 401 всем; фото чеков без входа не отдаются.
   Добавлены тесты, что за прокси запросы без токена и с поддельным токеном
   (даже с `X-Forwarded-For: 127.0.0.1`) получают 401, а `/health` — 200.
5. **Dockerfile:**
   - убран адрес локального Ollama (`host.docker.internal:11434`); для
     локального запуска он уже задан в `compose.yaml`; в образе действует
     распознавание через OpenAI из `appsettings.json`;
   - сборка frontend и .NET идёт на платформе сборщика без эмуляции,
     публикация под `linux/amd64` (под эмуляцией Vite на Mac падает);
   - ReadyToRun: холодный старт быстрее примерно на треть (замеры ниже);
   - запуск от непривилегированного пользователя `app` (uid 1654);
   - `DOTNET_gcServer=0` (workstation GC), см. замеры.
   - SDK-образ закреплён на `10.0.302`: плавающий тег `10.0` уже указывает на
     SDK 10.0.4xx, который `global.json` (10.0.301, latestPatch) не принимает.
6. **`.dockerignore`** не пускает в сборку `data/`, `logs/`, `test-data/`,
   `tmp/`, документы, тесты и `*.env`.
7. **Скрипт `scripts/publish-image.sh`:** логин в GHCR токеном из `gh` (не
   печатается), сборка `linux/amd64`, выкладка с тегом времени (UTC) и
   `:latest`, вывод digest.
8. **Документы:** новый `docs/ДЕПЛОЙ_RENDER.md` (переменные Render — секретные и
   нет, порт, health check, как обновлять), ссылки из
   `docs/ДЕПЛОЙ_ЧТО_НУЖНО_ОТ_ВАС.md`, `PORT` и
   `ReverseProxy__TrustForwardedHeaders` в `docs/ПЕРЕМЕННЫЕ_И_СЕКРЕТЫ.md`.

Видимых пользователю изменений нет, подсказки не менялись.

## Замеры

Docker Desktop на этом Mac запускает `amd64` через QEMU (Rosetta в Docker
выключена), а под QEMU .NET и медленный (×20–30), и нестабильный. Поэтому:

- **время и память** измерены на том же Dockerfile, собранном под `arm64`
  (нативно), с `--memory=512m --cpus=0.1`, SQLite в контейнере, первый запуск с
  пустой базой (10 миграций);
- **образ `amd64`** проверен функционально под QEMU (смоук ниже), его цифры
  времени и памяти не показательны (QEMU сам занимает память).

| Что | Результат (0.1 CPU, 512 МБ) |
|---|---|
| Старт до `/health` = 200, без ReadyToRun | 17.9–20.1 с |
| Старт до `/health` = 200, с ReadyToRun (итоговый образ) | 11.6–13.7 с |
| Память (RSS) в простое | ≈ 161–166 МБ |
| После загрузки SPA и нескольких API-запросов | ≈ 163–175 МБ |
| Загрузка фото 4123×5600 (1.8 МБ) + сжатая копия | 6–9 с, RSS ≈ 213 МБ, пик ≈ 260 МБ |
| После попытки распознавания (без сети, см. ниже) | ≈ 220 МБ |
| Размер образа (несжатый) | ≈ 450 МБ (ReadyToRun добавил ≈ 48 МБ) |

Сборка мусора (тот же сценарий с фото):

| Режим | 0.1 CPU: пик / после | 8 CPU: пик / после |
|---|---|---|
| workstation (`DOTNET_gcServer=0`) | 263 / 220 МБ | 268 / 235 МБ |
| server (по умолчанию в web SDK) | 263 / 222 МБ | 274 / 238 МБ |
| workstation + `GCConserveMemory=5` | 265 / 220 МБ | — |

При квоте 0.1 CPU среда видит один процессор, и режимы равны. Если хостинг
покажет больше процессоров, server GC берёт на несколько МБ больше. Поэтому в
образе закреплён workstation GC, а `GCConserveMemory` не дал выигрыша и не
добавлен. Запас до 512 МБ — больше 240 МБ.

Как мерили фото без платных вызовов: Development + `Auth__DevelopmentBypass`,
запросы из соседнего контейнера через loopback; распознавание `openai` без
ключа (падает локально, без сети), запасной Ollama — на закрытый порт
`127.0.0.1:9`; категории и аналитика выключены. Статус чека — `failed`, как и
ожидалось.

## Известные ограничения

- Под QEMU (этот Mac) .NET в `amd64` при включённом W^X может упасть с
  `AccessViolationException`; для локальной проверки `amd64` нужен
  `DOTNET_EnableWriteXorExecute=0` или Rosetta в Docker Desktop. На настоящем
  `amd64` (Render) это не нужно, в образе W^X не выключен.
- Первый запуск на пустой базе включает все миграции; на Render холодный старт
  после засыпания добавит ещё время на подъём контейнера.
- Запасной путь распознавания `ollama` в облаке недоступен (адрес
  `127.0.0.1:11434`): если OpenAI не ответит, запасная попытка сразу
  завершится ошибкой, чек станет «не распознан», как и без запасного пути.
- Ключи Data Protection хранятся внутри контейнера (предупреждение в логе).
  Приложение их не использует для входа (вход — по JWT Supabase), так что это
  ни на что не влияет.
- Диск Render временный: файловые логи пропадают при перезапуске; логи
  смотреть в панели Render.
- Локальный `compose.yaml` монтирует `./data`. Проверить это с образом на этом
  Mac не удалось без использования `data/`: тестовое монтирование папки из
  временного каталога падает с `readonly database` одинаково от root и от
  `app`, то есть дело не в новом пользователе. На Linux при монтировании папки
  она должна принадлежать uid 1654.

## Деплой на Render

Сделано 06.10.2026, приложение работает: https://purchase-memory.onrender.com

**Сервис.** `purchase-memory` (`srv-db2f85h7lnhs73eoaod0`), Render free,
Франкфурт, из образа `ghcr.io/chukin/purchase-memory:latest` (digest
`sha256:6691647e…dc17f`), health check `/health`. Автодеплой выключен:
новая версия выкладывается скриптом `scripts/publish-image.sh`, затем
**Manual Deploy** в Render.

**Переменные.**

- Несекретные, вписал агент через API: `ASPNETCORE_ENVIRONMENT=Production`,
  `PORT=10000`, `ReverseProxy__TrustForwardedHeaders=true`,
  `Database__Provider=Postgres`, `Storage__Provider=S3`,
  `Storage__S3__ServiceUrl`, `Storage__S3__Region=eu-west-2`,
  `Storage__S3__Bucket=receipts`, `Auth__SupabaseUrl`,
  `Auth__SupabasePublishableKey`.
- Секретные, вписал владелец в панели: `OPENAI_API_KEY`,
  `ConnectionStrings__Postgres`, `Storage__S3__AccessKeyId`,
  `Storage__S3__SecretAccessKey`.
- Не заданы и задаваться не должны: `Auth__DevelopmentBypass`,
  `ReceiptRecognition__BaseAddress`.

Проект Supabase на самом деле в Лондоне (`eu-west-2`), а не во Франкфурте, как
считалось раньше. Задержка Франкфурт ↔ Лондон небольшая, менять ничего не нужно.

**Как шёл запуск.**

1. Первый запуск упал: секреты ещё не были вписаны, строка подключения пустая.
   Так и ожидалось.
2. Второй упал: в `ConnectionStrings__Postgres` была вставлена ссылка вида
   `postgresql://…`, а приложение (Npgsql) ждёт формат
   `Host=…;Port=…;Username=…;Password=…;SSL Mode=Require`.
3. Третий успешный: применены 4 миграции, создана схема `purchase_memory`
   (16 таблиц), подключено хранилище S3, приложение слушает порт 10000.

Шум в логе, не влияющий на работу: нет `libgssapi_krb5` (Kerberos не нужен),
предупреждения Data Protection, одна ожидаемая ошибка при первом чтении
истории миграций (таблицы ещё не было).

**Проверка снаружи (настоящий адрес).**

| Запрос | Ответ |
|---|---|
| `/`, `/health`, `/api/auth/config` | 200; вход без пароля (`developmentBypass`) выключен, способы входа: email и Google |
| `/api/me`, `/api/purchases`, `/api/receipts` без токена | 401 |
| Поддельный JWT + `X-Forwarded-For: 127.0.0.1` | 401 |
| `POST /mcp` без токена | 401 |
| Data API Supabase (`/rest/v1`) публичным ключом | 401 / 503, таблицы приложения не видны |

Роли `anon`, `authenticated` и `service_role` не имеют доступа к схеме
`purchase_memory`, поэтому предупреждение Supabase «RLS disabled» для этих
таблиц не означает утечку: через публичные ключи их не прочитать. Приложение
ходит в базу как владелец таблиц.

**Первый вход.** Владелец вошёл, получил статус «ожидает»; агент через SQL
поставил `approved`.

**Первый настоящий чек** (с телефона, E.Leclerc, 06.10.2026): фото 3,9 МБ
сохранено в бакет `receipts`, рядом сжатая копия 655 КБ (1800×2400);
распознавание OpenAI `gpt-6-sol` около 26 секунд; 53 позиции, сумма позиций
423,46 PLN совпала с итогом чека; 9 позиций без товара в каталоге, 4 — в
очереди «Нужно проверить».

**Замеченное после запуска** (исправляется на следующем этапе):
при каждом открытии приложения проверка статуса распознавания стучится в
Ollama (`127.0.0.1:11434`), которого в облаке нет, и пишет в лог полный стек
ошибки. На работу не влияет.
