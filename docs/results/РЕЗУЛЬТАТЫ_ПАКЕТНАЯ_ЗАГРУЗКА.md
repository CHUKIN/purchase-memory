# Results: batch upload («каждое фото — отдельный чек»)

Date: 2026-10-08.

## What was done

- Capture screen (`/purchases/new`): when two or more photos are selected, a
  choice «Что на этих фото?» appears: «Части одного чека» (default, old
  behaviour) or «Отдельные чеки». Each option has a one-line explanation.
- Separate mode: photos are labelled «Чек N», reordering is hidden, a note says
  each photo is recognised separately (N photos = N recognitions), the button
  reads «Загрузить N чеков». Limits: max 10 photos per batch, 15 MB per photo,
  JPEG/PNG/WebP.
- Upload is sequential (one `POST /api/receipts?process=true` per photo), with a
  per-photo status: waiting, uploading, uploaded (recognizing), already uploaded
  (exact duplicate), failed (with server message and «Повторить»), upload limit.
- 429: the batch stops at once (no further requests), shows the wait from
  `Retry-After` in minutes, and the rest is resumed only by «Загрузить
  оставшиеся». Remaining photos are shown as «Не загружено».
- After the batch: summary «Загружено чеков: X из N», links «Открыть чек» per
  photo, «На главную», «Загрузить другие фото».
- Every successful upload invalidates `["receipts","recent"]`, so App polling
  starts and per-receipt ready/failed notifications work for the whole batch
  (`listRecentReceipts(20)` covers a batch of 10).
- Leaving the screen stops the batch after the photo in flight.

## Backend change (small, needed)

The upload rate limit (`RateLimiting:ReceiptUploads`, burst 10, then 1 per
180 s) is shared by `POST /api/receipts` and `POST /api/receipts/{id}/process`,
so the existing upload+process flow spends 2 tokens per receipt — a 10-photo
batch would hit 429 after 5. Added optional `?process=true` to the upload
endpoint: it queues recognition in the same request (1 token per receipt).
Exact duplicates are not queued. If queueing fails after a durable upload, the
receipt is returned as `uploaded` (logged, EventId 7101); the receipt page
already offers the queue action. Without the flag behaviour is unchanged; the
single-receipt flow still uses upload + `/process`.

## Known limitations

- The client cannot know how much of the burst is left; a partly spent burst
  ends in a 429 and the user resumes later.
- Home «Чеки в работе» shows only 5 receipts; the rest of a batch is reachable
  from the batch summary and notifications.
- Single-receipt flow still costs 2 tokens (upload + process); switching it to
  `?process=true` is a candidate follow-up.
- A batch is not resumable after leaving the screen or reloading.

## Next candidate step

Use `?process=true` in the single-receipt flow too (one token per receipt).

## Review follow-up (2026-10-09)

- Single-receipt capture (one photo or parts of one receipt) now also uses
  `POST /api/receipts?process=true` — one rate-limit token per receipt instead
  of two. Behaviour is unchanged: an exact duplicate is not queued (it was not
  queued before either; the duplicate notice links to the existing receipt,
  whose page offers «Начать распознавание»/retry if it is still uploaded); if
  the server can't queue, the receipt comes back `uploaded` and its page
  offers the explicit queue action. The client no longer calls `/process`
  after upload. The two limitation/next-step bullets above are resolved.
- Receipt detail title is now per status: «Чек загружен» (uploaded / queued /
  processing), «Чек распознан» (ready, not saved yet), «Чек не распознан»
  (failed), «Чек сохранён» only for saved (en: Receipt uploaded / recognized /
  not recognized / saved). Keys `receiptProgress.title{Active,Ready,Failed,Saved}`.
- Help `capture-batch` (ru/en) now mentions «Не загружено» / “Not uploaded”
  and «Загрузить другие фото» / “Upload other photos”.
- Batch «Открыть чек» status link has a 44px min-height.
- Tests: `CapturePage.test.tsx` — upload+queue in one request, server-could-
  not-queue path, per-status titles; batch test expects `{ process: true }`
  for the parts flow.
