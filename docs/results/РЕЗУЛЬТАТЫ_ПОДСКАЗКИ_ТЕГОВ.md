# AI tag suggestions (Haiku) — 11 Oct 2026

Product rules (`ПРОДУКТОВАЯ_СЕССИЯ.md`, «Категории и теги»; `РЕЗУЛЬТАТЫ_ТЕГИ.md`):
only people create tags; AI may suggest only existing household tags; nothing
is applied without a person's confirmation.

## What was done

### API

`POST /api/products/{id}/tag-suggestions?locale=ru|en` (no body; approved-user
policy like every endpoint; own per-user rate-limit bucket `tag-suggestions`,
30 burst then 1 per 2 min ≈ 30/hour, `RateLimiting:TagSuggestions:*`).

```json
{ "productId": "…", "offeredTagCount": 4,
  "suggestions": [ { "tagId": "…", "name": "веган", "reason": "Овсяный напиток на растительной основе" } ] }
```

- `offeredTagCount` = household tags not yet on the product. 0 (no tags, or all
  already on the product) → empty answer, **no model call**. A product at the
  20-tag limit also gets an empty answer without a call.
- 404 unknown product; 503 `{code: "tagSuggestionsUnavailable"}` when the
  suggester is switched off / has no key / times out / errors / refuses /
  returns malformed JSON (cause only in the log); 429 `Too many tag
  suggestions` with `Retry-After`.
- Accepting is the existing `PUT /api/products/{id}/tags` (so the product audit
  trail records it as a human change).

### Code

- Application `Products/Tags/ProductTagSuggestions.cs`: `ITagSuggester`
  (provider contract), `IProductTagSuggestionService`/`ProductTagSuggestionService`
  — builds context (name, brand, category path, up to 5 receipt wordings and
  merchant keys from aliases), offers only tags not on the product, then drops
  any id that was not offered, repeats, caps at 5, trims reasons to 160 chars.
- Infrastructure `Tagging/AnthropicTagSuggester.cs` + `TagSuggestionOptions`
  (`TagSuggestions:*`: `Enabled`, `Model`=`claude-haiku-5-5`, `Effort`=Low,
  timeout 30 s, 1 retry, 4000 output tokens, up to 200 offered tags). Reuses the
  recognition `AnthropicMessagesTransport` (text-only request = no images) and
  `AnthropicPricing`; tags go as codes `t1…tN` in a strict `enum` in the
  structured-output schema. Prompt marks receipt text as data, asks for reasons
  in ru/en. Log: model, effort, latency, message id, offered/suggested counts,
  tokens, cost estimate; never the key or the prompt.
- Small refactor: `AnthropicFailure.Categorize` (in the transport file) now
  shared by the receipt provider and the tag suggester (same categories as before).
- Test host sets `TagSuggestions:Enabled=false` so tests never call a paid model.

### Web

- `features/tags/TagSuggestions.tsx`, wired in `ProductTags` (view mode) via
  `ProductCard.onSuggestTags` → `suggestProductTags(productId, locale)`.
- «Предложить теги» (Sparkles icon + text) appears only when some household tag
  is not on the product yet and the product has < 20 tags. States: loading
  («Подбираем подходящие теги…», button spinner), shown (chip + reason,
  «Добавить» = check icon on phones / text on wide screens, «Скрыть» = cross,
  «Добавить все» when ≥ 2), empty («Подходящих тегов не нашлось.»),
  unavailable, rate-limited (minutes from `Retry-After`), accept error. Status
  messages are in an `aria-live` region.
- `ProductCard` no longer remounts `ProductTags` on every tag change (it would
  drop the remaining suggestions after one accept); editing still re-reads the
  current tags when it starts.
- i18n ru/en `tags.suggest*`, `accept*`, `dismiss*`. Stories: `WithSuggestions`,
  `WithSuggestionsMobileEn`, `SuggestionsShown(Mobile)`, `SuggestionsLoading`,
  `SuggestionsEmpty`, `SuggestionsUnavailable`, `SuggestionsRateLimited`.
- Help topic `tags` (ru+en): how to use «Предложить теги», that AI only picks
  existing tags and nothing is added without «Добавить»/«Добавить все», and the
  three error messages. `docs/ПЕРЕМЕННЫЕ_И_СЕКРЕТЫ.md`: `TagSuggestions__*` row.

## Quality and cost (opt-in benchmark)

`tools/PurchaseMemory.TagSuggestionBenchmark` — no database; 12 synthetic
household tags, 15 typical Polish grocery products with expected/acceptable
tags; stops at a budget (default $0.05). Run:
`zsh -ic './scripts/dotnet.sh run --project tools/PurchaseMemory.TagSuggestionBenchmark -- --locale ru'`.

| Run | Precision (picked ∈ expected/acceptable) | Recall of expected | Cost | Per call | Median latency |
|---|---|---|---|---|---|
| ru | 21/23 (91 %) | 14/14 | $0.00172 | $0.00011 | 1.6 s |
| en | 22/25 (88 %) | 14/14 | $0.00175 | $0.00012 | 1.6 s |

Manual judgement: picks are sensible. Misses are "loosely related" extras —
«без глютена» for tofu (actually true), «завтрак» for gluten-free bread or
milk. «акция» was picked only when the receipt said PROMOCJA. ~820 input and
~50–110 output tokens per call (adaptive thinking at low effort barely thinks).

Anthropic spend this stage: ≈ $0.0036 (2 benchmark runs + 1 smoke call).
OpenAI: $0.

## Review follow-up

Independent review findings, fixed (no paid calls):

1. `ProductCard` keys `ProductTags` by `product.id`: switching to another
   (cached) product starts fresh — no carried-over suggestions, no accept
   onto the wrong product, an in-flight answer for the old product is dropped.
   Accepting still keeps the remaining suggestions. Two new `ProductCard`
   tests (both fail without the key).
2. Every 503 cause is logged with an event id, no secrets: service warns 3402
   when the suggester is off/unconfigured; the suggester logs 3412 for
   `disabled`/`not_configured`, transport categories, stop reasons, malformed
   JSON and a new catch-all `unexpected:<ExceptionType>` (so any SDK surprise
   is a 503, not a 500).
3. `TagSuggestionOptionsValidator` + `ValidateOnStart`: model required when
   enabled, effort defined, timeout 1–300 s, retries 0–5, output tokens
   256–64000, offered tags 1–1000. Bad config stops the host at startup.
4. A11y: the `aria-live` region announces «Найдена/Найдены/Найдено N
   подсказ…» / «N suggestion(s) found»; after «Добавить»/«Скрыть» focus moves to
   the next suggestion (first enabled button in that row), or to «Предложить
   теги» when none are left.
5. Accept builds the PUT from the freshest tags: `ProductsPage` passes
   `readCurrentTagIds` (reads the product from the query cache at click time);
   the render-time tags are only a fallback.

Re-run: `dotnet build` 0 warnings/0 errors; `dotnet test` 622 passed, 8
skipped, 0 failed (+2: logging of every unavailable cause, options
validation incl. host start failure); `tsc -b` clean; `vitest` 35 files, 285
passed (+3: product switch ×2, freshest tags; focus/announcement assertions
added to the accept test).

## Known limitations

- Suggestions are not cached: each press is a new call (cheap, rate-limited).
- Context is product-level only (name, brand, category, aliases); tags about
  circumstances («к празднику») are suggested only when the name says so.
- Tags have no description field, so the model sees only tag names.
- Suggestions are per product; no bulk tagging (product decision, later).
- No OpenAI fallback: without `ANTHROPIC_API_KEY` the button shows
  «недоступны» (the rest of the app is unaffected).
