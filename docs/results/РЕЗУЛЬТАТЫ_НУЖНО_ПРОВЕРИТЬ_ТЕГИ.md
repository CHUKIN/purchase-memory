# Фильтр по тегу в «Нужно проверить» (3 октября 2026)

Продолжение `РЕЗУЛЬТАТЫ_НУЖНО_ПРОВЕРИТЬ.md` и `РЕЗУЛЬТАТЫ_ТЕГИ.md`. Теперь
очередь «Нужно проверить» можно сузить до одного тега: например, разобрать
только то, что касается товаров «Для ребёнка». Правила очереди не менялись,
миграций нет.

## Что сделано

### Что значит «пункт с тегом»

Тег принадлежит товару, поэтому пункт очереди подходит под тег только через
товар из каталога:

| Группа | Когда пункт остаётся с тегом |
|---|---|
| Категория не подтверждена, Без категории | у самого товара есть тег |
| Сумма не сходится, Нет цены | хотя бы одна строка покупки связана с товаром, у которого есть тег (то же правило, что в «Истории покупок») |
| Чек не распознан, Чек ждёт сохранения | никогда — у такого чека ещё нет товаров |
| Товар не сопоставлен | никогда — строка ещё не связана с товаром; «похожий товар» не считается, даже если у него есть тег |

- Несколько тегов (`?tagId=a&tagId=b`) — это «И»: нужны **все** теги на
  **одном** товаре. Если один тег у одной строки покупки, а другой — у
  другой, покупка не подходит. Так же работают каталог и лента.
- Лимит «первые N в группе» работает как раньше; числа в группах и общее
  число на экране — уже с учётом тега.
- **Число в меню (значок) остаётся общим.** `GET /api/review-queue/count`
  тег не принимает (лишний параметр игнорируется): значок про всю очередь,
  а не про то, что выбрано на экране. Экран пишет «N пунктов с тегом «…»
  требуют внимания» и поясняет, что число в меню считает всю очередь.
- Неизвестный или удалённый тег — 400, не-GUID — 400, пустое `?tagId=` —
  фильтра нет. Это то же поведение, что у `/api/purchases` и
  `/api/products` (общая проверка `ProductClassificationFilter`).

### API

- `GET /api/review-queue?limitPerKind=20&tagId=…` — `tagId` можно повторить.
- Подходящие товары отбираются тем же SQL-запросом, что и для ленты
  (`ListMatchingProductIdsAsync`, подзапрос `EXISTS` на каждый тег), поэтому
  перевод запроса в SQLite и Postgres уже проверен; сопоставление с пунктами
  очереди — в памяти, как и остальная очередь. Репозиторий очереди теперь
  отдаёт для каждой покупки id товаров её строк.
- Доступ — как у остальных данных (только одобренный пользователь).

### MCP

- `list_review_queue` принимает необязательный `tagIds` (массив id из
  `list_tags`, нужны все). В описании инструмента сказано, что именно
  остаётся с тегом и что нераспознанные чеки и несопоставленные строки
  при этом не видны. Неизвестный тег — ошибка инструмента с понятным
  текстом («Tag … was not found.»).

### Интерфейс

- Над очередью — поле «Тег» («Все теги» + теги семьи). Это тот же элемент,
  что в «Истории покупок» и «Товарах»: из `ClassificationFilterFields`
  выделен отдельный компонент `TagFilterField`, и его используют все три
  экрана. Поле видно, только когда в доме есть хотя бы один тег; без тегов
  страница выглядит как раньше.
- Тег хранится в адресе (`/needs-attention?tag=…`), как в ленте: ссылкой
  можно поделиться, после «Назад» фильтр на месте. Тег из ссылки, которого
  больше нет, молча сбрасывается на «Все теги» без лишнего запроса с 400;
  если список тегов не загрузился, показывается вся очередь.
- С выбранным тегом под полем — пояснение (что скрыто и что число в меню
  про всю очередь) и кнопка «Сбросить фильтр».
- Пустой результат с тегом — «С этим тегом всё проверено» / «Нет пунктов о
  товарах с тегом «…». Остальное — в полной очереди.» и «Сбросить фильтр»
  (обычное «Всё проверено» с тегом не показывается, чтобы не путать).
- Тексты ru и en. Страница разделена на подключение к API
  (`ReviewQueuePage`) и отображение (`ReviewQueueView`) — для stories.
- Stories `Purchase Memory/Review queue/Tag filter`: `WholeQueueDesktop`,
  `KidsMobile`, `KidsDesktopEn`, `FilteredEmptyMobile`, `NoTagsMobile`.
  На 375 px горизонтального скролла нет (проверено в браузере).

### Подсказки

## Известные ограничения

- Выбрать можно один тег; несколько (И) — только через API/MCP.
- С тегом не видно нераспознанных и несохранённых чеков и несопоставленных
  строк — это следствие правила «тег есть только у товара», а не ошибка.
- «Сумма не сходится» и «Нет цены» показываются, если тег есть у любой
  строки покупки, даже если проблема в другой строке (как в ленте).
- Как и раньше, проверяются последние 5000 покупок.
- В MCP параметр называется `tagIds` (массив, как в `run_analytics_plan`), а
  не `tagId`, как в `search_purchases`.

## Для подсказок

- В «Нужно проверить» есть поле «Тег»: выберите, например, «Для ребёнка»,
  чтобы разобрать только это. «Все теги» или «Сбросить фильтр» возвращают
  всю очередь. Поле появляется, когда есть хотя бы один тег.
- С тегом остаются товары с этим тегом (категория не подтверждена, без
  категории) и покупки, где хотя бы одна строка — такой товар (сумма не
  сходится, нет цены).
- Нераспознанные и несохранённые чеки и несопоставленные строки с тегом не
  видны: у них ещё нет товара.
- Число в меню всегда считает всю очередь.
- «С этим тегом всё проверено» — по товарам с этим тегом вопросов нет, а
  остальная очередь может быть не пустой.
