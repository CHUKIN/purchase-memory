# Purchase Memory — результаты проверки технического ядра

Дата проверки: 31 июля 2026  
Среда: Apple Silicon, .NET 10, локальный Ollama 0.31.1  
Контракт: `receipt.extract.prompt.v1` + `receipt.extract.schema.v1`

## Итог

Техническое ядро жизнеспособно:

```text
фото
  → REST upload
  → локальная очередь
  → выбранный конфигурацией provider
  → общий prompt и JSON Schema
  → строгий parser и C#-валидация
  → редактируемый черновик
  → сохранение только после подтверждения
```

OpenAI и Ollama реализуют один Application-контракт. Обычные тесты не требуют
сети, API key или запущенной модели. Реальный OpenAI-вызов не выполнялся:
`OPENAI_API_KEY` отсутствовал.

## Автоматические проверки

| Проверка | Результат |
|---|---:|
| `dotnet build` | успешно, 0 warnings, 0 errors |
| .NET tests | 76/76 |
| `dotnet format --verify-no-changes` | чисто |
| Frontend tests | 1/1 |
| Production PWA build | успешно |

Contract tests отдельно проверяют:

- фактическое тело OpenAI Responses API, созданное официальным SDK;
- image detail, model, reasoning, limits, `store=false` и strict schema;
- Ollama `/api/tags` и `/api/show`;
- отказ до image-call, если модель не объявляет `vision`;
- одинаковую JSON Schema в Ollama `format` и prompt;
- caller cancellation, timeout, network, HTTP и некорректные ответы;
- одну ограниченную repair-попытку и отсутствие автоматического сохранения.

## Реальные локальные прогоны

Это smoke-прогоны, а не репрезентативный benchmark. Время включает загрузку
моделей и зависит от их прогрева.

| Изображение | Pipeline | Время | Фактический результат |
|---|---|---:|---|
| Lidl, 230×371 | `glm-ocr → qwen3.5:4b` | 25,4 с | strict JSON; итог 102,62 PLN; 0 позиций |
| Lidl, 230×371 | `glm-ocr → qwen3.5:9b` | 36,4 с | strict JSON; все поля пусты |
| Lidl, 230×371 | `glm-ocr → gemma4:12b-mlx` | 81,1 с | 14 позиций, но много OCR-ошибок и неверных сумм |
| Lidl, 230×371 | direct vision `qwen3.5:9b` | 34,6 с | 9 позиций, но заметные галлюцинации и неверный итог |
| Biedronka, 2856×3879 | `glm-ocr → qwen3.5:4b` | 34,8 с smoke / 42,3 с API E2E | магазин, дата, валюта и 3/3 товарных строк; скидка и итог распознаны неверно |

Маленький иллюстративный Lidl оказался стресс-тестом, а не хорошей имитацией
фото с телефона. На high-resolution Biedronka быстрый 4B baseline извлёк:

- `Biedronka`;
- дату `2020-01-09 13:18 +01:00`;
- валюту `PLN`;
- три правильных названия и цены строк.

Он пропустил скидку `-2,00` и вернул итог `8,66` вместо `8,27`. Общая
проверка не скрыла проблему: черновик получил предупреждение, что сумма строк
`10,27` не совпадает с распознанным итогом `8,66`.

Вывод: локальный 4B pipeline подходит как быстрый dev-provider и уже полезен
для проверки интеграции, но не должен сохранять данные без review. Увеличение
Qwen с 4B до 9B само по себе качество не исправило. Выбор production/default
модели требует общего benchmark на фотографиях владельца; для размещённой PWA
основным кандидатом остаётся OpenAI.

## Сквозная проверка API и PWA

Приложение было запущено на чистой временной SQLite-базе:

- `/health` → healthy;
- `/api/recognition/status` → `ollama`, обе модели доступны;
- multipart upload → `uploaded`;
- process → `queued → processing → ready`;
- готовый draft содержит provider `ollama`, model
  `glm-ocr:latest → qwen3.5:4b`, три строки и предупреждение;
- история PWA осталась пустой, потому что draft не подтверждался и не
  сохранялся.

Встроенный тестовый браузер корректно отрисовал PWA и статус модели, но его
file chooser не передал файл скрытому camera-input. Поэтому multipart-часть
сквозного теста была выполнена через настоящий HTTP endpoint. Сам UI выбора
файла остаётся покрыт frontend-тестом и доступен для ручной проверки в обычном
браузере/телефоне.

После изолированной проверки приложение перезапущено в обычном локальном
режиме: SQLite находится в `data/purchases.db`, изображения — в
`data/receipts/`, ежедневные логи — в `logs/purchase-memory-*.log`.

## Что доказано, а что ещё нет

Доказано:

- провайдер меняется конфигурацией без изменения frontend и workflow;
- OpenAI key остаётся только на backend;
- Ollama работает локально без OpenAI key;
- модель не может обойти строгий DTO и C#-валидацию;
- ошибка/пустой/невалидный ответ не создаёт покупку;
- текущая PWA и API умеют довести файл до проверяемого draft.

Не доказано:

- production-качество OpenAI без реального ключа;
- достаточная точность на чеках владельца;
- удобство итогового UX на телефоне;
- восстановление очереди при нескольких репликах;
- безопасность публичного deploy для нескольких пользователей.
