# Purchase Memory — результаты UI-3, срез «лента покупок и фильтры»

Дата реализации: 26 августа 2026
Статус: реализован узкий первый срез UI-3. **UI-3 целиком не завершён**:
issue-based review, полноценный редактор сохранённой покупки и audit trail
остаются отдельными будущими срезами.

## Результат

Главная больше не показывает список «недавних чеков» как основной контент.
Вместо него появилась настоящая хронологическая лента сохранённых покупок с
фильтрами: период, статус проверки и прежний свободный текстовый поиск. Все
фильтры комбинируются по AND и передаются в backend как query-параметры одного
запроса `GET /api/purchases`.

Карточка покупки показывает магазин, дату, сумму, количество позиций и статус
проверки. Статус проверки не хранится в БД: покупка считается требующей
внимания, если её `Warnings` непусты, то есть если сумма строк расходится с
итогом чека. Никаких новых доменных полей (сеть/филиал магазина, участник,
категория товара, признак промо) не добавлялось.

## Решения, принятые в рамках среза

- **Пагинация — `page` + `pageSize`, а не курсор.** `GET /api/receipts?limit=N`
  из UI-2 отдаёт «последние N» и не пагинируется, поэтому переиспользовать его
  форму было нечего. Страничная модель даёт ленте `totalCount`, который нужен,
  чтобы отличить «покупок ещё нет» от «под фильтры ничего не подходит».
  `pageSize` по умолчанию 20, максимум 100.
- **Порядок — по фактическому моменту покупки убыванию.** Ключ сортировки —
  `PurchasedAt`, а при его отсутствии `CreatedAt`: покупка без распознанной даты
  всё равно должна быть видна, и её естественное место — момент сохранения.
  Дальше сортировка добивается по `CreatedAt` и `Id`, чтобы страницы были
  стабильны.
- **Диапазон дат применяется только к `PurchasedAt`,** обе границы включительно.
  Как только задана хотя бы одна граница, покупки без распознанной даты из
  выдачи уходят. Это отличается от ключа сортировки намеренно: пользователь,
  фильтрующий по периоду, спрашивает про дату покупки, а не про дату сохранения.
- **Фильтрация по статусу и тексту выполняется над прикладным слоем.**
  `Warnings` вычисляются в `PurchaseDraftService` из текущего снимка, а поиск по
  тексту уже с UI-1 работает in-memory, потому что case folding SQLite
  ASCII-центрично и ломает русские и польские названия. Поэтому репозиторий
  отдаёт ограниченное окно кандидатов (1000 записей), отфильтрованных по дате и
  уже отсортированных, а текст/статус/страница применяются выше. Если окно
  исчерпано, ответ содержит `truncated: true`, и лента честно сообщает об этом
  пользователю. Ограничение исчезнет вместе с переездом на PostgreSQL.
- **Активные чеки остались отдельной секцией над лентой.** Слияние их в ленту
  было бы враньём: незавершённый чек — это ещё не покупка, у него нет ни
  итоговой суммы, ни позиций. Секция теперь показывает только чеки, требующие
  внимания или работы (`uploaded`, `queued`, `processing`, `ready`, `failed`), и
  скрывается целиком, когда таких нет. Сохранённые чеки из неё убраны: они уже
  представлены в ленте как покупки. Polling, восстановление по stable URL и
  одноразовые in-app уведомления из UI-2 не изменялись.
- **Пикер периода — нативные `input type="date"`.** `@mantine/dates` не входит в
  зависимости проекта, а нативные поля дают локализованный формат, клавиатурную
  доступность и мобильный date picker без новых пакетов. **Новых npm-зависимостей
  в этом срезе нет.**

## Backend

### Прикладной слой

`PurchaseFeed.cs` вводит `PurchaseReviewStatus` (`All`, `NeedsAttention`,
`Reviewed`), запрос `PurchaseFeedQuery` и страницу `PurchaseFeedPage`
(`Items`, `Page`, `PageSize`, `TotalCount`, `HasMore`, `Truncated`).

`IPurchaseDraftService.GetFeedAsync` валидирует запрос и возвращает страницу.
Ошибки валидации — `ArgumentException`, который существующий
`ApiExceptionHandler` уже отдаёт как `400 Bad Request`:

- `q` длиннее 200 символов;
- `page` меньше 1;
- `pageSize` вне диапазона 1…100;
- `from` позже `to`.

Прежний `SearchAsync` сохранён без изменений: им пользуется MCP-инструмент
`search_purchases`, и его контракт «10 последних совпадений» менять не нужно.

### Персистентность

`IPurchaseDraftRepository.ListFeedCandidatesAsync` — единственная новая точка на
границе персистентности. Фильтр по датам, сортировка и ограничение окна
выполняются в SQL; EF Core корректно транслирует `PurchasedAt ?? CreatedAt` для
хранимых как `long` значений. **Миграций нет: схема БД не изменилась.**

### REST-контракт

`GET /api/purchases`

| Параметр | Значение по умолчанию | Смысл |
|---|---|---|
| `q` | — | свободный текст по магазину и названиям позиций, до 200 символов |
| `from` | — | нижняя включительная граница `PurchasedAt` |
| `to` | — | верхняя включительная граница `PurchasedAt` |
| `status` | `all` | `all`, `needsAttention` или `reviewed` |
| `page` | `1` | номер страницы |
| `pageSize` | `20` | размер страницы, максимум 100 |

Ответ — объект, а не массив (это breaking change относительно UI-2):

```json
{
  "items": [ { "id": "…", "merchantName": "Lidl", "purchasedAt": "…",
               "currency": "PLN", "receiptTotal": 152.90,
               "createdAt": "…", "updatedAt": "…",
               "items": [ … ], "warnings": [ … ] } ],
  "page": 1, "pageSize": 20, "totalCount": 42,
  "hasMore": true, "truncated": false
}
```

Неизвестный `status` даёт `400` с понятным `detail`. Остальные endpoint-ы
чеков и покупок не изменялись.

## Frontend

- `src/features/purchases/PurchaseFeed.tsx` — презентационный компонент ленты:
  панель фильтров, список карточек, состояния loading, error, «покупок ещё нет»
  и «под фильтры ничего не подходит», кнопка «Показать ещё» и предупреждение об
  усечённом окне. Компонент не знает про сеть и полностью управляем props.
- `src/features/purchases/PurchaseFeedSection.tsx` — контейнер на
  `useInfiniteQuery`. Дебаунсится только текстовый поиск (250 мс): выбор даты и
  статуса — осознанные одиночные действия и должны срабатывать сразу. Смена
  любого фильтра сбрасывает накопленные страницы, потому что фильтры входят в
  `queryKey`.
- `src/features/purchases/PurchasesPage.tsx` — страница `/purchases`,
  переиспользующая ту же ленту. Прежняя `HistoryPage` с собственным
  `useEffect`-поиском и `<details>`-карточками удалена вместе со своими строками
  локализации.
- `src/features/home/HomePage.tsx` — секция чеков в работе плюс та же лента.
- `src/api/client.ts` — `getPurchaseFeed`. Локальные календарные дни из полей
  фильтра расширяются до полных суток и уходят на сервер как инстанты:
  `from` → начало дня, `to` → конец дня по локальному времени пользователя.

Статус проверки в карточке отображается существующим `StatusBadge`
(`needsAttention` / `verified`) — новых визуальных примитивов не вводилось.
Все новые строки есть на русском и английском, включая правильные
множественные формы для количества покупок и позиций.

Новые .NET-тесты (`tests/PurchaseMemory.IntegrationTests/PurchaseFeedTests.cs`)
покрывают порядок и корректность страниц, fallback на `CreatedAt` для покупок
без даты, включительный диапазон дат с исключением покупок без даты, фильтр по
статусу проверки, комбинацию текст + период + статус по AND, сохранившийся
Unicode-поиск по магазину и позициям рядом с фильтрами и отказ на некорректных

Новые frontend-тесты покрывают содержимое карточки и статус проверки, оба
различных empty state, loading и error, передачу каждого фильтра одним
callback, «Показать ещё», английскую локализацию, а также — на уровне
контейнера — точные query-параметры первого запроса, немедленный запрос при
смене статуса и дат, дебаунс текста, дозагрузку второй страницы и текст ошибки.

Дополнительно лента проверена вручную на реальной dev-базе: 9 сохранённых
покупок, корректный порядок, статусы, суммы и количество позиций; `400` на
неизвестном `status`, перевёрнутом диапазоне и `pageSize=999`.

### npm audit

`npm audit` сообщает о 3 транзитивных уязвимостях (`nanoid` и `postcss` через
`vite`, `undici` через `jsdom`); при `--omit=dev` остаётся 2. **Ни одна из них
не связана с этим срезом: новых зависимостей не добавлялось, прямые версии не
менялись.** Это дрейф базы advisory с 3 августа. Все три чинятся обновлением
только транзитивных версий в `package-lock.json` и не требуют смены закреплённых
прямых версий, но это изменение выходит за рамки согласованного среза и
предлагается отдельно.

## Ограничения

- Лента просматривает ограниченное окно в 1000 записей после фильтра по датам;
  при его исчерпании ответ помечается `truncated`, а UI сообщает об этом.
  Ограничение снимается переездом на PostgreSQL с серверным поиском.
- Статус проверки бинарный и выводится только из расхождения суммы строк с
  итогом. Привязка `Needs attention` к конкретным полям и позициям — следующий
  срез UI-3.
- Редактирование сохранённой покупки из ленты недоступно: карточка только
  показывает предупреждения. Полноценный редактор и audit trail — будущие срезы.
- Сеть/филиал магазина, участник домохозяйства, категория товара и признак
  промо в фильтрах отсутствуют: соответствующих доменных полей ещё нет.
- Раздел `/needs-attention` остаётся placeholder-ом; фильтр «Нужно проверить»
  живёт внутри ленты.
- Ответ `GET /api/purchases` сменил форму с массива на объект страницы. Внешних
  потребителей, кроме этого фронтенда, у него нет; MCP-инструмент
  `search_purchases` использует прикладной сервис напрямую и не затронут.

## Как открыть

```bash
./scripts/run-local.sh
```

Открыть `http://127.0.0.1:5099`, затем:

- `/` — чеки в работе и лента покупок с фильтрами;
- `/purchases` — та же лента отдельной страницей;
- `/purchases/new` и `/receipts/{id}` — поток UI-2 без изменений.

Для UI Lab:

```bash
cd src/PurchaseMemory.Web
npm run storybook
```

Открыть раздел `Purchase Memory / PurchaseFeed / Production`.
