# Итерация 1 — проверка жизнеспособности через MCP

Дата плана: 13 июля 2026  
Тип итерации: одноразовый технический и продуктовый spike  
Главный принцип: сделать только то, что необходимо для ответа «удобно ли добавлять и находить покупки через чат без собственного UI?»

Статус на 13 июля 2026: **локальный backend и MCP smoke-test готовы; внешний tunnel и ручной тест с тремя чеками в Claude Mobile ещё не проводились**.

## 1. Проверяемая гипотеза

Пользователь может с телефона:

1. приложить фотографию чека в Claude;
2. попросить сохранить покупку;
3. позволить Claude распознать чек и вызвать наш MCP tool;
4. исправить ошибку обычным сообщением;
5. в новом разговоре найти сохранённую покупку по магазину или названию позиции.

В этой итерации **модель клиента распознаёт фотографию**. Backend не получает и не хранит исходное изображение, не вызывает AI API и не выполняет собственный OCR.

## 2. Основной клиент

Основной проверочный клиент — **Claude Free + remote MCP custom connector**.

Почему:

- custom remote MCP доступен на бесплатном тарифе;
- Free-пользователь может подключить один собственный connector;
- connector работает в web, desktop и mobile;
- один и тот же MCP URL смогут позже подключить два пользователя;
- это самый прямой тест исходной идеи без собственного UI.

Первоначальную настройку connector удобнее сделать через web, а основной end-to-end тест провести с телефона.

**Необязательный бонус после успешного теста:** подключить тот же endpoint к ChatGPT Plus в developer mode и повторить один чек. Это не является критерием завершения итерации.

## 3. Единственный сквозной сценарий

```text
Фото чека в Claude Mobile
        ↓
Claude распознаёт видимые поля
        ↓
MCP: create_purchase_draft
        ↓
C# backend сохраняет данные в SQLite
        ↓
Пользователь исправляет ошибку
        ↓
MCP: update_purchase_draft
        ↓
Новый чат: «Где я покупал X?»
        ↓
MCP: search_purchases
```

Если этот сценарий неудобен или нестабилен, бессмысленно пока строить каталог, PostgreSQL, video pipeline и собственный OCR.

## 4. Минимальный технический состав

### Backend

- C#;
- ASP.NET Core Minimal API;
- актуальная LTS .NET на момент реализации;
- официальный MCP C# SDK;
- MCP Streamable HTTP endpoint `/mcp`;
- health endpoint `/health`;
- один SQLite-файл в `./data/purchases.db`;
- запуск обычной командой `dotnet run`, без Docker.

### Почему SQLite и без Docker

В этой итерации проверяется взаимодействие «фото → модель → tool → сохранение → поиск», а не инфраструктура. SQLite даст настоящую персистентность и поиск, но уберёт настройку контейнеров и PostgreSQL.

Если гипотеза подтвердится, во второй итерации SQLite можно выбросить и заменить PostgreSQL. Это сознательный disposable prototype.

### Доступ извне

- временный Cloudflare Tunnel/ngrok до локального ASP.NET Core;
- tunnel включён только во время теста;
- Mac должен оставаться включённым;
- в этой итерации нет полноценного OAuth.

Из-за отсутствия OAuth использовать только синтетические либо обезличенные чеки без платёжных, персональных и скидочных идентификаторов. Случайный URL tunnel не считать настоящей защитой.

## 5. Минимальная модель данных

### `PurchaseDraft`

- `id`;
- `merchantName` — nullable;
- `purchasedAt` — nullable;
- `currency` — nullable;
- `receiptTotal` — nullable;
- `createdAt`;
- `updatedAt`.

### `PurchaseItem`

- `id`;
- `purchaseDraftId`;
- `name` — как его прочитала модель;
- `quantity` — nullable;
- `unit` — nullable;
- `unitPrice` — nullable;
- `lineTotal` — nullable.

Деньги сохраняются как decimal. Сложной нормализации, категорий, товаров, штрихкодов, адресов магазинов и оценок пока нет.

## 6. Ровно три MCP-инструмента

### `create_purchase_draft`

Назначение: сохранить распознанный чек.

Вход:

- магазин;
- дата/время;
- валюта;
- итог;
- массив позиций.

Ответ:

- созданный `purchaseId`;
- сохранённые поля;
- простые предупреждения, например расхождение суммы строк с итогом.

Описание tool должно явно говорить модели:

- вызывать его только после чтения чека;
- не выдумывать невидимые значения;
- неизвестные поля передавать как `null`;
- всегда сохранять оригинальные названия позиций на языке чека.

### `update_purchase_draft`

Назначение: исправить поля покупки или заменить позиции после уточнения пользователя.

Вход:

- `purchaseId`;
- поля, которые нужно изменить;
- при необходимости полный обновлённый массив позиций.

Ответ: полный актуальный черновик.

### `search_purchases`

Назначение: найти сохранённые покупки.

Вход:

- одна текстовая строка запроса.

Поиск в первой версии:

- нечувствительное к регистру вхождение в название магазина;
- нечувствительное к регистру вхождение в название позиции;
- пустой запрос возвращает последние 10 записей.

Ответ: не более 10 покупок с датой, магазином, итогом и найденными позициями.

## 7. Что реализовать

1. Создать solution и небольшой набор проектов по слоям вокруг одного ASP.NET Core процесса.
2. Подключить официальный MCP C# SDK и SQLite.
3. Автоматически создавать простую схему SQLite при запуске; полноценные migrations пока не нужны.
4. Реализовать repository/application service для create, update и search.
5. Обернуть эти операции тремя MCP tools.
6. Добавить `/health`.
7. Добавить структурированные логи без содержимого всего чека.
8. Написать минимальные автоматические тесты.
9. Проверить MCP локально через MCP Inspector или другой MCP-клиент.
10. Открыть временный tunnel.
11. Подключить URL в Claude web как custom connector.
12. Провести тест с телефона.

## 8. Минимальные автоматические тесты

Достаточно трёх интеграционных тестов с временным SQLite-файлом:

1. создание черновика сохраняет покупку и позиции;
2. обновление действительно меняет данные;
3. поиск находит запись по магазину и по позиции.

Также нужен один ручной MCP smoke-test: клиент видит все три инструмента и успешно вызывает каждый из них.

## 9. Тестовый набор

Использовать три обезличенных чека:

1. короткий и хорошо читаемый;
2. длиннее, с количеством/весом или скидкой;
3. менее качественный либо на другом ожидаемом языке.

Для каждого заранее вручную записать эталон:

- магазин;
- дату;
- итог;
- список реальных позиций.

Фото в backend не загружаются и после теста не сохраняются проектом.

## 10. Ручной сценарий проверки

Для каждого чека:

1. Открыть новый разговор в Claude Mobile с включённым connector.
2. Приложить фотографию.
3. Написать: «Прочитай этот чек и сохрани покупку через Purchase Memory. Не выдумывай неразборчивые поля».
4. Проверить, вызван ли `create_purchase_draft`.
5. Сравнить ответ с эталоном.
6. Намеренно или по фактической ошибке написать исправление: «Во второй позиции должно быть …».
7. Проверить вызов `update_purchase_draft` и повторно получить данные.
8. Начать новый разговор.
9. Спросить: «Где и когда я покупал …?».
10. Проверить вызов `search_purchases` и корректность ответа.

## 11. Критерии успеха

Итерация считается успешной, если:

- мобильный Claude подключается к локальному backend через remote MCP;
- модель самостоятельно выбирает нужный tool;
- минимум 2 из 3 чеков сохраняются без выдуманных позиций;
- на этих чеках верно определены магазин и итог, если они читаемы;
- не менее 80% читаемых строк перенесены с узнаваемым названием;
- исправление естественным языком приводит к `update_purchase_draft`;
- поиск из нового разговора находит запись по названию магазина или позиции;
- весь сценарий субъективно проще, чем ручное заполнение формы.

Последний критерий важнее красивой архитектуры.

## 12. Интерпретация результата

### Успех

Продолжаем с PostgreSQL, авторизацией и сохранением оригинальных изображений. MCP остаётся основным каналом.

### Частичный успех

Распознавание хорошее, но Claude плохо выбирает tools или формирует параметры. Сначала улучшаем названия, описания и JSON Schema. Затем сравниваем тот же flow с ChatGPT Plus/Custom GPT Actions.

### Неуспех из-за клиента

Фото распознаётся, но клиент не может стабильно вызвать tool с большим массивом позиций. Пробуем Custom GPT Actions. Backend и схема данных сохраняют ценность.

### Неуспех из-за распознавания

Переходим к backend-owned upload и отдельному vision extractor. Это означает, что чат пригоден как интерфейс управления, но не как место распознавания.

### Неудобно исправлять в чате

Добавляем во второй итерации единственный маленький экран review. Полноценное приложение всё ещё не требуется.

## 13. Явно не входит в итерацию

- PostgreSQL;
- Docker и Docker Compose;
- пользователи и семейные аккаунты;
- OAuth;
- публикация ChatGPT App;
- Custom GPT;
- OpenAI/Anthropic API key;
- Ollama;
- backend OCR/vision;
- загрузка и хранение фотографий;
- каталог товаров и сопоставление дублей;
- оценки «понравилось/не понравилось»;
- адреса магазинов;
- подтверждение окончательной покупки;
- отчёты и аналитика;
- embeddings;
- видео;
- production deployment.

Если в ходе работы возникает желание добавить что-то из списка, это записывается в backlog и не делается в этой итерации.

## 14. Результаты итерации

В репозитории должны остаться:

- запускаемый C# MCP server;
- SQLite schema/initialization;
- три MCP tools;
- три автоматических теста;
- README с командами запуска и подключения;
- заполненный `РЕЗУЛЬТАТЫ_ИТЕРАЦИИ_1.md` с таблицей по трём чекам;
- решение: продолжать MCP-first, пробовать Actions либо переходить к минимальному upload/review UI.

Автоматизированная техническая часть выполнена. Таблица пока намеренно не заполнена результатами реальных чеков: это следующий ручной продуктовый эксперимент, а не то, что можно честно имитировать автоматическим тестом.

## 15. Следующее действие

1. Подобрать три обезличенных чека.
2. Запустить backend по README.
3. Открыть временный tunnel только на время теста.
4. Подключить `/mcp` как custom connector через Claude web.
5. Провести сценарий с телефона и заполнить `РЕЗУЛЬТАТЫ_ИТЕРАЦИИ_1.md`.

Новых архитектурных решений до этого теста не требуется.
