# UI-4 «Товары» — разбивка на этапы

Согласовано с владельцем 13 сентября 2026. Заменяет трактовку UI-4 из
`ДИЗАЙН_БРИФ_И_UI_СТЕК.md` как одного монолитного этапа: содержание то же,
но разбито на части, каждая из которых имеет самостоятельную ценность и
отдельно проверяется по `AGENTS.md`.

## Почему разбивка

В брифе UI-4 описан как каталог + карточка продукта + история цен +
категории/теги + впечатления двух пользователей + barcode. В текущем коде
у этого есть две отсутствующие предпосылки:

- `PurchaseItem` хранит только сырой текст с чека, сопоставление с каталогом
  в коде явно отложено — значит «Ser Gouda 250g» и «SER GOUDA 250G» сейчас
  разные строки, и историю цены построить не на чем;
- пользователей в системе нет вообще (ни `UserId`, ни аутентификации), а
  впечатления по продуктовой сессии персональны для каждого из двух
  участников household.

Поэтому сначала доменное ядро, затем видимая ценность, затем аккаунты.

## Этап 1 — ядро нормализации товаров (готов, 13 сентября 2026)

Сделан и принят независимым review — см.
`РЕЗУЛЬТАТЫ_UI_4_ЭТАП_1_КАТАЛОГ_ТОВАРОВ.md`.


Каноническая сущность продукта, алиасы «магазин + сырое название → продукт»,
детерминированное сопоставление позиций при сохранении покупки и очередь
неуверенных сопоставлений. Без UI, без LLM, без категорий и впечатлений.

Ценность: с этого момента новые покупки накапливаются уже в пригодном для
истории цен виде.

## Этап 2 — карточка продукта и история цены (готов, 19 сентября 2026)

Сделан и принят независимым review в три прохода — см.
`РЕЗУЛЬТАТЫ_UI_4_ЭТАП_2_КАРТОЧКА_ТОВАРА.md`.

`/products`: каталог с поиском, карточка продукта — последняя покупка и
магазин, минимальная/средняя/последняя цена, график цены, частота покупок.
Ради этого продукт и задумывался («сколько этот товар стоил в прошлый раз»).

Поиск работает и по написанию с чека, а не только по каноническому названию.
Цены сравниваются только внутри пары «валюта + единица измерения», товар,
купленный и на вес, и поштучно, даёт две отдельные серии. «Покупка» везде
означает поездку в магазин: две одинаковые позиции в одном чеке — одна
покупка, и средняя цена взвешена так же.

Ограничение, снятое не здесь: на реальной истории владельца этап не проверялся,
потому что миграция каталога на боевую базу ещё не применялась — см.
`РЕЗУЛЬТАТЫ_ПРОВЕРКА_МИГРАЦИИ_НА_КОПИИ_БАЗЫ.md`.

## Этап 3 — очередь исправлений

`/needs-attention`: разбор неуверенных сопоставлений из этапа 1 плюс уже
существующие issue-покупки. Счётчик на главной.

## Этап 4 — household-аккаунты и впечатления

Два аккаунта, атрибуция покупок (`CreatedByUserId` / `PurchasedByUserId`),
личные оценки и заметки по продукту. Единственный этап, требующий
аутентификации, поэтому вынесен отдельно.

## Затем — UI-5 «Аналитика»

Без изменений относительно брифа: считает SQL/аналитический слой, LLM только
превращает вопрос в ограниченный план запроса.

## Не входит

Категории/теги, barcode и фото упаковки, «продаваемый вариант → редакция
упаковки», семантический поиск — после этапа 2, по отдельному решению
владельца. Ранее отклонённое (остатки, сроки годности, экспорт, offline-
захват, рестораны, тёмная тема) не пересматривается.
