# Локальные модели для распознавания — приоритетный трек (Track B)

Статус: **владелец подтвердил (30 августа 2026) цель — перевести
распознавание чеков полностью на локальные модели на этом Mac**, отказавшись
от текущего облачного OpenAI/Ollama hybrid pipeline. Это по-прежнему требует
отдельного task brief и явного «делай» перед реализацией по правилам
`AGENTS.md` — здесь зафиксировано решение о приоритете, а не разрешение на
код.

## Результат первого сравнения (Track B, 30 августа 2026)

На 20 реальных чеках владельца (см.
`РЕЗУЛЬТАТЫ_ТРЕК_B_СРАВНЕНИЕ_МОДЕЛЕЙ.md`) прямой vision-LLM (`qwen3-vl:8b-instruct`)
уверенно обошёл двухступенчатый пайплайн Apple OCR → текстовая LLM: сумма
чека верна в 20/20 против 18/20, число позиций — в 15/20 против 4/20.
Двухступенчатый вариант систематически теряет позиции из-за того, что Apple
Vision склеивает колонки наклонённого чека в одну строку без координат.
Аргумент про скорость двухступенчатого пайплайна не подтвердился (паритет,
~17-18 сек/чек).

**Следствие: двухступенчатый пайплайн (раздел ниже) снят с рассмотрения как
основной путь.** Дальнейшая работа должна отталкиваться от прямого
vision-LLM (`qwen3-vl:8b-instruct`, не `:8b` — тег `:8b` оказался
thinking-сборкой, зацикливается и возвращает пустые ответы на плотных чеках)
с постобработкой кодом:
- сверка `sum(line_total)` с `total`;
- канонизация имени сети через уже существующий `canonicalMerchantName` из
  `src/PurchaseMemory.AppleIntelligence`;
- вычитание строк `OPUST/RABAT` из позиций.

Известные ограничения сравнения (не переоценивать уверенность): выборка — 18
уникальных чеков, а не 20 (два дубля); Biedronka/Kaufland/Dino/Aldi не
представлены; немецкий чек прогонялся с польским языком OCR по ошибке;
диакритика ненадёжна у обоих подходов (~63%) — для будущего поиска её нужно
нормализовать, а не полагаться на точное распознавание.

## Зафиксированные рамки (29-30 августа 2026)

Владелец сузил задачу до конкретного MVP-контекста — это не отменяет пункты
ниже, но снимает часть развилок:

- **Только фото бумажных чеков.** Email/PDF-чеки интернет-магазинов вне
  скоупа — не нужен отдельный текстовый парсер для них сейчас.
- **Скорость не критична.** Продукт — личное использование (владелец + жена),
  не нужен near-instant результат «пока чек ещё в руках». Это снимает
  главный аргумент за двухступенчатый пайплайн (Apple OCR → LLM) — экономия
  времени была его основным плюсом. Двухступенчатый вариант остаётся
  жизнеспособным по языкам, но теперь не имеет явного преимущества перед
  прямым vision-LLM (Qwen3-VL) запросом, кроме нагрузки на Neural Engine —
  сравнивать всё равно стоит на образцах, но приоритет смещается на точность,
  а не на скорость.
- **Только Mac, только этап разработки.** Никакого переноса на телефон пока
  не рассматриваем; кроссплатформенность (аргумент против Apple Vision) сейчас
  не блокер. Мобильное приложение — отдельная будущая тема, не влияет на
  выбор модели сейчас.
- **Семантический поиск отложен.** Сейчас цель — только наполнение БД и выбор
  модели распознавания. Векторный поиск (BGE-M3 и всё, что ниже в разделе
  «Поиск по смыслу») переносится к UI-5 «Аналитика», как и предполагалось.
- **Без облачного fallback.** На этапе разработки всё остаётся on-device —
  решение про облако для сложных чеков отложено на потом, не блокирует MVP.

Из этого следует уточнённый фокус первой тест-стадии: сравнить на реальных
польских чеках **только точность** распознавания (Apple Vision OCR → Ollama
LLM для структурирования **против** прямого Qwen3-VL vision→JSON), без учёта
скорости и без встраивания векторного поиска.

## Вопрос, с которого начали

Может ли Apple Vision (`VNRecognizeTextRequest`) распознавать польский текст, и
стоит ли использовать его как быстрый первый проход перед тяжёлой vision-LLM
в Ollama?

**Проверено напрямую на реальном Mac** (не по документации — вызовом
`VNRecognizeTextRequest().supportedRecognitionLanguages()`):

- уровень `.accurate`: `pl-PL` — **есть**, `ru-RU` — **есть** (полный список:
  en-US, fr-FR, it-IT, de-DE, es-ES, pt-BR, zh-Hans, zh-Hant, yue-Hans,
  yue-Hant, ko-KR, ja-JP, ru-RU, uk-UA, th-TH, vi-VT, ar-SA, ars-SA, tr-TR,
  id-ID, cs-CZ, da-DK, nl-NL, no-NO, nn-NO, nb-NO, ms-MY, **pl-PL**, ro-RO,
  sv-SE);
- уровень `.fast`: только 6 языков (en/fr/it/de/es/pt) — **pl-PL и ru-RU
  недоступны**, для чеков обязателен `.accurate`.

Вывод: Apple Vision technically тянет оба нужных продукту языка на нужном
уровне точности. Двухступенчатый пайплайн ниже жизнеспособен по языковому
покрытию — остаётся вопрос практической точности на реальных чеках
(диакритика, мелкий шрифт термопринтера), который проверяется только на
образцах, не списком языков.

## Идея двухступенчатого пайплайна (если Apple Vision тянет польский)

```
Фото чека
   │
   ▼
Apple Vision OCR (Neural Engine, локально, ~бесплатно, миллисекунды)
   │  сырой текст построчно, без структуры
   ▼
Ollama LLM (текстовая, не vision-модель) — группировка по смыслу,
извлечение позиций/цен/скидок, структурирование в JSON
```

Плюсы:
- OCR-проход почти бесплатен по времени/энергии — не грузит GPU/Neural Engine
  тяжёлой vision-LLM на сырых пикселях;
- текстовая LLM для структурирования может быть заметно меньше и быстрее, чем
  vision-LLM того же качества (не нужно "видеть" изображение — только понимать
  текст);
- уже есть готовый compatibility-путь через Apple sidecar в проекте, есть куда
  встраивать.

Риски/минусы:
- Apple OCR не размечает пространственную структуру чека (колонки, отступы) так
  явно, как это может сделать vision-LLM, глядя на изображение целиком — для
  многоколоночных чеков группировка по смыслу может быть сложнее с чистым
  текстом без координат bounding box (хотя Vision framework их отдаёт — можно
  передавать LLM);
- если Apple Vision не тянет `pl-PL` вообще — вариант отпадает для основного
  сценария (продукт ориентирован на польские чеки), и Qwen3-VL/InternVL как
  прямой vision→JSON остаётся единственным путём;
- два прохода вместо одного — усложнение пайплайна и ещё одна точка отказа,
  оправдано только если разница в скорости/стоимости действительно ощутима на
  практике, а не только в теории.

**Вывод:** сначала проверить факт поддержки `pl-PL` в Vision framework, потом
решать, стоит ли городить два прохода вместо одного vision-LLM запроса.

## Общая идея: две модели, а не одна

1. **Распознавание чека** (редко, тяжело) — vision-LLM или Apple OCR + text-LLM,
   см. выше. Кандидаты: `Qwen3-VL` (4B/8B, лучший OCR среди компактных моделей
   в 2026 по DocVQA/OCRBench) или `InternVL3.5-8B` как альтернатива — сравнить
   на реальных польских чеках, включая диакритику (ą, ć, ę, ł, ń, ó, ś, ź, ż).
2. **Поиск по смыслу** (часто, легко) — эмбеддинг-модель, отдельная от
   распознавания. Кандидат: `BGE-M3` (100+ языков, единое пространство
   RU/PL/EN, до 8192 токенов, есть в Ollama). Вектор считается один раз при
   сохранении покупки/позиции, дальше используется для произвольных запросов
   пользователя ("сколько потратили на кофе в марте", "покажи все покупки в
   Lidl со скидкой").

Это разделение соответствует тому, как в проекте уже разделены контракты
recognition (`IReceiptExtractor`) и поиск (`IPurchaseDraftService.SearchAsync`
/ будущий `GetFeedAsync`) — поиск по смыслу логично добавлять отдельным
сервисом поверх векторного индекса, не трогая recognition pipeline.

Хранилище векторов: для домашнего объёма данных достаточно `sqlite-vec`
(держит текущий локальный SQLite-путь) или `pgvector`, если/когда проект
переедет на PostgreSQL (уже упоминается как будущий шаг в
`РЕЗУЛЬТАТЫ_UI_3_ЛЕНТА.md` как решение проблемы ограниченного окна ленты).
