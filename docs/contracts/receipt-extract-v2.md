# Контракт `receipt.extract` v2 — дельта к v1

v2 не отменяет [`receipt.extract` v1](receipt-extract-v1.md): все правила
значений, ошибки, retry/repair-политика и требование ручного review остаются в
силе. Нормативная schema — [`receipt-extract-result-v2.schema.json`](receipt-extract-result-v2.schema.json).

> **Примечание (Track B, диагностика пустых ответов).** Схема ниже (и её
> рантайм-копия в `ReceiptAnalysisContract.JsonSchema`) инлайнит `boundingBox`
> в оба места, где он используется, вместо объявления его один раз под
> `$defs` и ссылки на него через `$ref`, как было раньше. Набор полей и правил
> валидации не изменился — изменилась только форма самой JSON Schema.
> Причина: `qwen3-vl:8b-instruct` (production vision-модель, см. раздел ниже)
> в связке с `$ref` на `$defs/boundingBox` в schema-режиме структурированного
> вывода детерминированно возвращал пустой результат (`merchantName: null,
> items: [], receiptTotal: null`) независимо от содержимого чека; после
> инлайнинга та же модель на тех же и на дополнительных чеках стабильно
> возвращает данные. Публичный wire-контракт (`ReceiptExtractionResult` и
> набор полей ответа) не менялся.

## Идентификаторы версий

| Сущность | Значение v2 |
|---|---|
| Intent | `receipt.extract` |
| Prompt | `receipt.extract.prompt.v2` |
| Schema | `receipt.extract.schema.v2` |

## Что добавлено

Единственное изменение — необязательная привязка распознанного значения к месту
на фотографии чека:

- `items[].boundingBox` — рамка строки позиции;
- `receiptTotalBoundingBox` — рамка напечатанного итога.

Рамка — объект `{ "x", "y", "width", "height" }` в **относительных долях**
размера изображения (0.0–1.0), где `x`/`y` — левый верхний угол. Пиксели не
используются: снимки с разных устройств имеют разное разрешение.

Оба поля обязательны в JSON (strict structured output), но их значением может
быть `null`. Модель обязана возвращать `null`, если не уверена в координатах:
неверная рамка хуже отсутствующей.

## Валидация рамки

Рамка проходит доменную валидацию (`PurchaseMemory.Domain.Receipts.BoundingBox`)
и при любом нарушении молча становится `null` — распознанные текстовые значения
при этом сохраняются, а UI показывает полное фото:

- отсутствует любая из четырёх координат или значение не является числом;
- значение не конечное (`NaN`, бесконечность);
- `x` или `y` меньше нуля, либо рамка выходит за пределы кадра;
- `width` <= 0.01 или `height` <= 0.002 (нечитаемая полоска);
- площадь рамки больше 0.9 кадра (рамка «на весь чек» не указывает на строку).

Допуск на округление модели — 0.005 по каждой границе.

## Совместимость

Парсер принимает ответ и без полей рамки: они входят в набор необязательных
свойств, поэтому ответ по schema v1 остаётся валидным. Клиентские значения
(review-запрос PWA) проходят ту же валидацию, что и вывод модели.

## Track B: постобработка на уровне кода (без изменения wire-контракта)

После перехода основного production-пайплайна распознавания на прямой
vision-LLM (`ollama`, режим `Vision`, модель `qwen3-vl:8b-instruct`, без
OCR-прохода) добавлена детерминированная постобработка результата
экстракции в `ReceiptExtractorRouter` (см.
`PurchaseMemory.Application.Receipts.ReceiptExtractionPostprocessor`),
применяемая одинаково ко всем пайплайнам (`apple`, `ollama`, `openai`):

- **Канонизация названия магазина** — известные варианты названия сети
  (Biedronka, Lidl, Auchan, Carrefour, Kaufland, Żabka, Netto, Dino, Aldi,
  Tesco, Rossmann, Stokrotka, Intermarché) приводятся к одному каноническому
  бренду через регистронезависимое сравнение подстрок. Неизвестные названия
  возвращаются без изменений.
- **Отсечение строк скидок** — позиции `items[]`, чьё `name` содержит маркер
  скидки/промо (`OPUST`, `RABAT`, `UPUST`, `PROMOCJA`, `ZNIŻKA`, `DISCOUNT`,
  `SKONTO`), удаляются из списка позиций до сохранения результата: модели не
  всегда соблюдают инструкцию промпта не включать такие строки как товар.

Это **не меняет форму контракта**: набор полей `ReceiptExtractionResult` и
JSON schema v2 остаются прежними, оба шага — чисто внутренняя очистка данных
перед сохранением. Флаг несовпадения суммы строк с итогом чека — это
отдельный, уже существовавший до Track B механизм: он вычисляется в
`ReceiptProcessingService.CreateWarnings` (допуск 0.01 денежной единицы) и
попадает в список `warnings` в `ReceiptCaptureView`, а не в
`ReceiptExtractionResult`; Track B не вводит новое поле для этого — только
переиспользует существующий путь.
