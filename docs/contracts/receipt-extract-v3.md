# Контракт `receipt.extract` v3 — дельта к v2

v3 не отменяет [v2](receipt-extract-v2.md) и [v1](receipt-extract-v1.md): правила
значений, ошибки, retry/repair и ручной review остаются. Нормативная schema —
[`receipt-extract-result-v3.schema.json`](receipt-extract-result-v3.schema.json),
рантайм-копия — `ReceiptAnalysisContract.JsonSchema`.

## Идентификаторы версий

| Сущность | Значение v3 |
|---|---|
| Intent | `receipt.extract` |
| Prompt | `receipt.extract.prompt.v3` (инструкция v9, польский) |
| Schema | `receipt.extract.schema.v3` |

## Что изменилось

- `rawLines` — массив строк: модель сначала переписывает каждую напечатанную
  строку секции позиций, потом строит `items`. Это не данные покупки: парсер
  принимает поле (в том числе его отсутствие — для старых ответов) и
  отбрасывает его; в БД и лог оно не попадает.
- `items[].lineTotal` может быть отрицательным: скидка (OPUST, RABAT …) — это
  отдельная позиция сразу после своего товара, `quantity` и `unitPrice` = null,
  `lineTotal` < 0. Цена товара остаётся напечатанной, скидка из неё не
  вычитается. Отрицательные `quantity`, `unitPrice`, `receiptTotal` —
  по-прежнему ошибка.

## Скидки после разбора

Общий постпроцессор помечает строку как скидку, если её сумма отрицательна или
имя содержит маркер скидки при отсутствии цены за единицу (положительная сумма
такой строки хранится со знаком минус). Скидка сохраняется строкой
`Kind = Discount` и `DiscountedItemPosition` = позиция ближайшего товара выше;
если товара выше нет — без привязки и с предупреждением. Привязка всегда
вычисляется из порядка строк, клиент её не задаёт. Скидка не создаёт товар
каталога и не участвует в сопоставлении и истории цен. Сумма строк (со знаком)
сравнивается с итогом чека.
