# Photo/barcode stage 5 «Найти по фото» — result

Level: Full (recognition). No migration. No paid calls: every test uses a fake
matcher or a fake transport; the benchmark was run only against a fake.
The feature is **off by default** (`ProductPhotoSearch:Enabled=false`).

## Done
- **API** `POST /api/products/find-by-photo` (multipart field `photo`, one
  JPEG/PNG/WebP ≤ 1.5 MB, same checks and request limit as «Название по фото»)
  → up to 3 matches `{productId, name, namePl, nameRu, brand, category,
  mainPhotoId, purchaseCount, lastPurchasedAt, confidence}` + `candidateCount`.
  `GET /api/products/find-by-photo/status` → `{enabled}` (free, for the button).
  Approved-user policy like all product endpoints (no households in this
  version: the catalog is the household's shared data).
- **Switch** `ProductPhotoSearch__Enabled` (default false in code and
  `appsettings.json`). Off → 503 `findByPhotoDisabled` before the upload is read;
  on without key / provider failure → 503 `findByPhotoUnavailable`.
- **Rate limit** own bucket `RateLimiting:FindByPhoto`, same shape as
  NameFromPhoto (20 burst, +1 / 180 s per user); 429 «Too many photo searches».
- **Candidates** (`ProductPhotoCandidateRepository`): all catalog products ranked
  by last purchase date (receipt date, else save time) desc, then purchase
  count, then never-bought products by `UpdatedAt`; cap
  `ProductPhotoSearch:MaximumCandidates` = 300 (validated 10–1000). Why: in the
  shop the photographed item is most likely something bought recently; 300 lines
  ≈ 12k input tokens keeps a search near $0.0015 on Haiku.
- **Matcher** `AnthropicProductPhotoMatcher` (Claude Haiku 5.5, effort Low, same
  Messages transport/key/logging style as the photo namer, no new SDK). Prompt:
  photo + list `pN | Polish | Russian | receipt | brand | category` (codes, not
  ids; `|` and line breaks in names neutralised; list is data). Rules: ≤3 matches
  best first, confidence high/medium/low, loose products by kind, empty list
  rather than a wrong match. Schema `{seen: string|null, matches:[{code,
  confidence∈high|medium|low}]}`. Unknown code, repeats, a 4th match, bad
  confidence are dropped and counted; the service re-checks ids against the
  candidate set. Thumbnails can later be sent as extra images next to codes
  (`ProductPhotoCandidate` is the extension point); not implemented.
- **Logging**: count of candidates/matches/rejected, ms, model, tokens, cost.
  Never the image, prompt, product names or key (tested on the log files).
- **UI**: «Найти по фото» under the scan camera (shown only when status is
  enabled) → phone camera (`capture=environment`) → photo shrunk by
  `photoForNaming` (~200 KB) → sheet «Похоже на это» with up to 3 rows (thumb,
  name, RU name, brand · confidence · last bought) and «Это он» per row → the
  barcode `FoundResult` summary (last purchase, how often, cheapest, rating,
  dislike/avoid) → «Открыть карточку товара». «Нет в списке» → search by name
  (tap opens the same summary) or «Новый товар» (creates and opens the card).
  Spinner, «server waking» note after 10 s, errors with «Попробовать ещё раз»
  (unavailable, 429, network), no retry for disabled/unreadable photo. One paid
  call per photo: the search is a React Query mutation sent once per photo id,
  so focus or a session refresh (`invalidateQueries()` in AuthGate) never
  repeats it; only «Попробовать ещё раз» or a new photo does. A product gone
  since the search says «Этого товара больше нет в каталоге» (no barcode wording).
  i18n ru/en, accessible labels («Это он: <name>»).
- **Help**: new topic «Найти по фото» (`find-by-photo`, ru+en, says it is
  approximate and the person confirms) + one pointer step in «Фото, штрихкод и
  скан в магазине»; `HelpLink` in the photo sheet.
- **Benchmark** `tools/PurchaseMemory.FindByPhotoBenchmark` (core linked into
  tests): refuses to run without a positive `--budget-usd` and for a model with
  no known price (`AnthropicPricing`, today only `claude-haiku-5-5`); stops
  before a call could cross the budget (first call assumed $0.005, then the most
  expensive so far; failures charged too; usage without a cost charged at a
  ceiling of $30 / $150 per M tokens); outputs top-1 / top-3, «not in list → empty» rate, mean
  ms, mean and total cost; per-photo CSV + `.summary.txt`.

## Estimated cost (computed, not measured)
Haiku 5.5 list price in the repo: $0.10 / M input, $0.50 / M output.
Input ≈ 450 prompt + 300 × ~40 list + ~1 050 image (1024×768) ≈ 13 500 tokens →
$0.00135; output ≈ 300 (low-effort thinking + JSON) → $0.00015. **≈ $0.0015 per
search**; worst case (4 000 output tokens) ≈ $0.0034. 30 photos ≈ $0.05.

## Limits
- Text-only candidates: the model never sees how the owner's products look; two
  similar loose products (tomato kinds, bread kinds) will often be «medium/low».
- Hit rate is unknown until the measurement; that is why the switch is off.
- Products beyond the 300 most recently bought are never offered.
- Benchmark candidates come from a file in catalog order (alphabetical when
  saved from `/api/products`), not the app's recency order; catalog pages have
  no category names. Same set when the catalog has ≤ 300 products.
- No prompt caching yet (the list is the same between searches; could cut cost).
- Not placed on Главная (only on the scan screen, reached from Главная and the
  Products tab barcode icon).

## How the owner prepares ~30 labelled photos
1. Put ~30 photos in a folder outside the repo, e.g. `~/Pictures/find-by-photo/`:
   ~10 loose vegetables/fruit, ~8 bread/bakery, ~7 packages, ~5 products never
   bought (for «none»). One product per photo, as you would shoot it in the shop.
2. `labels.csv` (UTF-8) in the same folder:
   ```
   file,expected
   IMG_0101.jpg,Pomidory malinowe
   IMG_0102.jpg,3f2a…-product-id
   IMG_0103.jpg,Chleb żytni;Chleb razowy
   IMG_0104.jpg,none
   ```
   `expected` = the product's Polish/Russian/receipt name exactly as in the app, or
   its id (from `/products/<id>`); `;` between several acceptable answers.
3. Candidates: the API needs the sign-in token, so a plain browser address does
   not work. In desktop Chrome/Safari open the app's «Товары» tab with developer
   tools → Network, scroll the list to the end, and «Save response» of each
   `/api/products?…` request as `page1.json`, `page2.json`, … into one folder,
   e.g. `~/Pictures/find-by-photo/candidates/` (or let the root agent prepare a
   JSON array `productId, receiptName, namePl, nameRu, brand, category`).
