# Purchase Memory — текущий контекст проекта

Короткая сводка для агентов. Обновляется root-агентом после этапов, меняющих
архитектуру или ключевые решения. Правила работы — в `AGENTS.md`.

## Что это

Учёт покупок по фото чеков для домохозяйства из двух человек в Польше.
Backend .NET 10 (`src/PurchaseMemory.Api`), frontend React 19 + TypeScript
(Vite, Storybook), опциональный Apple Vision sidecar (Swift) для локального OCR.
UI (с 13.10.2026): Ionic React 9 в режиме iOS на всех устройствах, React
Router 8 без `IonRouterOutlet`, графики — recharts; Mantine удалён
(`РЕЗУЛЬТАТЫ_IONIC.md`).

## Принятые решения

- **Распознавание чеков (с 11.10.2026):** основной путь — Anthropic
  `claude-haiku-5-5` (`ReceiptRecognition__Pipeline=anthropic`, ключ
  `ANTHROPIC_API_KEY`; `РЕЗУЛЬТАТЫ_HAIKU_ИНТЕГРАЦИЯ.md`), repair-повтор.
  Since 14.10.2026 the anthropic pipeline uses contract v4 "full-structured"
  (`ReceiptStructuredAnalysisContract`, effort Medium; items + separate
  discounts + totals, a box on every line, no rawLines) — byte-identical to
  `haiku-full-structured-medium` in `РЕЗУЛЬТАТЫ_СРАВНЕНИЕ_OCR.md` (≈ $0.0018 per
  receipt, ~12 s median, up to ~37 s). The parser maps discounts back to
  negative `Kind = Discount` rows after their item, so storage/UI are
  unchanged. Rollback is config only: `AnthropicReceiptContract=V3` +
  `AnthropicEffort=Low`. OpenAI/Ollama keep the shared contract v3 (schema v3
  without unsupported keywords for Claude).
  Запасной маршрут — `FallbackPipelines` = `openai` (`gpt-6-sol`, reasoning
  Low, ≈ $0.02 за чек), затем Ollama: при отказе модели, обрыве по лимиту,
  невалидном JSON после повтора, таймауте, 429/5xx/529 и при отсутствии ключа.
  Локальные модели и Apple-OCR остаются для экспериментов.
- **Скидки** хранятся отдельными строками (`Kind = Discount`) с привязкой к
  товару (вариант A).
- **Вход:** Supabase Auth (email-ссылка/код, Google и др.), новые
  пользователи ждут ручного одобрения владельцем в `public.app_users`.
  Локально без Supabase — `Auth__DevelopmentBypass=true`, только с loopback и
  никогда через туннели наружу.
- **Данные общие** для всех одобренных пользователей (без разделения на
  домохозяйства в этой версии).
- **Целевая инфраструктура:** Supabase Postgres + Supabase Storage для фото,
  бесплатный хостинг. Фото планируется сжимать (~2400 px по длинной стороне,
  JPEG 80–85), оригиналы хранить, пока хватает места.
- База: по умолчанию SQLite (`data/purchases.db`, бэкап в `data/backups/`
  перед миграцией); `Database__Provider=Postgres` — Supabase Postgres, таблицы в
  схеме `purchase_memory`, миграции в `src/PurchaseMemory.Infrastructure.Postgres`.
  Миграции обеих баз применяются при старте.
- Фото: по умолчанию папка `data/receipts/`; `Storage__Provider=S3` — закрытый
  бакет Supabase Storage. Хранится оригинал + сжатая копия (≤ 2400 px, JPEG 82,
  без EXIF/GPS); UI показывает копию, распознавание — оригинал (переключатель
  `ReceiptImages__AnalysisSource`). Переменные и секреты —
  `docs/ПЕРЕМЕННЫЕ_И_СЕКРЕТЫ.md`.
- **Категории и бренд** (`РЕЗУЛЬТАТЫ_КАТЕГОРИИ_И_БРЕНД.md`): двухуровневое
  дерево (готовое + свои категории), одна основная категория и бренд у
  товара, источник `Suggested` (AI) / `Confirmed` (человек). Решение человека
  главное, AI его не перезаписывает. Подсказки даёт `gpt-6-luna`
  (`Categorization__*`) в фоне после сохранения покупки; backfill запускается
  вручную, `POST /api/products/categorization/backfill`. Теги — см. ниже.
- **Аналитика** (`РЕЗУЛЬТАТЫ_АНАЛИТИКА.md`): вопрос своими словами →
  `gpt-6-luna` (`Analytics__*`, reasoning Low) переводит его только в
  типизированный план (метрика, фильтры, период, разбивка); модель не пишет SQL
  и не считает. Сервер проверяет план (`AnalyticsPlanValidator`), сам считает
  цифры в `AnalyticsCalculator` и пишет вывод шаблонами (ru/en). Правка фильтров
  чипами — `POST /api/analytics/run` без модели; вопрос — `POST
  /api/analytics/ask`, лимит 20 в час на пользователя. MCP: `run_analytics_plan`.
- **Очередь «Нужно проверить»** (`РЕЗУЛЬТАТЫ_НУЖНО_ПРОВЕРИТЬ.md`): считается на
  лету из сохранённых данных без AI и без своих таблиц — нераспознанные и
  несохранённые чеки, несходящиеся суммы, строки без цены, несопоставленные
  строки, неподтверждённые и отсутствующие категории. `GET /api/review-queue`,
  `GET /api/review-queue/count` (значок на вкладке «Главная»), MCP `list_review_queue`.
- **Редактирование сохранённой покупки** (`РЕЗУЛЬТАТЫ_РЕДАКТИРОВАНИЕ_ПОКУПКИ.md`):
  страница `/purchases/{id}` с режимом «Исправить»; `GET`/`PUT
  /api/purchases/{id}` (полный снимок, `expectedUpdatedAt` → 409 при чужой
  правке, выбор товара `auto`/`existing`/`new`). Выбор человека становится
  псевдонимом `HumanConfirmed`; снимок чека и его история правок обновляются
  вместе с покупкой. Пункты очереди ведут прямо в редактор на нужное поле.
- **Впечатления о товаре** (`РЕЗУЛЬТАТЫ_ВПЕЧАТЛЕНИЯ.md`): таблица
  `product_impressions` — оценка `dislike`/`neutral`/`like`, заметка, фото
  впечатления (только сжатая копия без EXIF, префикс `impressions/` в том же
  хранилище). Привязка к строке покупки; у каждого участника своя история,
  только дописывается, своё можно мягко удалить (чужое — 403). Правка покупки
  переносит впечатления на новую строку с тем же названием. `POST
  /api/impressions` (multipart), списки по товару/покупке/строке,
  `GET /api/impressions/unrated` для блока «Оценить недавнее». MCP (чтение):
  `list_product_impressions`.
- **Фильтр по категориям и брендам** (`РЕЗУЛЬТАТЫ_ФИЛЬТРЫ.md`): `GET
  /api/purchases` и `GET /api/products` принимают `categoryId` (группа
  включает подкатегории), `uncategorized=true`, `brand` (часть
  нормализованного бренда, без учёта регистра и польских букв). Покупка
  подходит, если хоть одна её строка связана с подходящим товаром; такие
  строки помечены `matchesFilter`. `GET /api/brands` — список брендов.
  Фильтры UI живут в адресе страницы. MCP: `search_purchases` с фильтрами,
  `list_brands`.
- **Теги товаров** (`РЕЗУЛЬТАТЫ_ТЕГИ.md`): таблицы `product_tags` (уникальность
  по нормализованному имени — без регистра и польских букв, до 40 символов) и
  `product_tag_links` (товар↔тег, до 20 тегов на товар). Теги создаёт только
  человек. `GET/POST /api/tags`, `PUT/DELETE /api/tags/{id}` (удаление снимает
  связи, товары остаются), `PUT /api/products/{id}/tags` (полная замена).
  Фильтр `tagId` у `GET /api/products` и `GET /api/purchases` — по И с
  категорией и брендом, несколько `tagId` — нужны все. Изменения тегов пишутся
  в журнал товара. UI: теги на карточке товара, «Управление тегами», фильтр
  «Тег» в ленте и каталоге. MCP: `list_tags`, `tagId` в `search_purchases` и
  `search_products`.
- **AI tag suggestions** (`РЕЗУЛЬТАТЫ_ПОДСКАЗКИ_ТЕГОВ.md`): `POST
  /api/products/{id}/tag-suggestions?locale=ru|en` — Claude Haiku 5.5
  (`TagSuggestions__*`, effort Low, key `ANTHROPIC_API_KEY`) picks 0–5 of the
  household's existing tags (codes `tN` in a strict enum, re-checked server
  side). Never applied automatically: «Предложить теги» on the product card,
  each hint accepted via `PUT /api/products/{id}/tags` or dismissed. No tags to
  offer → empty answer without a call; no key/error → 503
  `tagSuggestionsUnavailable`; 30/hour per user. Contract `ITagSuggester`.
- **Теги в аналитике** (`РЕЗУЛЬТАТЫ_АНАЛИТИКА_ТЕГИ.md`): в плане есть фильтр
  `tags` (несколько — по И, тег сужает категорию/название) и разбивка
  `groupBy: tag` (строка считается под каждым тегом товара, остальное — «Без
  тега»; итог и покрытие — без задвоения, `coverage.multiTaggedLines`).
  Неизвестный тег убирается с заметкой `unknownTag`. Модель видит до 100 самых
  используемых тегов кодами `tN` в строгом enum; списки в промпте помечены как
  данные. UI: поле «Тег» и «По тегам» в «Изменить», пояснение о пересечении под
  таблицей. MCP `run_analytics_plan` принимает теги.
- **Тег в «Нужно проверить»** (`РЕЗУЛЬТАТЫ_НУЖНО_ПРОВЕРИТЬ_ТЕГИ.md`):
  `GET /api/review-queue?tagId=…` (несколько — по И, неизвестный — 400, как в
  ленте). Проблемы товара — если тег у товара; проблемы чека — если хоть одна
  строка ссылается на товар с тегом; нераспознанные чеки и несопоставленные
  строки под фильтр не попадают. Счётчик на вкладке «Главная» (`/count`)
  остаётся общим. UI: строка «Тег» в окне фильтров (`?tag=` в URL), общий
  компонент `TagFilterRow` для ленты, каталога и очереди. MCP `list_review_queue` принимает `tagIds`, `categoryId` и
  `uncategorized` (как HTTP-фильтр очереди).

- **Строки чека на фото** (`РЕЗУЛЬТАТЫ_ПОДСВЕТКА_СТРОК.md`, `РЕЗУЛЬТАТЫ_СВАЙП_ПРОВЕРКА.md`,
  `РЕЗУЛЬТАТЫ_КАРУСЕЛЬ_СТРОК.md`): карусель строк `LineCarousel`
  (`features/line-review/`) — фото едет к строке, строка правится на месте,
  свайп/стрелки/точки, «Верно, дальше». На «Чек распознан» — `CaptureLineReview`
  (вместо удалённого `IssueReview`; полный редактор — «Магазин, дата и итог»), в
  покупке — окно `PurchaseLineReview` (вместо стопки карточек `LineReview`);
  фото с выделением и pinch-zoom (`features/receipt-photo/`).
  Отметки «проверено» сначала на телефоне, на сервер — пакетами
  (`POST /api/purchases/line-approvals`, колонки `Approved*` в `purchase_items`).
  Рамки — доли одного фото; чек из нескольких фото и строки без рамки — целое фото.
- **Printed-text highlight** (plan #1 stage 1.3, `РЕЗУЛЬТАТЫ_1_3_ВЫДЕЛЕНИЕ_ТЕКСТА.md`):
  optional Azure Document Intelligence `prebuilt-read` (`IReceiptTextLocator`,
  env `AZURE_DOCINTEL_ENDPOINT` / `AZURE_DOCINTEL_KEY`; absent → off, Haiku frame
  as before). Background worker `ReceiptTextLocationWorker` (DB-driven queue, new
  receipts first, then backfill; budget `TextLocation__*`, F0-paced) sends the
  single viewing photo, stores the OCR layout in `receipt_text_layouts` and
  per-line outlines (`receipt_capture_items.TextPolygons` JSON, `BoxSource`).
  Matching (`ReceiptTextMatcher`, port of `highlight_study`) re-runs on every
  review/purchase correction. API: `textPolygons` + `boxSource` next to
  `boundingBox`. Web: `TextHighlight` SVG ("combo") in `LinePhoto` (line carousel,
  editor line sheet); window fits the outlines.

- **Since 2026-10-16 (short, English):**
  - Every receipt line becomes a product (flag «проверить», merge, manual
    create); «Ревью» hub on Главная; AI display names PL + RU, from text and
    from the first product photo (`РЕЗУЛЬТАТЫ_1_1…1_6`, `РЕЗУЛЬТАТЫ_ФОТО_НАЗВАНИЯ_V2.md`).
  - Product photos and barcodes are stored on the server (Supabase Storage,
    `products/` prefix), scan in the shop, remembered codes
    (`ПЛАН_ФОТО_И_ШТРИХКОД_ТОВАРА.md`, `РЕЗУЛЬТАТЫ_ФОТО_ШТРИХКОД_2…4.md`).
  - Find by photo (`ProductPhotoSearch__Enabled`) and haul photo → receipt
    lines (`HaulPhoto__Enabled`) are deployed with the switches OFF until
    measured on the owner's photos.
  - Every image decode is charged its whole memory footprint against a
    per-call cap and a process-wide gate (`ImageDecodeGate`,
    `РЕЗУЛЬТАТЫ_ЗАЩИТА_БОЛЬШИХ_КАРТИНОК.md`); Render free has 512 MB.
  - Production: Render (Docker image built on the Mac by
    `scripts/publish-image.sh`, deployed by digest) + Supabase Postgres,
    Storage and Auth.
