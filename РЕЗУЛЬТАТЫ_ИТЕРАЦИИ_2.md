# Результаты итерации 2

Дата прогона: 16 июля 2026 года. Машина: MacBook Pro M4 Pro, 48 ГБ RAM. Ollama 0.31.1.

## Итог

Прототип жизнеспособен: один качественный снимок чека проходит `PWA/REST → локальный OCR → редактирование → SQLite → поиск` без облачного LLM. После дополнительной Apple-итерации основной нативный pipeline стал быстрее и сам исправляет проверяемые скидки, но очень маленькие изображения всё равно требуют ручной проверки.

Рабочая конфигурация на Mac теперь такая:

```text
Apple Vision OCR → Translation PL→EN → Foundation Models → C#-валидация → проверка человеком → SQLite
```

Если Apple Intelligence или sidecar недоступен либо результат проваливает жёсткую проверку, router повторяет запрос через `glm-ocr:latest → qwen3.5:4b`. Docker сразу использует Ollama.

Apple и Ollama теперь реализуют общий `IReceiptRecognitionPipeline`. Router получает коллекцию реализаций через DI и выбирает цепочку по строковым `Pipeline`/`FallbackPipelines` из конфигурации. Поэтому будущий локальный или облачный pipeline можно добавить без изменения логики router.

## Сравнение моделей

Оценка учитывает магазин, дату, итог, количество строк, фрагменты названий и совпадение суммы строк с итогом. Подробные структурированные ответы лежат в `test-data/receipts/benchmarks/latest.json`.

| Pipeline | Успешно | Средний балл успешных | Среднее время | Вывод |
|---|---:|---:|---:|---|
| Apple Vision → Translation → Foundation | 3/3 | 79,3 | 7,5 с | Лучший default на Mac: 95/93 на Biedronka и хотя бы правдоподобный черновик 50/100 на сложном Lidl |
| GLM-OCR → Qwen 4B | 2/3 | 92,5 | 12,4 с | Лучшее качество на нормальных изображениях; не прочитал образец шириной 230 px |
| Qwen 4B vision | 3/3 | 60,3 | 13,4 с | Лучший простой fallback; 85/93 на Biedronka, но 3/100 на маленьком Lidl |
| Qwen 9B vision | 3/3 | 59,3 | 19,6 с | Медленнее 4B и не точнее на этом наборе |
| MiniCPM v4.6 | 3/3 | 45,3 | 7,7 с | Быстрый, но опасно искажает суммы и даты |
| Gemma 4 12B MLX | 3/3 | 5,3 | 15,2 с | Для этого pipeline непригодна: галлюцинировала одинаковый чек Żabka |

Важно: 92,5 у гибрида — среднее только двух успешных запусков. Третий пример не прочитан, поэтому это не «92,5% точности» и не production-метрика.

## Наблюдения

- На реальном фото Biedronka гибрид правильно нашёл магазин, дату, итог 8,27 zł и три позиции, но не применил скидку 2 zł к третьей строке. Backend показал расхождение 10,27 против 8,27; в end-to-end тесте строка была исправлена на 2,99 до сохранения.
- Новый Apple pipeline на том же фото за 5,8 с получил 95/100 и автоматически восстановил скидку: gross 4,99, скидка 2,00, финальная строка 2,99; сумма строк совпала с 8,27.
- На e-paragon Apple pipeline получил 93/100 за 4,6 с. На Lidl — 50/100 за 12,3 с: итог 102,62 и сеть распознаны, но плохое исходное разрешение потеряло товары и исказило дату.
- C#-валидатор применяет скидки, исправляет потерянный десятичный разделитель (`18460 → 18,46` при итоге 102,62), отклоняет позиции дороже всего чека и включает fallback при расхождении более 50%. Меньшее расхождение показывается пользователю как предупреждение.
- На чистом e-paragon Biedronka гибрид правильно извлёк все проверяемые поля и обе позиции.
- Официальный пример Lidl имеет всего 230×371 px. GLM-OCR не получил надёжного текста, а vision-модели уверенно выдумывали даты/магазин или видели только 6–8 из 13 строк. Это хороший негативный тест: приложение не должно считать любой JSON достоверным.
- Qwen иногда оборачивал structured output в Markdown fence и игнорировал имена полей схемы. Parser усилен явным контрактом ключей и безопасным снятием внешнего ```json-блока; добавлен регрессионный тест.
- Более крупная модель не гарантировала улучшение. На этой машине Qwen 4B — разумный баланс скорости и качества.

## Что проверено автоматически

- .NET solution: build без предупреждений и ошибок;
- 25/25 backend/integration tests, включая скидки, decimal repair и арифметическую границу fallback;
- `dotnet format --verify-no-changes`;
- frontend unit test и production PWA build;
- Docker image `purchase-memory:iteration-2` и связь контейнера с нативным Ollama;
- fresh SQLite migration и обновление старой базы с сохранением прежних записей;
- magic-byte validation, лимит 15 МБ, SHA-256 и защита пути изображения;
- retry после ошибки, идемпотентный повторный save и `SourceReceiptId`;
- responsive layout 390×844 без горизонтального overflow;
- камера input содержит `capture=environment`, форматы JPEG/PNG/WebP;
- живой end-to-end Biedronka с исправлением скидки и появлением покупки в PWA-истории.

## Ограничения набора

В интернете найдено много современных чеков Żabka, Auchan и Carrefour, но их изображения защищены авторским правом или опубликованы пользователями без разрешения на повторное использование. Они сохранены как ссылки, а не скопированы в проект. Для E.Leclerc найден только синтетический образец. Репозиторий содержит один CC BY-SA снимок и два официальных визуальных примера для приватного QA.

Поэтому следующий benchmark должен использовать 30–50 собственных чеков семьи с ручной разметкой и отдельными группами: хороший снимок, перспектива, тень, смятый чек, длинный чек и низкое разрешение.

## Рекомендации

1. Использовать Apple pipeline default-вариантом при нативном запуске на совместимом Mac; сохранить Ollama fallback и обязательную ручную проверку.
2. Не использовать Gemma 4 12B и MiniCPM для автоматического сохранения чисел.
3. В следующей итерации добавить preprocessing: поворот, перспектива, контраст, проверка минимального разрешения и разбиение длинного чека.
4. На собственных чеках сравнить текущий Apple Vision OCR с PaddleOCR и Tesseract; LLM оставить структурирующим parser.
5. Добавить confidence/причины сомнения по каждому полю и запрещать сохранение без подтверждения арифметических предупреждений.
6. Для поиска перейти на SQLite FTS5 и отдельный нормализованный каталог товаров; embeddings пока не нужны.
7. Для телефона использовать HTTPS в приватной сети. До появления авторизации не выставлять backend с реальными чеками в публичный интернет.
