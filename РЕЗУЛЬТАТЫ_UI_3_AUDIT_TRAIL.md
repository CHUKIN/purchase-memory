# UI-3 — audit trail для правок на этапе review (10 сентября 2026)

Последний оставшийся кусок UI-3 реализован и принят независимым review.

## Что сделано

- При правке чека на review (`ReviewAsync`) каждое реальное изменение поля или
  удаление распознанной позиции пишется в append-only таблицу
  `receipt_review_audit_entries` (actor, поле, тип изменения, старое/новое
  значение, время) — в одной транзакции с самим review, без окна
  рассинхронизации.
- Actor — заглушка `"Owner"` (константа), без реальной авторизации: в
  приложении её пока нет вообще, схема готова к замене на настоящего
  пользователя без реструктуризации.
- История видна в самом `IssueReview.tsx` — сворачиваемый блок «История
  изменений», подгружается лениво только при раскрытии, RU/EN, уважает
  `prefers-reduced-motion`.
- Диффер сравнивает типизированные значения (decimal/DateTimeOffset), а не
  форматированные строки — это реальный баг, найденный и исправленный в
  процессе (SQLite округляет `1` → `1.0`, что давало ложные срабатывания на
  повторной отправке того же review). Независимый review воспроизвёл и
  подтвердил исправление вживую.
- Миграция чисто аддитивная (`CreateTable` + индекс, без `AlterColumn`).

## Известное ограничение (не блокер, но зафиксировано явно)

Сопоставление позиций чека для диффа — **по индексу**, а не по стабильному
id (в review-payload нет стабильного идентификатора позиции). Это не просто
неполнота — при удалении/вставке позиции **не в конце списка** список
записей после неё сдвигается, и лог получает недостоверную запись: например,
удаление первой позиции («Apples») при показанном списке из двух позиций
задним числом читается как «Apples переименовано в Bread» + «Bread удалено»,
хотя по факту Bread никто не трогал. Обнаружено и подтверждено independent
review вживую (не гипотетически).

**Не блокирует приёмку** этого среза (принято с этим ограничением, брифом
допускалось), но стоит учитывать при чтении истории — совпадения записей по
позиции ближе к началу списка чека могут быть недостоверны. Если это станет
проблемой на практике — нужен стабильный per-item key в самом payload
review (например, серверный id позиции), а не позиционное сопоставление.
