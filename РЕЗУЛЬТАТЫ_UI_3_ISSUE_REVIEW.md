# Purchase Memory — результаты UI-3, срез «issue-based review»

Дата реализации: 29 августа 2026
Статус: реализован второй срез UI-3. **UI-3 целиком не завершён.** Полный
редактор как вторичный режим сделан именно в этом срезе, а audit trail
применённых исправлений остаётся будущей работой. Привязка неточности к
фрагменту фотографии была открытым вопросом этого среза и сделана в следующем —
см. `РЕЗУЛЬТАТЫ_UI_3_ФРАГМЕНТ_ФОТО.md`.

## Результат

Чек, требующий внимания, больше не открывается сразу в полном редакторе всех
полей. Основным входом стал экран точечной проверки: список карточек, по одной
на каждую найденную неточность. Карточка называет проблему обычными словами,
показывает, что именно распознала модель, предлагает исправление и даёт поле
ввода, ограниченное ровно теми значениями, о которых идёт речь. Полный редактор
никуда не делся и не изменился — он открывается явным действием «Открыть полный
редактор» и остаётся открытым до конца визита.

Плоский список строк-предупреждений `Warnings` у покупки заменён структурой
`Issues`: тип, номер и название позиции, распознанное значение, предлагаемое
исправление. Лента UI-3 и её фильтр `needsAttention`/`reviewed` теперь работают
поверх этой структуры с прежней семантикой «нужно проверить, если неточности
есть».

## Решения, принятые в рамках среза

- **Чистое переименование `Warnings` → `Issues` у покупки, без слоя
  совместимости.** У этой формы JSON нет внешних потребителей: её читают только
  собственный фронтенд и собственный MCP-инструмент, оба обновлены в этом же
  изменении. Держать рядом производный список строк «на всякий случай» —
  ровно тот балласт, который `AGENTS.md` запрещает.
- **Один детектор на две поверхности.** `PurchaseDraftIssueDetector` —
  единственное место, где решается «нужно ли внимание». Им пользуется и
  сохранённая покупка (`PurchaseDraftView`), и ещё не сохранённый чек
  (`ReceiptCaptureView`). Иначе экран проверки чека и статус в ленте разъехались
  бы при первом же изменении правил.
- **У чека `Warnings` сохранены рядом с `Issues`.** Предупреждения чека
  покрывают и то, что этот срез не структурирует: нераспознанный магазин, дату,
  валюту, отсутствие позиций. Полный редактор продолжает показывать их
  как раньше, а `Issues` — это тот их подмножество, по которому можно
  действовать поштучно. Превращать все семь видов предупреждений в типы
  неточностей — отдельный разговор, в scope не входило.
- **Сравнение сумм считается только когда все строки заполнены.** Пока у части
  позиций нет суммы строки, актуальны именно карточки `MissingItemPrice`, а
  карточка расхождения итога лишь повторяла бы их другими словами.
- **`MissingItemPrice` срабатывает и когда известна только сумма строки.**
  Условие — `UnitPrice` **или** `LineTotal` равно `null`, как и просил бриф.
  Распознанная половина попадает в `RecognizedValue`, чтобы карточка показала
  человеку, от чего отталкиваться.
- **Локализация — на фронтенде, по типу неточности.** Backend отдаёт
  `RecognizedValue` (число с валютой) и английский `SuggestedFix`. Это
  fallback: интерфейс рисует русский и английский текст из `type` и
  структурных полей, а к строке от сервера обращается только для типа, которого
  ещё не знает. Иначе язык интерфейса определял бы сервер.
- **Сохранение из точечной проверки заблокировано, пока неточности не сняты.**
  Кнопка «Сохранить покупку» на этом экране неактивна, пока хоть одна карточка
  не помечена исправленной. Подтверждение в два клика при этом работает в обоих
  режимах, а не только в полном редакторе: первое нажатие всегда отправляет
  снимок на пересчёт, и если сервер всё же вернул неточности, сохранение
  откладывается до второго, осознанного нажатия. В точечной проверке карточки
  обычно перекрывают эту ветку заранее, и она срабатывает только когда сервер
  не согласен с клиентской проверкой разрешённости. Пропускать второе нажатие
  в этом случае нельзя: пользователь видел бы все карточки исправленными, а
  сохранение молча не срабатывало бы, и выхода из этого состояния не было бы.
  В полном редакторе кнопка честно меняет подпись на «Всё равно сохранить».
- **Прочие предупреждения не блокируют сохранение в точечной проверке.**
  Экран честно отвечает только за структурированные неточности, поэтому
  нераспознанный магазин там не должен превращаться в невидимую преграду.
  Проверка перед сохранением смотрит на `issues` в этом режиме и на прежние
  `warnings` — в полном редакторе.
- **Разрешённость карточки пересчитывается на клиенте.** Правила повторяют
  `PurchaseDraftIssueDetector`, чтобы карточка отмечалась исправленной без
  похода на сервер. Авторитет остаётся за сервером: при сохранении он
  пересчитывает неточности заново.
- **Удаление позиции из карточки не предлагается.** Оно сдвинуло бы позиции и
  обесценило `ItemPosition` у остальных неточностей. Удаление живёт в полном
  редакторе, и текст подсказки прямо туда и отправляет.
- **Новых npm-зависимостей нет.** Иконки взяты из уже подключённого
  `lucide-react`, состояния — из существующих `Surface`, `StatusBadge`,
  `EmptyState`.

## Backend

### Прикладной слой

`src/PurchaseMemory.Application/Purchases/PurchaseDraftIssue.cs` — новый файл:

```csharp
public enum PurchaseDraftIssueType { ReceiptTotalMismatch, MissingItemPrice }

public sealed record PurchaseDraftIssue(
    PurchaseDraftIssueType Type,
    int? ItemPosition,      // null для неточности уровня чека
    string? ItemName,       // null для неточности уровня чека
    string RecognizedValue, // «9.00 PLN» либо пустая строка
    string SuggestedFix);   // английский fallback
```

Там же `PurchaseDraftIssueItem` (позиция, название, цена, сумма строки) — форма,
в которую проецируются и покупка, и чек, — и `PurchaseDraftIssueDetector.Detect`.
Допуск сравнения денег прежний, `0.01`.

`PurchaseDraftView.Warnings` заменено на
`Issues: IReadOnlyList<PurchaseDraftIssue>`. Приватный `CreateWarnings` в
`PurchaseDraftService` и ставшая ненужной константа допуска удалены,
`MatchesStatus` считает по `Issues.Count`.

`ReceiptCaptureView` получил `Issues` рядом с существующим `Warnings`;
`ReceiptProcessingService.CreateView` заполняет оба.

**Миграций нет: схема БД не изменилась.** Неточности, как и прежние
предупреждения, вычисляются из текущего снимка на каждом чтении.

### REST-контракты

`GET /api/purchases` — в каждом элементе `items[]` поле `warnings` заменено на
`issues` (breaking change относительно предыдущего среза):

```json
{
  "issues": [
    {
      "type": "receiptTotalMismatch",
      "itemPosition": null,
      "itemName": null,
      "recognizedValue": "148.40 PLN",
      "suggestedFix": "Correct the receipt total or the line totals so that they match."
    },
    {
      "type": "missingItemPrice",
      "itemPosition": 3,
      "itemName": "CHLEB ŻYTNI",
      "recognizedValue": "",
      "suggestedFix": "Set the price for this item or remove it."
    }
  ]
}
```

`type` уходит в JSON как camelCase-строка (`receiptTotalMismatch`,
`missingItemPrice`), а не как число: числовой enum на границе HTTP молча
ломается при любой вставке нового значения в середину.

`GET /api/receipts/{id}`, `POST /api/receipts`, `POST /api/receipts/{id}/process`,
`PUT /api/receipts/{id}/review` — в `ReceiptResponse` добавлено поле `issues`
рядом с сохранённым `warnings`.

`POST /api/receipts/{id}/save` возвращает `PurchaseResponse`, то есть тоже с
`issues` вместо `warnings`.

Параметры запросов, коды ответов и фильтры ленты не менялись.

### MCP

`src/PurchaseMemory.Api/Mcp/PurchaseTools.cs` логировал число предупреждений
созданного черновика — теперь логирует `created.Issues.Count`.

Инструменты `create_purchase_draft`, `update_purchase_draft` и
`search_purchases` возвращают `PurchaseDraftView` целиком, поэтому новый
`PurchaseDraftIssueType` попал и на MCP-провод — но там его сериализует SDK, а
не ручной маппинг из `PurchaseEndpoints`. По умолчанию это дало бы числа `0` и
`1` при строках в REST, то есть ровно тот разъезд форматов, против которого
написан абзац выше. Поэтому в `Program.cs` в `mcpJsonOptions` добавлен
`JsonStringEnumConverter(JsonNamingPolicy.CamelCase)`: обе поверхности отдают
`receiptTotalMismatch` и `missingItemPrice` одинаково.

## Frontend

- `src/features/issues/issueText.ts` — общий слой: `issueCopy` (локализованные
  заголовок, описание, подсказка по `type`), `issueKey` (стабильный ключ, один
  тип повторяется на разных позициях) и `isIssueResolved` — клиентское
  повторение серверных правил.
- `src/features/receipts/IssueReview.tsx` + `IssueReview.module.css` — новый
  экран. Заголовок со счётчиком оставшихся неточностей и `StatusBadge`, список
  карточек, внизу два действия: «Открыть полный редактор» и «Сохранить
  покупку». Карточка расхождения итога даёт поле «Итого» и кнопку «Взять сумму
  строк: N». Карточка отсутствующей цены даёт «Цена» и «Сумма»; для позиции с
  количеством 1 заполнение одного поля проставляет оба, потому что там это одно
  и то же число. Исправленная карточка помечается «Исправлено».
- `src/features/receipts/CapturePage.tsx` — `ReceiptDetailPage` выбирает режим:
  при `issues.length > 0` и пока полный редактор не запрошен показывается
  `IssueReview`, иначе прежний `ReviewForm`. Сам `ReviewForm` не тронут.
  Логика сохранения получила разный признак блокировки для двух режимов.
- `src/features/purchases/PurchaseFeed.tsx` — карточка ленты считает статус по
  `issues` и выводит локализованные заголовки неточностей вместо серверных
  строк.
- `src/api/types.ts` — `PurchaseDraftIssueType`, `PurchaseDraftIssue`, `issues`
  у `ReceiptView` (рядом с `warnings`) и у `PurchaseView` (вместо `warnings`).

Все новые строки есть на русском и английском, включая русские формы
множественного числа для счётчика оставшихся неточностей.

## Ограничения

- Фрагмент фотографии рядом с неточностью не показывается: в пайплайне
  распознавания нет координат. Открытый вопрос описан в
  `ВОПРОСЫ_ДЛЯ_ОБСУЖДЕНИЯ.md`.
- Audit trail применённых исправлений отсутствует: сохраняется только итоговый
  снимок, как и раньше.
- Типов неточностей ровно два. Нераспознанные магазин, дата, валюта и полное
  отсутствие позиций остаются плоскими предупреждениями чека и правятся в
  полном редакторе.
- Точечная проверка доступна только для ещё не сохранённого чека на
  `/receipts/{id}`. Из ленты сохранённая покупка по-прежнему не редактируется:
  карточка лишь перечисляет неточности.
- «Восстановить нераспознанную строку» и «связать с существующим товаром» —
  территория UI-4, не делалось.
- Разрешённость карточки на клиенте — повторение серверных правил. При
  расхождении прав сервер: он пересчитывает неточности при сохранении.
- Ответ `GET /api/purchases` и `ReceiptResponse` сменили форму. Внешних
  потребителей у них нет.

## Как открыть

```bash
./scripts/run-local.sh
```

Открыть `http://127.0.0.1:5099`, затем:

- `/purchases/new` — снять чек; при неточностях его детальная страница
  `/receipts/{id}` откроется сразу в точечной проверке;
- на этой же странице «Открыть полный редактор» — прежний редактор всех полей;
- `/` и `/purchases` — лента со статусами, посчитанными по новым неточностям.

Для UI Lab:

```bash
cd src/PurchaseMemory.Web
npm run storybook
```

Открыть раздел `Purchase Memory / IssueReview / Production`.
