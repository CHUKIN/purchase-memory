## Scanner page

- Where: `scanner-lab.html` in `src/PurchaseMemory.Web/` (project root of Vite).
- Kept out of production: a second HTML file is not a Vite build input, so
  `npm run build` ignores it; it has no import from the app and nothing in the app
  imports it. Chosen over a dev-only route because a route would still sit in the
  production router and bundle. Verified: `dist` (wwwroot) JS/HTML has no
  `zxing`, `barcode` or `scanner-lab`; `sw.js` precache has none; main chunks
  unchanged (`index` 440.82 kB / 127.03 kB gzip, `components` 862.74 kB /
  183.38 kB gzip, precache 74 entries / 2253.06 KiB, same hashes as before).
- Packages `barcode-detector` and `@vitejs/plugin-basic-ssl` are devDependencies.
- The decoder is imported on «Старт» (dynamic import), and the `.wasm` is served
  from our own server (no CDN call), as it would be in the PWA later.
- Features: rear camera 1280x720, EAN-13/EAN-8/UPC-A/UPC-E, vibration on hit,
  ms from camera start and from previous hit, average ms per frame, Open Food
  Facts lookup (only the barcode is sent), session list, «Скопировать
  результаты» (tab-separated text), torch button only if the track reports it,
  clear messages for camera denied / not HTTPS / no getUserMedia.

## Library choice

Chosen: `barcode-detector` 3.2.2 (MIT, polyfill of the web `BarcodeDetector` API
over `zxing-wasm` 3.1.3 = ZXing-C++ compiled to WASM; last published
2026-08-16, `zxing-wasm` 2026-10-06, actively maintained). Same API as native
Chrome/Android detector, so on browsers that have it, it can be dropped.

| | barcode-detector 3.2.2 | @zxing/browser 0.2.1 + @zxing/library 0.23.0 | html5-qrcode 2.3.8 |
|---|---|---|---|
| Engine | ZXing-C++ WASM | ZXing pure JS port | ZXing JS port |
| License | MIT | MIT / Apache-2.0 | Apache-2.0 |
| Last release | 2026-08 | 2026-04 (library) | 2023-04, unmaintained |
| Size (npm unpacked) | 0.26 MB + wasm 1.1 MB | 11.9 MB package | 2.6 MB |
| Lazy chunk, gzip | JS 15.1 kB + wasm 463.8 kB | not measured (JS port, larger) | not measured |
| Main bundle impact | 0 (dynamic import) | 0 if lazy | 0 if lazy |

WASM decoders are generally faster and better on small or blurred codes than the
JS ports; this is expected, not yet measured on the phone. Alternatives were
compared by published size and maintenance only, not by decoding runs.
Note: iOS Safari needs `getUserMedia` over HTTPS; WASM works in all iOS 16+.

## How to open

Stories: `cd src/PurchaseMemory.Web && npm run storybook`, open
`http://localhost:6006`, section "Prototype".

Scanner on the Mac itself (no camera test, just to see the page):
`npm run dev`, open `http://localhost:5173/scanner-lab.html` (localhost counts as
secure, a Mac webcam works).

Scanner on the iPhone (camera needs HTTPS):
1. Mac and iPhone on the same Wi-Fi.
2. `cd src/PurchaseMemory.Web && npm run dev:lab`.
3. The terminal prints `Network: https://192.168.x.x:5173/`. Use that IP.
4. On the iPhone open Safari at `https://<that IP>:5173/scanner-lab.html`.
5. Safari warns that the certificate is not trusted (self-signed, expected):
   «Показать подробности» → «посетить этот веб-сайт» → confirm.
6. Tap «Старт», allow the camera. Stop the server with Ctrl+C afterwards.

Limits: this tests Safari in a tab. The installed PWA on the Home Screen cannot
run it (the scanner page is not in the production build); installed-PWA camera
behaviour is checked in a later stage after a deploy approved separately. If
Safari refuses the self-signed page for the camera, fallback options:
a tunnel with a real certificate (e.g. `cloudflared tunnel`, not installed, needs
owner OK) or a one-off private deploy of the page; nothing was deployed.

## Known limitations

- Decoding speed on a real iPhone is unmeasured; the page was only served and
  fetched in dev (HTTP 200 for page, module and wasm), the camera was not run.
- Torch is usually unavailable in iOS Safari; the button hides then.
- Stories are mocks: no routing, no data, no real camera, i18n not wired.
