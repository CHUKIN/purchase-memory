# Results: swipe line review + pinch-zoom (2026-10-14)

Replaces the tap/swipe line viewer and its setting with one Tinder-style
review of a saved purchase's lines, and stores per-line «checked» marks.

## UI (purchase page `/purchases/{id}`)
- Lines header gets an icon button (ListChecks + `3/12`, aria «Проверить строки:
  проверено N из M») → review from the first unchecked line. Tapping any line
  (product or discount, with or without a receipt photo) opens the review right
  at it — no intermediate sheet. Checked lines show a small ✓ (sr text «, проверено»).
- `features/line-review/LineReview.tsx`: full-screen IonModal. Card = photo
  region with the outline (fills the free space, `fitWindow`) + name (≤3 lines),
  `qty unit × price`, sum, the product's discounts and price after discount
  (or, for a discount, which product it belongs to), product link status.
  Fits 375×667 and 812×375 (landscape: photo | info, buttons in a column).
  - Swipe right / ✓ «Строка верна» / → : mark, card flies off (220 ms, none with
    reduced motion), next unchecked line.
  - Swipe left / ✎ «Исправить строку» / ← : the existing `LineFields` form in a
    sheet; «Сохранить» saves the purchase (same full PUT snapshot as the editor,
    only that line changed), marks the new line checked, moves on. 409 → message,
    purchase is refetched; errors stay in the sheet.
  - Back (Undo2, «Предыдущая строка», Backspace); «Снять отметку «Проверено»» on
    a checked card; ✕ «Закрыть проверку».
  - Session order: tapped line first, then unchecked lines (wrapping); header
    button = unchecked only. End: «Все строки проверены» + «Проверить ещё раз»
    (all lines) or «Не проверено: N» + «Продолжить». Reopening shows only unchecked.
  - Progress «✓ 3/12» in the toolbar (aria «Проверено 3 из 12»); live region
    announces «Строка N из M: name, sum».
- Pinch-zoom: `receipt-photo/usePinchZoom.ts` (plain pointer events, no new
  dependency): two-finger pinch around the midpoint, one-finger pan when zoomed,
  double-tap toggles 1×/2.5×, max 5×, clamped so no gaps; corner button
  «Увеличить/Уменьшить фото» for mouse/keyboard. Photo and outline share one
  transformed layer (outline border compensated by `--pm-zoom`). Card swipe is
  ignored while zoomed and cancelled when a second finger lands.
- `receipt-photo/LinePhoto.tsx` replaces `ReceiptPhotoFocus` (measures its space
  with ResizeObserver; whole photo, no outline, when no usable box or a
  multi-photo receipt; outline only after the natural ratio is known).
- Editors (`LinesEditor`: receipt draft review + purchase editor): «Показать на
  фото» removed; the line sheet now shows the line on the photo (zoomable) above
  its fields. Drafts have no marks (not saved purchases).
- Removed: `ReceiptLineViewer` (+test, stories), `lineLocatorMode.ts`, the
  «Строки чека на фото» segment in Settings, `lineLocator.*` i18n (→ `lineReview.*`).
  The old `localStorage` key `purchase-memory.line-locator-mode` is left on devices (harmless).

## Marks: phone first, server in batches
- `features/line-review/approvalSync.ts` (`LineApprovalSync`, one per signed-in
  user, `localStorage` key `purchase-memory.line-approvals.v1:<userId>`): a swipe
  is stored at once (`pending`); batch goes out 5 s after the last swipe, at once
  at 20 pending, on `visibilitychange→hidden` / `pagehide` (fetch `keepalive`)
  and on `online`. Failure → retry 2 s, 4 s, … ≤ 60 s; 400 drops the batch
  (cannot succeed). Batches respect server limits (≤200 items, ≤20 purchases).
  A swipe made while its batch is in flight is re-sent. `notFound` entries are dropped.
- Merge (`useLineApprovals`): unsent marks always win; confirmed (`synced`) marks
  win until fresh purchase data agrees, the line is gone, or 10 min pass; a
  confirmed batch invalidates the purchase query. Unsent marks are flushed before
  any purchase PUT (swipe-left save and the full editor).

## Backend
- `PurchaseItem`: `ApprovedAt` (ms, nullable), `ApprovedByUserId` (≤200),
  `ApprovedByEmail` (≤320); `Approve` (first approval wins, idempotent),
  `RevokeApproval(at)` (ignored if older than the approval), `CarryApprovalFrom`.
  Marking does not change the purchase's `UpdatedAt` (no false 409 in editors).
- Migrations (additive, nullable columns on `purchase_items`): SQLite
  `20261014171920_AddPurchaseItemApprovals`, Postgres
  `20261014171932_AddPurchaseItemApprovals` (schema `purchase_memory`). SQLite
  one generated via a temporary design-time factory on a scratch DB (removed).
- `POST /api/purchases/line-approvals` body `{ items: [{ purchaseId, lineId,
  approved, at }] }` → `{ items: [{ purchaseId, lineId, status:
  applied|unchanged|notFound, approved, approvedAt }] }`. Approved-user policy like
  every endpoint; 400 for empty/missing fields/empty GUIDs/>200 items/>20
  purchases. Unknown purchase or a line not in that purchase → `notFound`, no
  change. Newest `at` per line wins inside a batch; future `at` clamped to now.
  Service: `PurchaseLineApprovalService` (Application).
- Detail DTO items: `approved`, `approvedAt`, `approvedByEmail`.
- Edit carry-over: `PUT /api/purchases/{id}` items accept optional `id` (the line
  it continues). Approved old line → replacement keeps the mark (who/when), even
  if its content changed (editing = looking at the line; swipe-left also marks
  the new line). Lines sent without `id` (older clients/MCP) start unchecked.
- «Household»: data is shared by all approved users in this version, so there is
  no other household to isolate; isolation = 401/403 + `notFound` (as in analytics history).

## Known limitations
- Accepted for v1: if the pre-PUT flush fails but the PUT succeeds, those unsent
  marks point at replaced lines and are dropped (`notFound`).
- Accepted for v1: two tabs of the app on one device overwrite each other's
  stored mark queue (last writer wins in localStorage).
- Not checked on a real iPhone (pinch tested only via unit tests; pan/double-tap in a desktop browser).
- `keepalive` flush on hide needs the token source to answer quickly (supabase-js reads its session from memory).
- Concurrent edit by another member between a swipe and its batch → mark reported `notFound` and dropped.
- Not run on Postgres locally (migration generated by EF, additive only).
- Drafts (before saving a receipt) have no marks.
